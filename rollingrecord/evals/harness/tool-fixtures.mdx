---
title: "Canonical Tool Fixtures"
description: "Injecting the real production tool set into kb_query cases, and validating mock_tools against it."
---

`tool_fixtures.py` (`evals/core/tool_fixtures.py`) loads the REAL production tool definitions an ai-engine operation sends, from generated JSON snapshots under `evals/fixtures/`. It exists so `kb_query` eval cases run against the true tool surface rather than a hand-written sandbox.

## Why the real tool set

`kb_query` cases used to hand-write a tiny two-tool sandbox (`searchContext` + `getRecordingTranscriptSnippet`). Production sends roughly 14 real tools (`KbToolSpec` in the Kotlin client), and the bot behaves differently under the full set — the sandbox masked real production bugs, such as the bot getting "stuck in card world" and refusing to pull a transcript. Evals must exercise the real tool set. When a `kb_query` case omits its own `tools` and `tool_instructions`, `AiEngineHttp` injects the canonical set; a case that supplies its own explicit `tools` keeps them, so migration of un-migrated sandbox cases is incremental. See [Kb tool spec](/rollingrecord/evals/kotlin-sut/kb-tool-spec).

## Fixture file and generation

The canonical spec for `kb_query` lives at `evals/fixtures/kb_query_tools.json`, shaped:

```json
{ "tools": [{"name": "...", "description": "...", "input_schema": {}}],
  "tool_instructions": "..." }
```

That file is GENERATED, not hand-written — the Gradle snapshot test `KbToolSpecSnapshotTest` serializes the Kotlin `KbToolSpec` into it and fails the build on drift. If the fixture is missing, `load_tool_fixture` raises `ToolFixtureError` carrying the regenerate command (run from `app/`):

```
./gradlew :app:testDebugUnitTest --tests "*KbToolSpecSnapshotTest" "-Dregenerate.kbtools=true"
```

The `-D` flag must be quoted — PowerShell otherwise splits it at the dot and Gradle reports a task-not-found error.

## Loading

`load_tool_fixture(operation)` returns a `ToolFixture` for the operation, parsed once and memoized in a process-wide cache keyed by operation name (guarded by a lock, because the runner drives cases on a thread pool). `_FIXTURE_PATHS` registers which operations have a fixture:

| Operation | Fixture path |
| --- | --- |
| `kb_query` | `evals/fixtures/kb_query_tools.json` |

`kb_query` is the only registered operation today; `extract` (4 server-side tools) can be added by dropping a `_FIXTURE_PATHS` entry once its tool set gets the same snapshot treatment.

`load_tool_fixture` raises `ToolFixtureError` when the operation has no registered path, the file is missing (with the regenerate command), the file is not valid JSON, or `_parse_fixture` finds a missing/empty `tools` array or a non-string `tool_instructions`. Parsing is strict — a malformed fixture means the Kotlin snapshot test produced a bad file, and tolerating it would let broken cases run.

## `ToolFixture`

| Field / property | Contents |
| --- | --- |
| `operation` | The ai-engine operation name. |
| `tools` | The production tool definitions — a list of `{name, description, input_schema}` dicts, byte-identical to what the Kotlin client sends. |
| `tool_instructions` | The production tool-usage instruction block. |
| `source_path` | The fixture file the data came from. |
| `tool_names` | Property — the wire names of every tool in the fixture, used to validate a case's `mock_tools` keys. |

## Validating mock_tools

`validate_mock_tool_names(operation, mock_tools, case_id)` checks that every key in a case's `mock_tools` is a real tool name present in the canonical fixture. A mismatch raises `MockToolNameError`, naming the offending key(s) and listing the valid tool names — catching typos and stale hand-written sandbox names (e.g. a leftover `searchContext`) after a case was supposed to migrate to the real tool set.

The check is meaningful only when the case uses the canonical tool set; the caller (`Runner._check_mock_tool_names`, see [Runner](/rollingrecord/evals/harness/runner)) skips it when the case supplies its own explicit `tools` — an un-migrated sandbox case — and it is a no-op when `mock_tools` is empty. A violation surfaces as a `stale_mock_tool_name` FAIL verdict so one stale case fails in isolation rather than aborting the run.
