`Runner` (`evalmode/core/Runner.kt`) is the run orchestrator. It checks access, loads cases, then drives each one through `corpus.prepare → SUT.call → judge → record` with bounded parallelism, emitting a single observable `EvalRunState` (`evalmode/core/EvalRunState.kt`) that the dashboard renders.

## The run loop

`run(suites, bucket?, resumeDone, resumeCostUsd)` is a `suspend` function wrapped in `coroutineScope`, so cancelling the calling scope aborts the run. Its sequence:

1. Emit `CheckingAccess`; call `access.check()`. On `Denied`, emit `Denied(reason)` and return.
2. Emit `LoadingCases(loaded, total)` per suite as `CaseLoader.loadSuite(...)` parses each — a determinate init bar. A parse failure or empty result emits `LoadFailed(message)`.
3. Seed a `ConcurrentHashMap<String, CaseProgress>` keyed by `fullyQualifiedId` (`<suite>.<id>`), pre-marking every case `PENDING`.
4. Launch one coroutine per case under a `Semaphore`, join all, then emit `Done` (or `Aborted` on cancellation).

Each case runs through `runOne(...)`: `CorpusResult.Skip` → `SKIP` (never a FAIL); a thrown SUT exception or a non-null `ActualOutput.error` → `SYSTEM_ERROR`; otherwise the resolved judge's `Verdict` maps to a terminal `CaseStatus`.

## Concurrency and the seeded-run exception

A `Semaphore(effectiveConcurrency)` caps in-flight cases. Concurrency defaults to `EvalConfig.MAX_CONCURRENCY` (4), but drops to **1** whenever any case in the run declares fixtures (`case.hasFixtures`). Seeded cases share the one per-user Room DB, so parallel execution could let one case's real `ask()` search surface another in-flight case's seeded rows (cross-case contamination — a "yesterday" case finding a "this morning" case's recording). Serializing makes each case's seed → run → teardown atomic. Non-seeded runs keep full parallelism. Shared run state (`ConcurrentHashMap`, `MutableStateFlow`, `CostLedger`) is thread-safe, so the parallel case coroutines update progress without a lock.

## Run state

`EvalRunState` is the one sealed source of truth the UI observes; the `Runner` is its only writer:

| State | Meaning |
| --- | --- |
| `Idle` | Nothing running. |
| `CheckingAccess` | `EvalAccess.check()` in flight. |
| `Denied(reason)` | Access refused — the lock screen. |
| `LoadingCases(loadedSuites, totalSuites)` | Parsing bundled case suites; determinate bar. |
| `LoadFailed(message)` | No cases found / a case file failed to parse. |
| `Running(counts, perCase, currentSuite, costUsd)` | Live counts, per-case rows, running suite, cost. |
| `Done(counts, perCase, costUsd, durationMs)` | Terminal success summary. |
| `Aborted(reason, counts, perCase, costUsd, durationMs)` | User-cancelled — partial snapshot kept and persisted. |
| `Failed(message, counts)` | Fatal infra failure — partial counts kept. |

## Case status and counts

`CaseStatus` tracks each row from `PENDING` through the in-flight states (`PREPARING_CORPUS`, `RUNNING`, `JUDGING`) to a terminal one (`PASS`, `FAIL`, `UNCERTAIN`, `SKIP`, `FLAKED`, `SYSTEM_ERROR`). Two mapping rules matter:

- `SYSTEM_ERROR` counts as a **failure** in `RunCounts.failed`, alongside `FAIL`.
- A FAIL or UNCERTAIN verdict on a case tagged `is_flake` routes to `FLAKED` instead, which is suppressed from the fail count.

`RunCounts` drives the dashboard's segmented bar: only `passed` (green) and `failed` (red) render as bar *segments*; `uncertain`, `skipped`, and `flaked` are shown as numbers. `passedFraction` / `failedFraction` give the segment widths.

## Cost ledger

`CostLedger` (`evalmode/core/CostLedger.kt`) aggregates dollar cost across the parallel run using an `AtomicLong` of micro-USD (1e-6 USD) — lock-free and free of floating-point accumulation drift. The runner charges two things into it:

- The **agent's** real `ai-engine` spend, priced via `EvalConfig.modelCostUsd(...)` from the SUT's reported tokens — charged on success *and* error alike (the bot burned tokens even on a max-rounds error).
- The **judge's** spend, which each LLM-backed judge adds through `JudgeContext.costLedger`.

## Verbose console logging

`onLog` emits two kinds of line into the dashboard's Console view. Per-case summary lines (`[PASS] suite.case — reason`) come from `logLine`; the run-end summary (`done · pass=… fail=… flaked=…`) is emitted by a direct `onLog(...)` call inside `run()`, not by `logLine`. A deeper `logVerbose` block surfaces, per case, the question asked, the seeded flag, round count and terminal reason, the tool calls, the retrieval summary, the bot's answer, and the verdict (kind, confidence, judge) — pasteable for deep triage. These are logcat-analog lines for the on-device Console, not the app's `FileLogger`.

## Resume after an OS kill

`run(...)` accepts `resumeDone: List<CaseProgress>` and `resumeCostUsd: Double`. Cases already graded in a recovered (OS-killed) run are pre-seeded as done and **not** re-run, and their prior spend pre-loads the ledger so the continued run's cost is cumulative. The `EvalViewModel` supplies these from a disk checkpoint — see [dashboard, results & upload](/rollingrecord/evals/on-device/results-ui) for the checkpoint mechanics.
