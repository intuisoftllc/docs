title: "Dashboard, Results & Upload"
description: "The on-device eval dashboard, per-run result JSON, OS-kill recovery, and Upload-to-PC."
---

The dashboard is the single screen mounted at the `EvalMode` debug route. It observes one `EvalViewModel`, renders whichever `EvalRunState` is live, and persists a per-run results JSON that can be pulled by ADB, saved to Downloads, or uploaded to the dev PC.

## EvalViewModel

`EvalViewModel` (`evalmode/ui/EvalViewModel.kt`) owns the `Runner`, exposes its live `state`, a verbose `log` for the Console, and the discovered `suites`. It is built by `EvalComponent.createViewModel()`. A run is single-flight — `runAll` / `runSuite` / `runBucket` no-op while one is active. On start it discovers suites off the main thread and checks for an OS-kill checkpoint. Helpers `countCases` / `previewCases` power the inline pre-run preview. When a run ends (cleanly *or* by cancel), `persistReport()` writes the report under `NonCancellable` so backing out mid-run never loses data.

## The dashboard screen

`EvalDashboardScreen` (`evalmode/ui/EvalDashboardScreen.kt`, top bar "AI Evals") maps each `EvalRunState` to a body:

| State | Body |
| --- | --- |
| `Idle` | "Ready to run" + controls. |
| `CheckingAccess` / `LoadingCases` | An initializing view — determinate bar while suites load, indeterminate otherwise. |
| `Denied` | The access lock screen, one message per `DeniedReason`. |
| `LoadFailed` / `Failed` | An error body. |
| `Running` | Current-suite card, segmented progress bar, stat dots, totals, and a live "Running now" list. |
| `Done` / `Aborted` | Summary (bar + stats + duration + cost) with tappable per-case rows. |

Staging a run picks a suite (or Run all) and swaps the content to an inline preview — case count, per-bucket breakdown, and the cases that would run — with the real "Run N" living in the pinned controls (no auto-run). A `BackHandler` intercepts back-press while a run is live and shows an exit sheet that aborts and saves the partial report before leaving. The whole screen is wrapped in `EvalV2Theme` to force the V2 palette over the overlays and sheets.

## Console overlay and case detail

- `EvalConsoleOverlay` (`evalmode/ui/EvalConsoleOverlay.kt`) is a full-screen black/white verbose Console — the on-device analog of watching the Python harness's stdout. It renders the `log` lines as monospace, tinting `[FAIL]`/`[SKIP]`/`[FLAKE]`/`[PASS]` lines, with a lock toggle for auto-scroll vs. free scroll and a `SelectionContainer` for copying a span.
- `EvalCaseDetailSheet` (`evalmode/ui/EvalCaseDetailSheet.kt`) opens on tapping a terminal case row: it shows the case identity, status badge, and the judge verdict breakdown (judge, verdict kind, confidence, cost, reason, and the per-child `details`) — selectable so a failing case can be copied into a bug note.

## Result files

`ResultWriter` (`evalmode/results/ResultWriter.kt`) persists a completed or aborted run as a JSON file, the Kotlin analog of the Python harness's `results/<date>/<uuid>.json`. The path is `{getExternalFilesDir}/evals/results/<yyyy-MM-dd>/<uuid>.json`. The payload carries `run_id`, `generated_at`, the producing build's `app_version_code` / `app_version_name` (run provenance now that evals run *in* the app), `aborted` / `interrupted` flags, `duration_ms`, `cost_usd`, a `counts` block, and a `cases[]` array (id, suite, status, plus — for every case with a non-null verdict, PASS included — the verdict, confidence, and judge, and — only for non-PASS verdicts — the per-child judge breakdown from `Verdict.details`, so a failure is diagnosable straight from the JSON).

## OS-kill recovery (checkpoint & resume)

As each case completes, the `EvalViewModel` calls `ResultWriter.checkpoint(...)`, overwriting an in-progress checkpoint at `evals/checkpoint.json` — deliberately **outside** the results dir so a live checkpoint is never listed as a finished run. A clean finish or user abort deletes it (`clearCheckpoint`); a process kill leaves it for `readInterrupted()` on next launch. The dashboard then offers a recovery dialog:

- **Continue** — `continueInterrupted()` re-runs only the not-yet-graded cases, keeping completed ones and their prior cost (via the runner's `resumeDone` / `resumeCostUsd`).
- **Save** — `saveInterrupted()` finalizes the checkpoint into a normal (interrupted-flagged) results file.
- **Discard** — drops it.

## Results browser and export

`EvalResultsOverlay` (`evalmode/ui/EvalResultsOverlay.kt`) lists every persisted run newest-first, backed by `EvalResultStore` (`evalmode/results/EvalResultStore.kt`), which walks the results dir, parses a light `RunSummary` per row, and can fully parse a run back into the same `RunCounts` + `CaseProgress` the live dashboard renders. Each run card shows a PASS/FAIL pill computed against `DEFAULT_PASS_FLOOR` (0.95) over *evaluated* cases (`passed / (passed + failed + uncertain)` — skipped and flaked don't count). The detail view offers:

| Action | What it does |
| --- | --- |
| Copy | Copies the run JSON to the clipboard. |
| Save to Downloads | Writes the JSON to public Downloads via MediaStore (API 29+). |
| Upload to PC | POSTs the JSON to the dev PC's `serve_apk.py` `/eval-results` endpoint — shown only when `EvalConfig.hasUploadUrl` is true (`EVAL_UPLOAD_URL` set in `.env.local`). |
| Delete | Removes the run file (confirmation dialog). |
