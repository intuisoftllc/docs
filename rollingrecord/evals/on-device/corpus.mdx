title: "Fixture Seeding & Corpus"
description: "How on-device eval cases seed and tear down real Room rows safely, behind the access gate."
---

The corpus layer resolves the Room data a case runs against, *before* the SUT runs. It is the one seam that lets seeded and (future) live tests coexist without a runner rewrite. `CorpusStrategy` (`evalmode/core/CorpusStrategy.kt`) is the interface; `SeededCorpus` (`evalmode/corpus/SeededCorpus.kt`) is the wired implementation.

## CorpusStrategy

```
suspend fun prepare(case: Case): CorpusResult   // Ready → run the SUT; Skip → record a SKIP
suspend fun teardown(case: Case)                 // reset after a case (no-op default)
```

`CorpusResult` is a sealed interface: `Ready` (proceed to the SUT) or `Skip(reason)` (record a `SKIP` with an actionable reason — never a FAIL). A `PassThroughCorpus` also exists as the Phase-1 placeholder (`prepare` always returns `Ready`); the graph the `EvalComponent` actually wires is `SeededCorpus`, which is a safe superset — a case with no `fixtures` block passes through as `Ready` with nothing seeded, so one run can mix seeded and non-seeded suites.

<Note>
The design also anticipates a `LiveCorpus` (no seeding — it checks `case.preconditions` against the real account DB and returns `Skip` when unmet). `RawCase` already carries a `preconditions` field and `Case.isLive` reflects it, but `LiveCorpus` is not yet implemented.
</Note>

## SeededCorpus

`SeededCorpus` delegates to a `FixtureSeeder` and tracks seeded ids per fully-qualified case id in a `ConcurrentHashMap`, so the parallel runner can seed and tear down many cases without a lock. `prepare` seeds and returns `Ready`; a seeding exception becomes `Skip("fixture seeding failed: …")` because an un-seeded case can't be judged fairly. `teardown` removes exactly the rows that case seeded.

## FixtureSeeder

`FixtureSeeder` (`evalmode/corpus/FixtureSeeder.kt`) plants a case's scratch corpus into the signed-in **test** account's real Room DB — the same "seed the real database so we truly know it works" approach the smoke tests take. Every seeded row is a real row exercising the whole stack (file existence, size, FTS, retrieval, context membership):

- **Recording** — a `RecordingEntity` whose `filePath` points at a real Opus file written to disk (a copy of the bundled `evals/audio/sample.ogg`; the audio need not match the transcript, since only the transcript is searched).
- **Transcript** — a fabricated `TranscriptEntity` with `status = "DONE"` and non-blank `text`, which fires the `transcript_fts` INSERT trigger so it is auto-indexed and searchable.
- **Contexts** — `ContextEntity` rows plus `ContextRecordingEntity` membership junctions linking named recordings (marked `incorporatedAt` so the extraction worker skips them).

### Fixture spec

`case.fixtures` declares the scratch corpus:

```json
{
  "recordings": [ { "name": "Team standup", "transcript": "…", "duration_ms": 90000 } ],
  "contexts":   [ { "name": "CS 101", "description": "…", "recordings": ["Team standup"] } ]
}
```

A recording spec supports `name`, `transcript`, `duration_ms` (or `durationMs`), and an optional recorded-at for date-sensitive cases — either `recorded_at_ms` (absolute epoch-ms) or `recorded_days_ago` (N days before now), defaulting to now. A context spec's `recordings` list links previously-seeded recordings by name.

## Safety and teardown

`FixtureSeeder` runs only behind [`EvalAccess`](/rollingrecord/evals/on-device/access) (dev + `+clerk_test` account). Every seeded row and audio file carries the `ID_PREFIX = "eval-seed-"` id, and teardown deletes **exactly** those ids — junctions first, then transcripts (firing the FTS DELETE trigger), then recordings and their audio files. Because teardown can only ever match the prefixed seed ids, a run can never delete a real recording or context. Seeded audio lives under a dedicated `eval_seed_audio` subdirectory of `filesDir`.
