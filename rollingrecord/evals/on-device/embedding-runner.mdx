`EmbeddingEvalRunner` (`devmode/eval/EmbeddingEvalRunner.kt`, RR-487) is a distinct debug harness for tuning the semantic-search cosine thresholds. It is **not** part of `evalmode` — it lives under `devmode/eval/`, grades retrieval quality rather than AI answers, and produces threshold sweep reports, not per-case verdicts.

## What it tunes

As of RR-487 embeddings are produced server-side (Cohere via the `search` and `indexing` Edge Functions). This runner embeds against that same server path the app uses, so a swept threshold transfers directly to production. It replicates both production retrieval pipelines:

| Pipeline | Corpus | Embedding | Graded against |
| --- | --- | --- | --- |
| Topic search | Recordings | Each transcript split with the real `TranscriptChunker.splitIntoChunks`; a recording's score is `max(chunk cosine)`. | `ClientConfig.topicSearchThreshold` |
| Section search | Context cards | Each section text embedded whole. | `ClientConfig.sectionSemanticThreshold` |

Cohere's asymmetric input types (`search_query` vs `search_document`, applied server-side) replace the retired on-device model's text prefixes. The runner requires connectivity and a semantic-search-eligible account (Pro+Cloud and up); it fails cleanly with a summary if the server embed is unavailable rather than throwing.

## The labeled eval set

The corpus is a fabricated, labeled asset at `assets/eval/eval_set.json` (debug source set only — never ships in release; note the singular `eval/`, distinct from `evalmode`'s `evals/`). No real user data is read, and nothing is written except result files in `cacheDir` (dev Rule 6 compliant). The schema:

- `EvalDocument` — `{ id, kind ("recording" | "section"), title, text }`.
- `EvalQuery` — `{ id, text, target, relevant[], bucket, note? }`, where `bucket` is `exact` / `paraphrase` / `multi` / `adjacent` / `negative`.
- `EvalSet` — `{ version, description, documents[], queries[] }`.

## Metrics

For each target, `buildTargetReport` computes a threshold sweep and ranking metrics. The sweep runs `0.10 → 0.60` in `0.01` steps (the zone where Cohere embed-v4.0 signal actually sits — relevant pairs ~0.24–0.50, irrelevant ~0.13–0.49), computing precision, recall, F1, and false positive/negative counts at each point:

| Metric | Meaning |
| --- | --- |
| `atLive` | Precision/recall/F1 at the live production threshold. |
| `bestF1` | The sweep point with the highest F1. |
| `recallAt1` / `recallAt3` | Fraction of queries whose first relevant doc ranks 1 / within top 3. |
| `mrr` | Mean reciprocal rank of the first relevant doc. |
| Separation stats | Relevant vs. irrelevant score mean/min/max — how cleanly the threshold splits them. |

## Output

`execute(onProgress)` embeds documents (`indexing` EF, batches of ≤96), scores every `(query, same-kind doc)` pair, computes the two `TargetReport`s, and writes to `cacheDir/embedding_eval/`: a `scores_<ts>.csv` of every scored pair and a `report_<ts>.txt` with the full sweep table (LIVE and BEST F1 rows marked) plus per-query top-3 detail. It returns an `EvalResult` with a human-readable `summary` and the two file paths, both ADB-pullable via `run-as`.
