The eval harness grades the AI behavior of RollingRecord's `ai-engine` operations — above all the KB-chat agent loop (`kb_query`) — by running a fixed set of golden cases against the live dev backend and scoring each response with a judge chain.

## What the harness evaluates

The system-under-test is the production `ai-engine` Edge Function, driven with real cases. A case is a golden example (`TestCase` in `evals/core/case.py`): a payload handed to the operation and an `expected` specification the judges grade against. Cases are grouped into suites under `evals/suites/` — `kb_chat`, `kb_chat_session`, `rag_real_content`, `template_moderation`, `extract_template`, `tool_correctness`, `security`, `abstention`, `efficiency`, `source_attribution`, and more. See the [suites catalog](/rollingrecord/evals/authoring/suites-catalog) for the full list.

The model under test and the models that judge it are hardcoded constants in `evals/config.py`, not env vars — bumping one is a reviewed code change:

| Constant | Value | Role |
| --- | --- | --- |
| `PRODUCTION_MODEL` | `claude-haiku-4-5-20251001` | The model the suite tests — mirrors what the app uses for `ai-engine`. |
| `JUDGE_MODEL` | `claude-sonnet-4-6` | Default LLM-as-judge model (used by `LlmJudge`). |
| `ARBITER_MODEL` | `claude-opus-4-6` | Tiebreaker/arbiter for ambiguous verdicts and bootstrapping golden data. |

The design rule is that the judge model must be meaningfully smarter than the model it grades.

## The pipeline in one line

`run.py` resolves which cases to run, hands each to a `SystemUnderTest`, captures the response, runs the suite's judge chain to produce a `Verdict`, tallies the run, and writes a results JSON plus an analytics row. See [Architecture & Data Flow](/rollingrecord/evals/architecture) for the full path.

## The runtime and its parity dimension

The harness has a single runtime — the Python harness (`evals/`): the CLI in `run.py`, the orchestrator `Runner` (`evals/core/runner.py`), and the default `AiEngineHttp` system-under-test. This is the pre-release safety net run from a developer machine or CI. (A debug-only on-device Kotlin port — the `evalmode` module — once ran the same suites inside the app against a seeded local corpus; it was deleted because it shipped a baked-in Anthropic key, and the Python harness is now the only eval runtime.)

Within the Python harness there is a parity dimension. The `--sut` flag chooses how SESSION (multi-round) cases are driven:

- `--sut=python` (default) uses the in-harness `SessionRunner` (`evals/core/session.py`), an imitation of the client agent loop.
- `--sut=kotlin` shells out to the `app/agentrunner` CLI, which drives the **literal** production agent loop in `app/agentcore` (`AgentLoop`) — same tool definitions, instructions, message assembly, and caps as the shipping app. See the [Kotlin SUT contract](/rollingrecord/evals/kotlin-sut/contract).

Single-shot (non-session) cases always use the Python HTTP client regardless of `--sut`.
