Credits are bonus resource beyond a user's monthly cap. They live in `user_credits` — at most two rows per user — with every grant, refund, and consumption event also written to the unified `l_credit_log` ledger. All of this is implemented in `_shared/db/user-credits.ts` and `_shared/db/credit-ceiling.ts`.

## The balance model

`user_credits` (defined in `migrations/20260508000000_baseline.sql`, renamed from `manual_credits`) is keyed on `(auth_user_id, credit_type)` where `credit_type` ∈ `{manual, bundle}` — so a user has at most one `manual` row and one `bundle` row. Each row carries three per-resource balances: `transcription_ms_balance` and `extraction_ms_balance` (both **BIGINT** since the widen migration) plus `ai_queries_balance` (int4). CHECK constraints keep every balance `>= 0`, and the table has **no FK** to `canonical_users`.

`ResourceType` is `'transcription_ms' | 'ai_queries' | 'extraction_ms'`; `RESOURCE_COLUMNS` maps each to its balance column. Reads come through `getCreditRowBalances` (one row), `getCreditBalance` (one resource), and `getAllCreditBalances` (both rows plus a per-resource `total` — `manual + bundle`, the figure `get-user-usage` shows). Missing rows read as zeros.

| Credit type | Written by | Helper |
| --- | --- | --- |
| `manual` | support-ops admin grants | `adjustManualCreditBalance` (hardcoded to the manual row) |
| `bundle` | RC `NON_RENEWING_PURCHASE` webhook branch — the only caller | `creditBundle` (keyed on `purchase_token`) |

`adjustManualCreditBalance` is hardcoded to `credit_type = 'manual'` and never touches the bundle row — the "support staff edit manual, not bundle" integrity boundary is enforced at the data layer. It clamps at zero (`clampedToZero`), writes an `l_credit_log` audit row with `source = 'support_op_manual'` and `consumed_by = 'admin:<id>'`, and returns an `AdjustResult` of `{previousBalance, newBalance, appliedDelta, clampedToZero}`.

## The unified ledger

`l_credit_log` is the append-only ledger for every credit event: manual grants/revokes, bundle grants, consumption, and refunds. Columns include `auth_user_id`, `id` (uuid PK), `resource_type` (nullable), `amount` (legacy per-resource, nullable), `consumed_by`, `reason`, `created_at`, `credit_type`, `source`, `purchase_token`, `sku`, the three delta columns `transcription_ms_delta` / `ai_queries_delta` / `extraction_ms_delta`, and `refund_of_token`. It too has **no FK** to `canonical_users`.

| CHECK / index | Constraint |
| --- | --- |
| `credit_type` CHECK | ∈ `{manual, bundle}` |
| `source` CHECK | ∈ `{rc_webhook, support_op_recovery, support_op_manual, consumption, rc_refund}` |
| partial UNIQUE on `purchase_token` (WHERE NOT NULL) | authoritative duplicate-purchase guard |
| partial UNIQUE on `refund_of_token` (WHERE `source = 'rc_refund'`) | double-clawback guard |

The reconciliation invariant is `SUM(deltas) GROUP BY (auth_user_id, credit_type)` equals the live `user_credits` balances within the retention window. `l_credit_log` was renamed from `l_credit_consumption` when it absorbed grants and refunds.

## Bundle grants and refunds

`creditBundle` has exactly one caller: `handleNonSubscriptionPurchase` in `functions/revenuecat-webhook/index.ts`, which passes `source: 'rc_webhook'`. Step 1 INSERTs the `l_credit_log` row keyed on `purchase_token`; a `23505` unique violation means that token was already credited (RevenueCat retries the same event id), so it returns `outcome: 'already_credited'` as a no-op. Step 2 UPSERTs the bundle row's balances. Tier-aware grant amounts are the caller's responsibility — the webhook reads the buyer's tier at webhook time and passes the deltas.

<Note>
`creditBundle`'s `source` parameter is typed `'rc_webhook' | 'support_op_recovery'`, and the doc comment describes it as "shared by the RC webhook and the support-op recovery path." **That second path does not exist.** No operation in `support-ops/operations/` calls `creditBundle` — the only support-ops credit writer is `grant-manual-credit.ts`, hardcoded to the `manual` row. `support_op_recovery` is a valid `l_credit_log.source` value the CHECK constraint accepts (and that `refundBundle` and the ledger-reader ops match on), but nothing writes it today, so `rc_webhook` is the only bundle-grant source in practice.
</Note>

That tier read is `fetchEffectiveEntitlements(authUserId, { bypassCache: true })` (`_shared/gates/entitlement.ts`) compared against `TIER.PRO_CLOUD_AI` — the **same** authority the gate chain reads, not the raw RC key set. A plain `getActiveEntitlementKeys(...).has("pro_cloud_ai")` silently answered false for everyone entitled by something other than that exact key — a `developer` account, or a `lifetime_pro_cloud_ai` holder. They were charged the full bundle price and credited transcription minutes only. `bypassCache` is set because a bundle purchase is a one-shot money event: the entitlement set is cached for five minutes, and a stale empty set here under-credits a real purchase with nothing to retry it.

| Buyer's effective tier | `transcriptionMsDelta` | `aiQueriesDelta` | `extractionMsDelta` |
| --- | --- | --- | --- |
| `pro_cloud_ai` in the effective set (incl. `developer`, `lifetime_pro_cloud_ai`) | `minutes_granted * 60_000` | `queries_granted` | `extraction_minutes_granted * 60_000` |
| Below Cloud+AI (Free / Pro / Pro+Cloud) | `minutes_granted * 60_000` | `0` | `0` |
| Tier lookup unavailable — the gate returned a `Response` (RC down), or the call threw | `minutes_granted * 60_000` | `0` | `0` |

The degraded row is an explicit branch, not a catch-all: the handler logs `tier lookup unavailable` / `tier lookup threw` and still credits the headline transcription grant, so the buyer keeps the value they paid for and the shortfall is left to a support top-up rather than failing the whole credit.

`refundBundle` is likewise called only from the webhook — `handleBundleRefund`, with `source: 'rc_refund'`. It looks up the grant by `purchase_token` (restricted to grant sources, `.in("source", ["rc_webhook", "support_op_recovery"])`), computes per-resource clawback **clamped at the current balance** (the user keeps whatever they consumed before the refund), INSERTs a negative-delta row keyed on `refund_of_token`, and decrements the bundle row. Its `outcome` is `refunded`, `already_refunded`, or `no_grant_found`.

<Warning>
`refundBundle`'s `source` parameter is typed `'rc_refund' | 'support_op_refund'`, but `support_op_refund` is **not insertable**. `l_credit_log_source_check` allows only `{rc_webhook, support_op_recovery, support_op_manual, consumption, rc_refund}` — the list above — so an INSERT carrying it would be rejected by the CHECK constraint. The double-clawback guard would not cover it either: `idx_l_credit_log_unique_refund_of_token` is scoped `WHERE source = 'rc_refund'`. The TypeScript union is ahead of the schema; only `rc_refund` works.
</Warning>

## `bundle_config` and SKU normalization

Bundle SKU definitions live in `bundle_config` (`migrations/20260508000000_baseline.sql`): `sku` PK, `display_name`, `minutes_granted`, `queries_granted`, `extraction_minutes_granted` (renamed from `extractions_granted`), `price_usd` `numeric(10,2)` reference-only — Google Play is the authoritative price — plus the `active` soft-disable flag, `description`, and `updated_at`. It has **two** readers today: the RC webhook (which decides the grant) and the [`get-bundle-catalog`](/rollingrecord/backend/edge-functions/get-bundle-catalog) Edge Function (which advertises it, applying the identical Cloud+AI zeroing rule so the two can't disagree).

The lookup key is **not** the raw store product id. `normalizeBundleSku(productId)` (`_shared/billing/bundle-sku.ts`) splits at the first `:` and keeps the prefix, and the webhook applies it to `event.product_id` before the `bundle_config` lookup. Stores qualify a product id with a sub-identifier when one exists — Google appends the base plan for subscriptions, and the purchase option for the newer one-time product model, as `product_id:sub_id` — and RevenueCat forwards whatever the store gave it. Normalizing is a no-op on an already-bare id, so it is applied unconditionally: a lookup miss in the purchase handler means a buyer was charged and credited nothing, and the only trace is one "unknown SKU" line in the function log.

| Input `product_id` | Normalized SKU | Why |
| --- | --- | --- |
| `bundle_transcription_1hr` | `bundle_transcription_1hr` | bare id passes through unchanged |
| `bundle_transcription_1hr:base` | `bundle_transcription_1hr` | Google's one-time product model, `product_id:purchase_option_id` |
| `bundle_transcription_3hr:monthly` | `bundle_transcription_3hr` | same shape subscriptions use for the base plan |
| `sku:a:b` | `sku` | only the first segment is kept |
| `""` / `:base` | `""` | degenerate input does not throw — the empty SKU simply misses the lookup and is logged, better than throwing inside a webhook RC would then retry forever |

All five rows are pinned by `supabase/tests/_shared/billing/bundle-sku_test.ts`. The client applies the identical rule when joining RevenueCat packages against the catalog (`product.id.substringBefore(':')`), so both sides agree on what a product id means. The `sku` stored on the `l_credit_log` row is the **normalized** value, so refunds (which look the grant up by `purchase_token`) and the ledger-reader support ops both see a consistent id.

## Drain order

Consumption drains **bundle first, then manual**, so paid credit is spent before support gratuities. `chargeOverage` is the per-op entry point after a successful metered call: it computes the overage crossing `baseCap`, floors it to whole credits, and calls `drainCredits`.

| Step | Row | Behavior |
| --- | --- | --- |
| 1 | `bundle` | drain first, clamp at 0 |
| 2 | `manual` | drain the remainder, clamp at 0 |
| ledger | `l_credit_log` | one `consumption` row (negative delta, `consumed_by = 'system'`) per row touched, via `writeConsumptionLog` |

Draining is best-effort — the user already got their operation, so a failed balance write is logged, not thrown.

## The credit ceiling

Admin manual-credit grants to the two time-denominated resources are bounded by a per-account ceiling in `_shared/db/credit-ceiling.ts`. `getCreditCeilingMs()` reads `server_config.max_credit_balance_minutes` (fallback `CREDIT_CEILING_MINUTES_DEFAULT` = 60000 minutes = 1000 hours) and multiplies by 60000 to get milliseconds. `CEILINGED_RESOURCES` is `[transcription_ms, extraction_ms]` — `ai_queries` is a small count and is **not** ceilinged. `wouldExceedCreditCeiling(current, delta, ceiling)` is pure; only positive deltas can exceed.

The ceiling is **all-or-nothing**: a manual grant that would push the resource total (manual + bundle) past the limit is rejected outright rather than partially applied, so no paid time is silently lost — an admin cannot top a user already at 998h up past the 1000h limit. Enforcement lives ONLY on the admin manual-grant path — the ceiling helpers are called from `grant-manual-credit.ts` and nowhere else. `creditBundle()` and the webhook's `handleNonSubscriptionPurchase()` never call them, so a bundle **purchase** is not ceiling-checked and can legitimately push the balance past the limit. When a grant would exceed the ceiling, `grant-manual-credit.ts` throws an `OperationError` carrying `AppError.CREDIT_CEILING_EXCEEDED.code` / `.httpStatus` plus the structured fields `{resource, limit_ms, current_balance_ms, projected_ms}`; the support-ops dispatcher returns that thrown `OperationError` as the `credit_ceiling_exceeded` (409) response body. (`credit-ceiling.ts` also defines a `CreditCeilingExceededError` class with matching fields and a `credit_ceiling_exceeded:`-prefixed message, but it is not on the runtime throw path — enforcement raises `OperationError` directly.) It is **not** dev-bypassable — an integrity limit, not a quota.

This per-account **holdable** ceiling is distinct from the per-**operator** grant budget (`admin_grant_budget_exceeded`, 403, `_shared/db/admin-credit-budget.ts`) covered under [Admin grant validation](#admin-grant-validation): `credit_ceiling_exceeded` bounds how much the *customer* may hold, the grant budget bounds how much an *operator* may give away over a rolling 30 days. Both are enforced ONLY on the admin manual-grant path (`grant-manual-credit.ts`); `creditBundle()` / webhook purchases are checked by neither.

## Admin grant validation

The support-ops `grant_manual_credit` op (`support-ops/operations/grant-manual-credit.ts`) validates its `amount` input paranoidly before any DB access. `MAX_ADJUSTMENT_BY_TYPE` bounds a single grant: `transcription_ms` and `extraction_ms` at 360,000,000 ms (100 hours), `ai_queries` at 10,000.

| Code | HTTP | Meaning |
| --- | --- | --- |
| `amount_not_integer` | 400 | `amount` is not a JSON integer (rejects numeric strings, floats, booleans, null) |
| `amount_not_finite` | 400 | `amount` is NaN or ±Infinity (defense-in-depth) |
| `amount_out_of_range` | 400 | `abs(amount)` exceeds the per-type single-grant cap |
| `amount_zero` | 400 | `amount: 0` rejected as a no-op |
| `invalid_credit_type` | 400 | resource key not in `{transcription_ms, ai_queries, extraction_ms}` |
| `credit_ceiling_exceeded` | 409 | grant would push a ceilinged resource total past the max holdable balance |
| `admin_grant_budget_exceeded` | 403 | positive grant would push THIS OPERATOR's rolling-30-day granted total for the resource past their per-operator ceiling (`admin_permissions.max_monthly_*`) |

Beyond bounding a single grant, `grant_manual_credit` enforces a **per-operator budget** before applying any positive delta (new file `_shared/db/admin-credit-budget.ts`, kept clearly distinct from the per-account holdable ceiling above). It reads the operator's ceilings from `admin_permissions` — `max_monthly_transcription_ms` and `max_monthly_extraction_ms` (both in **milliseconds**, matching the `extraction_ms` resource and the `*_delta` columns, **not** a count) plus `max_monthly_ai_queries` (a count); `0` = unlimited. It reads the operator's already-granted spend over a trailing window (`GRANT_BUDGET_WINDOW_DAYS` = 30) via the `admin_credit_granted_since` RPC, which sums only positive deltas (`GREATEST(delta, 0)`) from `l_credit_log` so revokes never restore headroom. The pure `evaluateGrantBudget(...)` returns a `BudgetDecision` with `reason` ∈ `{super_admin, unlimited, within_ceiling, not_a_grant, would_exceed}`. Three bypasses skip the check: a super admin, a ceiling of `0` (the unlimited default — adding the feature changes no existing operator's authority), and revokes (a negative amount, short-circuited as `not_a_grant`). Landing **exactly on** the ceiling is allowed — refusal is strict `>`. A read-only companion op, `get_my_grant_budget` (`support-ops/operations/get-my-grant-budget.ts`), reports an operator's ceilings, spend, and remaining headroom via the **same** `admin_credit_granted_since` RPC, so enforcement and reporting can never disagree.

The `credit_type` wire field actually names the RESOURCE being adjusted (a CLI back-compat holdover), not the manual/bundle discriminator that `credit_type` means inside `user_credits`.

## Deletion coverage

Neither `user_credits` nor `l_credit_log` has an FK to `canonical_users`, so CASCADE never reaches them. Both are listed in `TABLES_TO_WIPE` in `_shared/users/wipe.ts` and hard-deleted explicitly for GDPR right-to-erasure. The unit note worth carrying: the time-resource balance and delta columns are in **milliseconds** and were widened int4 → BIGINT in `migrations/20260729120000_widen_credit_ms_columns_to_bigint.sql`, because the 1000-hour ceiling (3.6e9 ms) overflows int4 (~596h). The extraction resource key was renamed `extractions` → `extraction_minutes` → `extraction_ms` across two migrations.
