title: "RevenueCat Integration"

---

RevenueCat is the authoritative source for entitlement **state**, read live per request; the database only mirrors lifetimes and dev grants as an audit ledger. Two pieces make up the integration: an RC v2 API client in `_shared/billing/revenuecat.ts` and the inbound `revenuecat-webhook` Edge Function that reacts to grant, revoke, purchase, and refund events.

## The RC v2 client

`_shared/billing/revenuecat.ts` does a two-step lookup. `fetchEntitlementCatalog()` builds a module-cached `entitlement_id → lookup_key` map (`catalogCache`, rebuilt on cold start), and `getActiveEntitlementKeys(authUserId)` fetches the customer's active entitlements, translates them through the catalog, and drops any whose `expires_at` is in the past. Per-customer results are cached for `ENTITLEMENT_CACHE_TTL_MS` (5 minutes) in `customerEntitlementCache`; a 404 (no such customer) caches an empty set, but failures are **not** cached so the next request can retry cleanly. `getEffectiveEntitlementKeys()` wraps this and applies the tier cascade (see [Entitlement taxonomy](/rollingrecord/backend/billing/entitlements)).

Both `getActiveEntitlementKeys` and `getEffectiveEntitlementKeys` take an optional `EntitlementFetchOptions` (`{ bypassCache }`). `runGates` sets `bypassCache` from the client header `X-Entitlement-Refresh: 1`, which the app sends right after a just-completed purchase or restore when its local RC state disagrees with what the server last reported. A pure `decideCacheUse(ageMs, bypassRequested)` then picks one of four `CacheDecision` states — `serve`, `expired`, `bypass`, or `bypass_throttled`. The bypass is throttled by a floor on **cache-entry age**, `ENTITLEMENT_BYPASS_MIN_AGE_MS` (20s): the first honored bypass refreshes the entry to age 0, so follow-ups fall back to serving cache, capping any one account at ~3 RC calls/minute. It is safe to expose to any authenticated caller because it only selects *where* the answer is read from, never *what* it is — RC stays the sole authority, so a forged request just earns a fresh, honest "no". `decideCacheUse` is unit-pinned by `supabase/tests/_shared/billing/revenuecat_test.ts`: the 20s floor is inclusive (`19999ms` → `bypass_throttled`, `20000ms` → `bypass`), and a throttled bypass must degrade to serving cache, never deny.

Every GET goes through `fetchRcWithRetry(url, apiKey)`:

| Constant | Value | Role |
| --- | --- | --- |
| `RC_API_BASE` | `https://api.revenuecat.com/v2` | RC v2 base URL |
| `RC_RETRY_ATTEMPTS` | 3 | 1 initial + 2 retries |
| `RC_RETRY_BACKOFFS_MS` | `[200, 500]` | backoff between attempts |
| `ENTITLEMENT_CACHE_TTL_MS` | 300000 | per-customer active-entitlement cache |

It retries network throws, HTTP 5xx, and 429; treats 2xx **and** 404 as terminal-success (the caller distinguishes 404 = "no customer, empty set" from an outage); returns other 4xx immediately; and throws after exhaustion so callers surface a 502. Two more client functions round it out: `deleteRcCustomer(authUserId)` (RC **v2** DELETE against `RC_API_BASE` = `https://api.revenuecat.com/v2` for GDPR erasure — 404 is a no-op, invalidates the customer cache, and fires CANCELLATION/EXPIRATION webhooks that revoke lifetime rows, but does **not** cancel the underlying store subscription), and `getCustomerAttributes(authUserId)` (reads the `grant_reason` customer attribute that classifies a lifetime grant's `source`).

## Webhook authentication

There is **no Svix and no HMAC signature verification.** The `revenuecat-webhook` Edge Function authenticates with a single shared-secret Bearer token, configured in both the RC dashboard and the Edge Function environment. `_shared/gates/webhook-secret.ts` compares `Authorization: Bearer <REVENUECAT_WEBHOOK_SECRET>` against the env var using `timingSafeEqual` (a constant-time compare that iterates the full length to prevent a timing oracle); a mismatch returns `invalid_signature` (401). `verifyWebhookSecret()` is the exported primitive; `runWebhookSecretGate()` is the gate wrapper that builds the 401.

The gate config in `revenuecat-webhook/index.ts` is minimal — `method: HttpMethod.Post`, `auth: AuthMode.WebhookSecret`, and two greppable opt-outs, each with an `// OPT-OUT:` comment because RC's server-to-server infrastructure sends neither header:

| Gate flag | Reason |
| --- | --- |
| `skipAppCheck: true` | RC never sends an `X-Firebase-AppCheck` token |
| `skipAppVersion: true` | RC never sends an `X-App-Version` header |

After the gate, the handler parses the envelope (`INVALID_BODY` on bad JSON, `MISSING_EVENT_FIELDS` when `event.type` / `app_user_id` are absent), dispatches, and **always** 2xx's RC on a handled outcome. It only returns `INTERNAL_ERROR` (500) on an unexpected throw so RC retries transient DB/RC failures.

## Event routing

`dispatchEvent()` fans each event out through a fixed pipeline: `extractEntitlementKeys` (flattens `entitlement_id` + `entitlement_ids[]` to a deduped list) → `filterMirroredKeys` (keeps only `WEBHOOK_MIRRORED_LOOKUP_KEYS`) → `logEntitlementEvents` → `handleRecurringSubEvent` → `handleRecurringSubRevenue` → the bundle branches → the lifetime grant/revoke switch.

| RC event type | Action |
| --- | --- |
| `INITIAL_PURCHASE` / `NON_RENEWING_PURCHASE` / `TEMPORARY_ENTITLEMENT_GRANT` (mirrored key) | `handleLifetimeGrant` → UPSERT `lifetime_entitlements` |
| `INITIAL_PURCHASE` / `RENEWAL` (recurring sub key, fresh) | `handleRecurringSubRevenue` → `revenue_micros += usdToMicros(price)` |
| Any recurring-sub event (`EXPIRATION` / `RENEWAL` / `PRODUCT_CHANGE` / `UNCANCELLATION` / `CANCELLATION` / dashboard revoke) | `handleRecurringSubEvent` re-reads the authoritative set live from RC and diffs it against the stored `last_known_entitlements` key snapshot; opens/clears the cloud grace window on the transition |
| `CANCELLATION` (mirrored lifetime key) | `handleLifetimeRevocation` with lowercased `cancel_reason` |
| `EXPIRATION` (mirrored lifetime key) | `handleLifetimeRevocation` fallback, reason `rc_expiration` |
| `NON_SUBSCRIPTION_PURCHASE` | `handleNonSubscriptionPurchase` → `creditBundle` + `revenue_micros` |
| `CANCELLATION` (product_id, no mirrored key) | `handleBundleRefund` → `refundBundle` clawback |
| `SUBSCRIBER_ALIAS` / `TRANSFER` / `BILLING_ISSUE` / `SUBSCRIPTION_PAUSED` | `l_entitlement_events` audit only |

## Lifetime mirroring

Only `WEBHOOK_MIRRORED_LOOKUP_KEYS` (lifetimes plus `developer`) reach the lifetime handlers. `handleLifetimeGrant` resolves `source` via `attributeSource`, looks up `email_hash` via `lookupEmailHash`, checks for an existing active row, and INSERTs — the existence check plus the unique index tolerate webhook-retry races. `handleLifetimeRevocation` is idempotent: it UPDATEs `revoked_at` + `revoked_reason` on the active row, and when a `CANCELLATION` arrives shortly after an `EXPIRATION` (within a 60-second window) it upgrades a generic `rc_expiration` reason to the more specific `cancel_reason`.

`attributeSource` decides what `lifetime_entitlements.source` records:

| Condition | `source` |
| --- | --- |
| entitlement key = `developer` | `developer` |
| `grant_reason` attribute = `manual_admin` | `manual_admin` |
| `grant_reason` attribute = `employee_perk` | `employee_perk` |
| `PROMOTIONAL` store, no `grant_reason` | `manual_admin` (logged anomaly) |
| real purchase of `founders_edition`, no `grant_reason` | `founders_edition_purchase` |

## Recurring-sub grace and revenue

Recurring subs are **not** mirrored into `lifetime_entitlements` — Gate 2 reads them live from RC — but the webhook is not log-only for them. `handleRecurringSubEvent` maintains the cloud grace window on `canonical_users`, keyed off a `last_known_entitlements` snapshot (an array of raw RC **keys**) and its `last_known_entitlements_at` timestamp. It is **not** a switch over event types: the webhook is now a **trigger** and RC is the **source**. On any recurring-sub event the handler re-reads the authoritative set via `getActiveEntitlementKeys(authUserId, { bypassCache: true })` and diffs it against the stored snapshot:

| Transition | Action |
| --- | --- |
| had cloud, now no cloud | open the window — set `cloud_grace_started_at = NOW()`, `cloud_grace_tier = pickHighestRecurringCloudTier(previous)`, guarded on the window not already being open so a redelivered webhook can't push the deadline out |
| holds cloud now | clear both `cloud_grace_started_at` + `cloud_grace_tier` (active / resubscribed / upgraded) |
| neither | snapshot only |

Every route out of cloud collapses into the open-window case: expiry, a deferred plan switch landing at `RENEWAL`, a refund, a chargeback, a dashboard revoke, and specifically the Pro+Cloud → Pro Google Play downgrade. `pickHighestRecurringCloudTier` prefers `pro_cloud_ai` over `pro_cloud`.

**Why state comparison, not event type.** A webhook's `entitlement_ids` are the entitlements *of that product*, not the customer's full set, so the absence of a cloud key proves nothing. And Google Play downgrades are **deferred**: `PRODUCT_CHANGE` fires immediately but is informational, the entitlements are replaced later at `RENEWAL`, and **no `EXPIRATION` is emitted** for the old cloud key — so the old `EXPIRATION`-keyed model missed every plan-switch downgrade entirely. `CANCELLATION` now needs no special-casing either: RC fires it the moment auto-renew is turned off, but the live fetch still shows cloud, so it lands in "holds cloud" and the clock doesn't start until the entitlement actually goes. On a failed RC fetch the handler **bails and leaves grace state untouched**, erring toward not starting a deletion countdown for a paid customer.

**Developer and lifetime grants get no grace window.** `RECURRING_CLOUD_KEYS` (`{pro_cloud, pro_cloud_ai}`) is the allowlist behind `pickHighestRecurringCloudTier`, so a `developer` or `lifetime_*` key never registers as "had cloud" and its removal is never a cloud transition — a revoked internal grant is a hard cutoff with no 30-day grace, and `pro` (non-cloud) gets none for the same reason. This is exactly why `last_known_entitlements` stores **keys, not a resolved tier**: `developer` and `pro_cloud_ai` resolve to the same tier but must behave differently, and a tier snapshot would read a dev revoke as `pro_cloud_ai` → free and wrongly start deleting a colleague's data. The paired CHECK constraints back this up — `canonical_users_cloud_grace_tier_values` pins the column to `pro_cloud` / `pro_cloud_ai`, and `canonical_users_cloud_grace_paired` requires both columns NULL or both non-NULL.

`handleRecurringSubRevenue` writes real revenue on a **fresh** `INITIAL_PURCHASE` / `RENEWAL` carrying a `RECURRING_SUB_KEYS` (`{pro, pro_cloud, pro_cloud_ai}`) member: `usdToMicros(event.price)` → `incrementFinancialColumn(user, 'revenue_micros', …)`. Pro is included even though it has no cloud cost, producing a correct 100%-margin row. `event.price` is documented by RC as **always USD** (developer net-of-store-fees) regardless of the customer's purchase currency; `event.currency` pairs with a separate field and is logging-only. Freshness comes from `logEntitlementEvents`, which upserts one `l_entitlement_events` row per entitlement (sentinel `(none)` for alias/transfer events) with `onConflict: 'event_id,entitlement_id'` and `ignoreDuplicates` — `isFreshEvent` is `true` only when rows actually inserted, so an RC retry never double-counts revenue. A failed log write is swallowed and returns `isFreshEvent = false`, erring toward missing revenue over double-counting.

## Bundle purchases and refunds

`handleNonSubscriptionPurchase` handles one-time IAP bundles. It reads `bundle_config` by `product_id` (an `active = false` SKU is refused), computes tier-aware grants (Cloud+AI gets minutes + queries + extraction ms; other tiers get minutes only), and calls `creditBundle()` keyed on `event.id` as the `purchase_token` — idempotent via the `l_credit_log` unique index. On `outcome === 'credited'` with a positive `event.price`, it records `revenue_micros`. `handleBundleRefund` runs when a `CANCELLATION` carries a `product_id` but no mirrored entitlement key: it hands `event.id` to `refundBundle({purchaseToken, source: 'rc_refund'})`, which is idempotent via a `refund_of_token` unique index and always 2xx's on `no_grant_found` / `already_refunded`. Both bundle helpers live in `_shared/db/user-credits.ts` — see [Credits & bundles](/rollingrecord/backend/billing/credits-and-bundles).

## The `RevenueCatEvent` shape

The webhook reads a small envelope. Key fields on `RevenueCatEvent`: `type`, `app_user_id` (the Supabase Auth / Clerk UUID set via `Purchases.logIn(authUserId)`), `entitlement_id` / `entitlement_ids`, `product_id`, `store` (`PROMOTIONAL` / `PLAY_STORE` / `APP_STORE`), `cancel_reason`, `price` (always USD, developer net-of-fees), `currency` (logging only), `id` (transaction / dedup key), `purchased_at_ms`, `expiration_at_ms`, and `environment`.
