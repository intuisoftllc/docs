Built-in extraction blueprints are server-owned prompts shipped inside `ai-engine`, addressed by stable numeric IDs. `BUILTIN_BLUEPRINTS` (`functions/ai-engine/blueprints/builtin/index.ts`) is the single source of truth — an array of `BuiltInBlueprint` ordered by ID, with each blueprint's prompt living in its own file for isolated editing.

## The registry

`BUILTIN_BLUEPRINTS` holds **eleven** active blueprints occupying IDs 1 and 3–12. `BUILTIN_BLUEPRINT_MAP` is a `Map<number, BuiltInBlueprint>` built from it for fast lookup, and `getDefaultBlueprint()` returns the `isDefault` blueprint (ID 1, General Notes).

Each entry is a `BuiltInBlueprint`:

| field | type | meaning |
| --- | --- | --- |
| `id` | number | stable numeric ID — append-only, never reused |
| `name` | string | display name |
| `description` | string | picker-card subtitle |
| `isDefault` | boolean | the default blueprint for new contexts |
| `isMultiSpeaker` | boolean | designed for multi-speaker recordings |
| `status` | `"active"` \| `"deprecated"` | deprecated blueprints still serve but aren't offered to new clients |
| `systemPrompt` | string | full prompt with `TOOL_INSTRUCTIONS` already appended |

`withToolInstructions` appends `TOOL_INSTRUCTIONS` (= `TOOL_SPEC_ONLY` + `CONTENT_BOUNDARY`, imported from `prompts/extract.ts`) to each blueprint's role/instruction body, so the blueprint files don't import prompt infrastructure themselves. Each of the eleven prompts lives in its own file (`general-notes.ts`, `sales-call.ts`, `developer.ts`, `one-on-one.ts`, `voice-memo.ts`, `sprint-standup.ts`, `brainstorming.ts`, `coaching.ts`, `lecture-notes.ts`, `medical-appointment.ts`, `interview.ts`).

## Append-only IDs

IDs are append-only: once a blueprint ships to production, its ID is permanently burned. Prompt revisions to the same blueprint keep the same ID (that is the whole point of server-owned prompts — old clients that send the ID get the updated behavior on their next extraction). A semantic replacement gets a new ID, and the old ID is marked deprecated rather than reused. The only retirement mechanism present in code today is the `status` field; no blueprint is currently `deprecated`, and there is no runtime `410 template_retired` path in this registry (that is CLAUDE.md policy, enforced elsewhere if needed).

The registry header notes the codebase is still **pre-launch**: IDs may be renumbered freely until RR-46 Phase 7b ships clients against the production `ai-engine`, at which point the append-only rule takes effect unconditionally.

## Pre-launch ID history

ID 2 was retired pre-launch (its blueprint was consolidated into General Notes), so it has no registry entry — that is why the IDs run 1 and 3–12 for eleven blueprints. Several IDs were swapped from an earlier blueprint before any client shipped against them; reusing those IDs was permitted only because no client was running against the old blueprints at swap time.
