---
title: "Operation Registry"
description: "How ai-engine operations are registered, validated, and dispatched through one typed-handler registry behind the runGates admission chain."
---

`ai-engine` is a single `POST` Edge Function (`functions/ai-engine/index.ts`). One `Deno.serve` handler runs the outer admission chain, looks the request body's `operation` string up in a static registry, and dispatches to a typed handler. There is no legacy `switch` — as of RR-46 Phase 6b every operation is an `OperationHandler`.

## Request lifecycle

`Deno.serve` calls `runGates(req, { method: HttpMethod.Post, auth: AuthMode.Jwt })` first. Note it passes **no** `rateLimit` chain-sugar: the rate limit runs later, inside `dispatchOperation`, so the `x-developer-bypass` / `x-ai-stubbed` response headers survive alongside it. After the gates resolve `authUserId`, `activeEntitlements`, and `isDeveloper`, the handler parses the JSON body, resolves the operation, and hands off to `dispatchOperation`.

| Step | What happens | Failure |
| --- | --- | --- |
| Admission gates | `runGates` — method, App Check, App Version floor, JWT, entitlement fetch | gate's own response |
| Parse body | `await req.json()` | `invalid_body` (400) |
| Read operation | `body.operation` must be a string | `missing_operation` (400) with `valid` |
| Lookup handler | `findHandler(operation)` in `OPERATIONS` | `invalid_operation` (400) with `valid` |
| Dispatch | `dispatchOperation(handler, ...)` | per-op (below) |

`missing_operation`, `invalid_operation`, `invalid_body`, and `handler_threw` are the dispatch-level codes from `AppError` (`functions/_shared/errors.ts`) — all `developer`-category. The two operation-lookup errors echo `OPERATION_NAMES` (every registered key) back to the caller as `valid`.

## The registry

`OPERATIONS` (`functions/ai-engine/operations/index.ts`) is a `Record<string, OperationHandler>` — the single dispatch path. Each handler is instantiated once at module load. `findHandler(op)` returns `OPERATIONS[op] ?? null`; `OPERATION_NAMES` is `Object.keys(OPERATIONS)`.

## The handler contract

`OperationHandler` (`functions/ai-engine/operations/handler.ts`) is a pure data + function bundle. Handlers carry no per-request state.

| Field | Meaning |
| --- | --- |
| `name` | Matches the `operation` string in the request body |
| `requiredEntitlement` | `TierKey` (from `_shared/billing/entitlements.ts`) or `'none'` |
| `capCategory` | `'user_facing'` \| `'runaway_protection'` \| `'handler_owned'` |
| `capKey` | `server_config` key holding the cap (or the multiplier key) |
| `parentCapKey` | Parent cap for `runaway_protection`, else `null` |
| `usageColumn` | `usage`-table column incremented on success |
| `featureFlag` | Optional `server_config` boolean kill-switch, else `null` |
| `validateInput(input)` | Returns an error-code string to reject with `400`, or `null` |
| `execute(ctx)` | Runs the operation, returns a `HandlerResult` |

`HandlerContext` carries `authUserId`, `isDeveloper`, `rawBody`, the opaque `input`, and `requestHeaders` (so handlers can read op-specific headers like `X-Query-Session-Token` without the dispatcher knowing about them).

`HandlerResult` is a discriminated union the dispatcher maps to HTTP:

| status | HTTP | Notes |
| --- | --- | --- |
| `ok` | 200 | `{ payload, responseHeaders? }` |
| `ok_passthrough` | upstream | Handler-built `Response` returned with merged headers |
| `validation_failed` | 400 | `{ error, details? }` |
| `forbidden` | 403 | `{ error }` |
| `not_found` | 404 | `{ error }` |
| `limit_reached` | 429 | `{ error, details? }` |
| `upstream_failed` | 502 (default) | `{ error, httpStatus? }` |
| `input_too_large` | 422 | `{ error }` |

## The cap categories

Cap category decides who enforces the monthly quota:

- **`user_facing`** — the dispatcher reads the cap from `capKey`, compares it to the usage column, rejects with `cap_reached` (429), and increments by 1 on success.
- **`runaway_protection`** — same flow, but a hit returns the `runaway_protection` code instead, and the effective cap is `parent_cap × multiplier` when a `parentCapKey` is set. A hit is a Crashlytics signal, not a user-facing error.
- **`handler_owned`** — the dispatcher skips the cap check **and** the counter increment entirely. The handler does both inside `execute()` because it needs unit conversion (transcribe), non-unit increments (`kb_query` counts only new queries, not continuation rounds), or multi-column budgeting (synthesis).

`computeEffectiveCap` implements the generic path: `getInt(parentCapKey, 0) * getInt(capKey, 4)` when a parent is set, otherwise `getInt(capKey, 100)`. Missing `server_config` rows fall back to those defaults so a deploy-ordering glitch can't take an operation offline.

## dispatchOperation gate order

`dispatchOperation` runs the per-op policy after the outer `runGates` chain. Its order is fixed:

| # | Gate | Reject | Dev-skipped? |
| --- | --- | --- | --- |
| 3 | `handler.validateInput(input)` | `400` with the returned code | no |
| — | Stamp `x-developer-bypass` + `x-ai-stubbed` headers | — | no |
| 4 | Per-op entitlement — `requiredEntitlement` in the effective set | `subscription_required` (403) | yes (dev cascade satisfies it) |
| 4.5 | Feature kill-switch — `getBool(featureFlag)` | `feature_disabled` (403) with `feature` | no (global kill-switch) |
| — | `ensureCanonicalUserRow` (idempotent FK upsert) | non-fatal | no |
| 5 | Cap check — `computeEffectiveCap` vs `readUsageColumn` | `cap_reached` / `runaway_protection` (429) | yes (and `handler_owned` self-manage) |
| 6 | `checkRateLimit(Bucket.AiEngine, authUserId, isDeveloper)` | rate-limit response | yes |
| 7 | `handler.execute(ctx)` in `try/catch` | `handler_threw` (500) on throw | no |
| 8 | `incrementUsageColumn(authUserId, usageColumn)` on `ok` | non-fatal | yes (and `handler_owned`) |

The feature kill-switch runs **after** entitlement so a tier-ineligible caller sees the clearer `subscription_required` rather than a vague `feature_disabled`. It fires even for dev accounts — the intent is a global kill-switch, not a quota. Today only `kb_query` declares a `featureFlag` (`kb_chat_enabled`).

## One global rate-limit bucket

`ai-engine` calls `checkRateLimit(Bucket.AiEngine, authUserId, isDeveloper)` inside `dispatchOperation` rather than via `runGates` chain-sugar. A single fixed-window `Bucket.AiEngine` counter spans **every** operation for a user. The goal is crash-loop / runaway-client protection, not per-operation budgeting — the monthly caps already handle that. Dev callers short-circuit the check. Doing it inside the dispatcher (not the outer chain) is what preserves the per-op observability headers.

`currentPeriod()` returns the `YYYY-MM` UTC period key stamped into cap-error payloads. `ensureCanonicalUserRow` upserts the `canonical_users` row (`ignoreDuplicates`) so FK child inserts (`transcribe_jobs`, `user_blueprints`) can't fail on a first-launch race; it is non-fatal.
