The backend is a set of Deno Edge Functions under `supabase/functions/`. There are 33 directories; 32 are HTTP endpoints registered in `config.toml`, and every one of those shares a single admission-chain entry point — `runGates()` — so authentication, App Check, and rate limiting always run in the same fixed order.

## Function count vs. registered endpoints

There are **33 directories** under `supabase/functions/` (excluding `_shared/`), but `config.toml` declares **32** `[functions.<name>]` blocks. One directory is intentionally unregistered:

| Directory | Why it is not in `config.toml` |
| --- | --- |
| `transcribe-drain` | A `Deno.cron("transcribe-drain", "* * * * *", …)` minute job — it has no HTTP handler and never calls `runGates()`. Its primary path is an inline `runDrain()` import from the `transcribe_submit` handler; the cron only mops up overflow and 429-backoff retries. |

`recovery-code-generate` was previously unregistered too. It is deprecated (superseded by the two-op `recovery-code` function), but `config.toml` now declares `[functions.recovery-code-generate]` with `verify_jwt = false` — closing the same inherited `verify_jwt = true` auth trap that every block-less `AuthMode.Jwt` function hits, so a stray call to the old path is rejected by our gate chain rather than by Supabase Auth.

Every registered function sets `verify_jwt = false`. That is deliberate: the built-in Supabase JWT check is replaced by our own `runGates()` chain, which verifies a **Clerk** session token (or App Check, or a webhook secret) depending on the function's auth mode. Leaving Supabase's check on would reject legitimate callers.

## The `runGates()` admission chain

`runGates(req, config)` (`functions/_shared/gates/index.ts`) is the single declarative entry point (RR-303). Each function passes one `GateConfig` object and gets back either `{ response: Response }` (a gate failed — return it immediately) or a mode-specific success context. The return type is narrowed by the config's `auth` mode, so reading `authUserId` on a webhook function is a compile error.

Gates always run in a fixed order — per-function reordering is structurally impossible, so a mistake like "rate limit before JWT" cannot be written:

| # | Gate | File | Opt-out / notes |
| --- | --- | --- | --- |
| 1 | HTTP method | `functions/_shared/gates/method.ts` | `405 method_not_allowed` on mismatch |
| 2 | App Check (`X-Firebase-AppCheck`) | `functions/_shared/gates/app-check.ts` | `skipAppCheck` — verifies against Firebase JWKS; `401 invalid_app_check` |
| 3 | App Version floor (`X-App-Version`) | `functions/_shared/gates/app-version.ts` | `skipAppVersion` — `410 client_too_old` below `min_supported_app_version_code` |
| 4 | Auth (`Jwt` / `WebhookSecret` / `None`) | `functions/_shared/gates/jwt.ts`, `webhook-secret.ts` | mode-specific |
| 5 | Entitlement fetch (JWT only) | `functions/_shared/gates/entitlement.ts` | derives `isDeveloper`; `502 entitlement_check_failed` |
| 6 | Entitlement check (JWT only, if `entitlement: [...]`) | `functions/_shared/gates/entitlement.ts` | at-least-one-of; RR-358 grace fallback when `allowGracePeriodRead` |
| 7 | Account-freeze check (JWT only, RR-310) | `functions/_shared/gates/account-frozen.ts` | fires **before** rate-limit so frozen attempts burn no quota; applies to dev too |
| 8 | Rate-limit sugar (if `rateLimit: { bucket }`) | `functions/_shared/gates/rate-limit.ts` | skipped for dev callers |

Entitlement **check** runs before rate limit on purpose: a non-paying caller gets `403 subscription_required` on the first request rather than spending rate budget to also collect a `429`.

### The step-0 health-probe door

The gate-order table above (steps 1–8) is preceded by a **step-0 door**: 15 functions host a read-only liveness probe declared via `healthCheck` in their `GateConfig`. When an `X-Health-Probe` header is present it short-circuits the chain **before** the method and App Check gates and returns a component-health result, so an uptime monitor can confirm the endpoint's critical dependency (DB, Storage, Clerk, Cohere, AssemblyAI, or the AI chain) is actually serving — without a real request, a JWT, or an App Check token. The functions hosting one: `account-otp`, `ai-engine`, `assemblyai-webhook`, `indexing`, `recovery-code`, `resolve-identity`, `search`, `set-user-pin`, `sync-audio`, `sync-group-exclude`, `sync-pull`, `sync-push`, `sync-reconcile`, `sync-reserve`, and `user-sync-preferences`. See [health probes](/rollingrecord/backend/gates/health-probes) for the probe types.

### Auth modes

`AuthMode` (`functions/_shared/gates/types.ts`) is a three-value enum:

| Mode | Wire value | Proof of identity |
| --- | --- | --- |
| `AuthMode.Jwt` | `jwt` | `Authorization: Bearer <jwt>` — a **Clerk** session token, RS256-verified against Clerk's JWKS (`iss` derived from `CLERK_JWKS_URL`, RR-451). Resolves `authUserId` + `email`. |
| `AuthMode.WebhookSecret` | `webhook-secret` | `Authorization: Bearer <secret>` matched against the env var named by `secretEnvVar` (default `REVENUECAT_WEBHOOK_SECRET`). No user identity. |
| `AuthMode.None` | `none` | No auth — App Check only. Public endpoints like `server-config`. Declaring `rateLimit` on this mode throws at startup (no subject-key strategy yet). |

<Note>
Several in-code docstrings still say "Supabase Auth JWT". That terminology is stale — `runGates` `AuthMode.Jwt` verifies a **Clerk** token via `jwt.ts`.
</Note>

## Response helpers are per-function, not shared

`runGates()` is the shared piece. The JSON response helper is **not** — every function declares its own local `function json(body, status): Response` that wraps `JSON.stringify` with `Content-Type: application/json`. `ai-engine` adds an `extraHeaders` parameter to its copy; the rest are plain. There is no shared response-helper module in `_shared/`.

Every `error` string returned to a client comes from the canonical registry in `functions/_shared/errors.ts` (`AppError.X.code` / `AppError.X.httpStatus`), never an inline literal — the Kotlin mirror is `AiEngineErrorCode.kt`.

## Operation-dispatch functions

Several functions front many logical operations behind one endpoint and switch on a `body.operation` field — the single-secret-deploy pattern. Adding an operation is a new `switch` case plus a client helper, with no new function deployment, secret, or gate config. `ai-engine` (a full handler registry) and `analytics` (`log_eval_run`) are the canonical examples; `extract-results`, `indexing`, `sync-audio`, and `sync-reconcile` also dispatch this way. `notifications` uses the same name-keyed `OPERATIONS` map with a derived `OPERATION_NAMES` as `ai-engine` and `support-ops` — the dispatcher resolves by name and can never reach an unregistered one.
