This page covers two unrelated-but-adjacent pieces of content-free telemetry: the `analytics` Edge Function (a server-to-server ingest the Python eval harness calls) and the platform-stats subsystem (anonymous lifetime usage counters bumped server-side when real events succeed). Neither records customer content, per the "No Use of Customer Data" rule.

`analytics` (`functions/analytics/index.ts`) is a `Deno.serve` POST dispatcher authenticated by a shared secret. v1 ships exactly one operation — `log_eval_run` — which upserts a single row into `l_eval_run` keyed on `run_id`. It records only run metadata (counts, cost, git SHA), never customer content.

## Gate chain

The entry calls `runGates(req, { method: Post, skipAppCheck: true, skipAppVersion: true, auth: AuthMode.WebhookSecret, secretEnvVar: "ANALYTICS_INGEST_SECRET" })`. Both App Check and App Version are opted out because the caller is the Python eval harness on a dev machine, not the mobile app — it sends neither header. The harness authenticates with `Authorization: Bearer <ANALYTICS_INGEST_SECRET>`.

After the chain, the body is parsed as `AnalyticsBody` (`{ operation: string, input: unknown }`):

| Condition | Response |
| --- | --- |
| Body isn't valid JSON | `INVALID_BODY` |
| `operation` missing / not a string | `MISSING_OPERATION` |
| `operation` unknown | `INVALID_OPERATION` (echoes `operation`) |
| Handler throws | `HANDLER_THREW` |

There is deliberately no shared body schema across operations — the analytics surface is heterogeneous, and each future op owns its own input validation.

## `log_eval_run`

`handleLogEvalRun` upserts into `l_eval_run` with `onConflict: "run_id"`. The harness calls it at run start, periodically as cases complete, and at run end, so a crashed harness still leaves an interrogable trail. Input is validated by `validateLogEvalRunInput` (`functions/analytics/validation.ts`), which returns a typed `LogEvalRunInput` or an error string that the dispatcher maps to `VALIDATION_FAILED` with a `detail`.

Only fields the caller actually provided are written, so a partial "progress" upsert never clobbers previously-recorded counts:

| Field group | Written by function? | Notes |
| --- | --- | --- |
| `run_id` / `status` / `scope` / `dry_run` | always | core upsert key + state |
| `started_at` / `finished_at` / `git_sha` / `git_branch` / `notes` | only if provided | passthrough — absent keys skipped |
| `cases_run` / `cases_passed` / `cases_failed` / `cases_uncertain` / `cases_skipped` / `cases_flaked` | only if provided | count columns |
| `production_*` / `judge_*` (calls, input/output tokens, `cost_usd`) | only if provided | model + cost telemetry |
| `pass_rate` | never | DB `GENERATED` column, derived from the counts |
| `total_cost_usd` | never | DB-side generated column |

On a successful upsert it returns `{ ok: true, run_id }` (200); a DB failure returns `DATABASE_ERROR`.

<Note>
An earlier design exposed a `judge_inference` operation that proxied Anthropic calls to keep the API key server-side. It was walked back — the harness now calls Anthropic directly via `evals/_anthropic.py` — so v1 has exactly one operation.
</Note>

## Platform stats

Platform stats are anonymous, lifetime, platform-wide usage counters — "bragging rights" numbers for company stats. Unlike the eval-run ingest above, there is **no Edge Function and no public endpoint**: the counters are bumped from inside other functions and from database triggers, and read manually through two views (Supabase SQL editor / service role). The subsystem is defined by `functions/_shared/analytics/platform-stats.ts` and migration `supabase/migrations/20261001120000_platform_stats.sql`.

Two properties define it:

- **Content-free.** Only a metric name and a number are ever written — no `auth_user_id`, no recording id, no text. This is the "aggregate, content-free metrics" case the "No Use of Customer Data" rule explicitly allows.
- **Outside the delete-user cascade.** Because the rows carry no user id, they are intentionally **not** FK-backed to `canonical_users` and **not** listed in `delete-user` — there is nothing per-user to wipe. This is also why the design uses counters rather than summing `usage` / `c_recordings`: lifetime totals must never go down, and those tables shrink on every account deletion. A counter a deletion never touches is the only shape that keeps a lifetime total monotonic.

### The six metrics

`PlatformMetric` enumerates the tracked slugs, which must match the `CHECK` constraint on `platform_stats_daily.metric`.

| Metric slug | Unit | Bumped when |
| --- | --- | --- |
| `accounts_created` | count | a `canonical_users` row is first created |
| `transcription_ms` | audio ms | a cloud transcription completes (raw audio duration) |
| `transcription_words` | count | the same completion (word count only, never the text) |
| `ai_questions_answered` | count | a KB-chat question gets its final answer |
| `insights_extracted` | count | an extraction job finishes (sections + tasks the run added) |
| `backup_audio_ms` | audio ms | a cloud audio backup commit succeeds |

### `platform_stats_daily` and the 8-shard layout

`platform_stats_daily` holds one row per `(metric, UTC day, shard)` — PK `(metric, day, shard)`, plus `value BIGINT` and `updated_at`. RLS is enabled with no policies. Three `CHECK` constraints guard it: `metric` must be one of the six slugs (so a caller typo can't invent a stray metric), `shard` is `BETWEEN 0 AND 7`, and `value >= 0`.

The **8 shards** exist to avoid row contention. Each increment lands on a random shard (`floor(random() * 8)`) with one atomic `INSERT ... ON CONFLICT DO UPDATE`, so concurrent writers rarely touch the same row and no increment is ever lost. Reads `SUM` the shards back together. Total volume stays tiny: 6 metrics × 8 shards × 1 row per day.

### The `increment_platform_stat` RPC

`increment_platform_stat(p_metric text, p_amount bigint)` is the single atomic write path. It no-ops when `p_amount` is null or `<= 0` (a stats write must never fail a real request), otherwise does the sharded `INSERT ... ON CONFLICT (metric, day, shard) DO UPDATE SET value = value + EXCLUDED.value`. It is `REVOKE`d from `anon` / `authenticated` and `GRANT`ed `EXECUTE` to `service_role` only — an unknown metric raises against the `CHECK`.

### Where each metric is counted

Three metrics are counted in **Edge code** (which already has an exactly-once success path) via the `recordPlatformStat` helper; the other three are counted by **database triggers**, because only the database sees the once-only moment.

| Metric | Counted by | Site |
| --- | --- | --- |
| `transcription_ms` | `recordPlatformStat` | `assemblyai-webhook` (`functions/assemblyai-webhook/index.ts`), using AssemblyAI's raw `audioDuration`, not the medical-mode-multiplied billed duration |
| `transcription_words` | `recordPlatformStat` | `assemblyai-webhook`, `transcript.words.length` (or `countWords` fallback) — a count only, text never leaves the function |
| `ai_questions_answered` | `recordPlatformStat` | `kb_query` (`functions/ai-engine/operations/kb-query.ts`), once at the terminal answer; the client's one-shot `expandQuery` / `hydeSearch` helper calls are excluded |
| `accounts_created` | DB trigger | `AFTER INSERT ON canonical_users` |
| `backup_audio_ms` | DB trigger | `c_recordings` `cloud_backup_committed_at` going `NULL` → set |
| `insights_extracted` | DB trigger | extract-runner stamps `extraction_jobs.insights_added`; the trigger increments on the transition into `DONE` |

### The four AFTER triggers

All three trigger-counted metrics are wired through four `AFTER` triggers (defined in the migration). Each trigger body wraps its work in `BEGIN ... EXCEPTION WHEN OTHERS THEN RAISE WARNING` so a stats bump can never abort the user's underlying write — least of all on `c_recordings`, a high-risk table. The triggers only read the firing row and write `platform_stats_daily`; none touches a crypto column.

| Trigger | Fires on | Guard |
| --- | --- | --- |
| `trg_platform_stats_account_created` | `AFTER INSERT ON canonical_users` | none — a brand-new account can't hold the `developer` entitlement yet |
| `trg_platform_stats_backup_committed_ins` | `AFTER INSERT ON c_recordings` | `cloud_backup_committed_at` + `storage_path` set, `deleted_at` null (a row pushed already committed) |
| `trg_platform_stats_backup_committed_upd` | `AFTER UPDATE OF cloud_backup_committed_at ON c_recordings` | `OLD` null → `NEW` set (the commit transition only; re-pushes never fire) |
| `trg_platform_stats_extraction_done` | `AFTER UPDATE OF status ON extraction_jobs` | `OLD.status` distinct from `DONE`, `NEW.status = DONE`, `insights_added > 0` |

Developer accounts are excluded, but by different mechanisms per metric. `backup_audio_ms`'s trigger calls `_platform_stats_is_developer(auth_user_id)` — the same `developer`-entitlement source of truth as `isDeveloperAccount()` — and skips the bump for a dev. `insights_extracted` has no in-trigger dev check: extract-runner already stamps `insights_added = 0` for developer runs, and the trigger's `insights_added > 0` guard means a `0` never fires it. `accounts_created` needs no check at all — the entitlement is granted after sign-up, so a brand-new account can't hold it yet.

### `extraction_jobs.insights_added`

The migration adds a nullable `insights_added INTEGER` column to `extraction_jobs`. extract-runner's `finalize` stamps it in the same `UPDATE` that sets `status = 'DONE'`: the count of sections + tasks the run **added** relative to the card it started from (`insightsAdded(before, after)` = `max(0, after - before)`, measured with `countCardInsights`), or `0` for developer accounts. The `trg_platform_stats_extraction_done` trigger counts it only on the transition into `DONE`, so a re-finalize (requeue / stale re-claim) never double-counts. It stays `NULL` on jobs created before the column shipped, and a `NULL` never fires the trigger.

### The read views

Two `security_invoker` views expose the numbers, both `REVOKE`d from `anon` / `authenticated` and `GRANT SELECT` to `service_role` only — there is deliberately no PostgREST-reachable public read:

| View | Shape | Notes |
| --- | --- | --- |
| `platform_stats_totals` | one row per metric: `total`, `display_value`, `display_unit`, `first_day`, `last_updated_at` | lifetime totals; `transcription_ms` also shown as minutes, `backup_audio_ms` as hours |
| `platform_stats_monthly` | one row per `(YYYY-MM, metric)`: `total`, `display_value` | per-UTC-month totals for growth over time |

### The `recordPlatformStat` helper

`recordPlatformStat(metric, amount, { isDeveloper })` is the Edge-side entry point. It is **fire-and-forget**: it never throws and never blocks the caller's success path (failures are logged and swallowed), so call sites invoke it with a trailing `.catch(() => {})` only to satisfy lint. It skips developer accounts, and coerces the amount through `normalizeStatAmount` — flooring fractions and dropping zero / negative / non-finite values to a no-op. The helper's contract for call sites: count **only on success**, **once per logical event** (after whatever guard already makes the success path run once), and pass `isDeveloper`.
