description: "The three inbound webhooks — clerk-webhook, revenuecat-webhook, and assemblyai-webhook — their auth mechanisms, and what each one writes."
---

Three inbound webhooks drive identity, entitlements, and transcription completion. All three are server-to-server callers that cannot send App Check or App Version headers, so both are opted out; all three are replay-safe because Clerk (Svix), RevenueCat, and AssemblyAI all retry failed deliveries.

| Webhook | Auth (`runGates`) | Secret env var | Primary writes |
| --- | --- | --- | --- |
| `clerk-webhook` | `AuthMode.None` + Svix HMAC in handler | `CLERK_WEBHOOK_SECRET` | `canonical_users` provision (created/updated), full GDPR `wipeUser` (deleted) |
| `revenuecat-webhook` | `AuthMode.WebhookSecret` | `REVENUECAT_WEBHOOK_SECRET` | `lifetime_entitlements`, `canonical_users` cloud-grace columns (`cloud_grace_started_at`/`cloud_grace_tier`) + `last_known_entitlements`, `l_entitlement_events`, bundle credits/refunds, `f_user_financials.revenue_micros` **and** `sandbox_revenue_micros` (environment-routed) |
| `assemblyai-webhook` | `AuthMode.WebhookSecret` | `ASSEMBLYAI_WEBHOOK_SECRET` | `transcribe_results` (encrypted), metered-op commit, `f_user_financials.ai_cost_micros`, `h_transcribe_history` |

## clerk-webhook

`functions/clerk-webhook/index.ts` calls `runGates(req, { method: Post, skipAppCheck: true, skipAppVersion: true, auth: AuthMode.None })`. Unlike the other two, its auth is **not** a `runGates` mode — it reads the raw body once and calls `verifySvixSignature(headers, rawBody, "CLERK_WEBHOOK_SECRET")` (`functions/_shared/auth/svix.ts`), an HMAC-SHA256 over `svix-id.svix-timestamp.rawBody` against the `whsec_…` secret. A mismatch returns `401 invalid_signature` — Svix does **not** retry 4xx. It routes on `event.type`:

| Event | Handler | Effect |
| --- | --- | --- |
| `user.created` | `handleUserCreated` | Upsert `canonical_users` (`ON CONFLICT DO NOTHING`, stores `email_hash`) + `carryForwardOnResignup` on fresh creation |
| `user.updated` | `handleUserUpdated` | Refresh `canonical_users.email_hash` |
| `user.deleted` | `handleUserDeleted` | `wipeUser(authUserId, { skipSubscriptionCheck: true })` — full GDPR cascade, **unless** the account is frozen, in which case it quarantines instead of wiping (see the freeze hold below) |
| any other | default | `200` no-op |

A missing `data.id` returns `missing_event_fields`. `wipeUser` (`functions/_shared/users/wipe.ts`) is the shared erasure ladder used by both this webhook and the in-app `delete-user` function: it wipes every user-data table and Storage bucket, writes the `l_deleted_identity` anti-abuse snapshot **when an email hash resolves**, and deletes the RC customer + Clerk user. The snapshot is conditional, not guaranteed: step 2 uses the stored `canonical_users.email_hash` (written by this webhook on `user.created` / `user.updated`) and falls back to `resolveEmailHash` — the supplied email, else a Clerk API lookup. If neither yields a hash it logs `no email hash resolvable for user; skipping anti-abuse snapshot` and continues with `snapshotWritten: false`, so re-signup carryover has nothing to key on. This path is the one most exposed to that: `handleUserDeleted` passes **no** email, and the Clerk user is already gone, so a user with no stored `email_hash` gets no snapshot. On partial failure it throws `IdentityLookupFailedError` / `CanonicalUserDeleteFailedError`, which map to `500` so Svix retries — `wipeUser` is idempotent, so the retry resumes cleanly.

**Frozen accounts are never wiped here (freeze hold).** Before wiping, `handleUserDeleted` reads `canonical_users.frozen_at` — the same check the account-frozen gate performs, done here because the webhook carries no JWT for that gate to run. If the account is frozen it QUARANTINES instead of wiping: it logs an `AbuseEventType.FrozenUserClerkDeletion` event (slug `frozen_user_clerk_deletion`, weight `10` — the ceiling) via `logAbuseEvent`, returns `200 { status: "quarantined_frozen" }`, and preserves the server data for the investigation (an admin resolves the hold via support-ops). A freeze is an evidence hold, and a Clerk-side deletion is the one path that used to slip past the account-frozen gate; self-serve Clerk deletion is disabled in the Clerk dashboard, so this guard is the defense-in-depth layer beneath that toggle. An unknown or failed frozen-state read returns `500` so Svix retries — `wipeUser` stays idempotent for the eventual clean run. (`AbuseEventType` and `logAbuseEvent` are imported from `functions/_shared/users/abuse-log.ts`.)

## revenuecat-webhook

`functions/revenuecat-webhook/index.ts` calls `runGates(req, { method: Post, skipAppCheck: true, skipAppVersion: true, auth: AuthMode.WebhookSecret })` (default `REVENUECAT_WEBHOOK_SECRET`). It is the authoritative writer of `lifetime_entitlements` — every path (admin script, real purchase, refund) flows through RC and arrives here. `dispatchEvent` runs, in order:

1. `logEntitlementEvents` — upserts one `l_entitlement_events` row per entitlement-in-event for **every** delivery (`onConflict: "event_id,entitlement_id"`), returning `isFreshEvent` for downstream dedup.
2. `handleRecurringSubEvent` — RR-358 / RR-328 cloud-grace tracking: maintains `canonical_users.cloud_grace_started_at` + `cloud_grace_tier` and the `last_known_entitlements` key snapshot they are derived from (see below).
3. `handleRecurringSubRevenue` — writes revenue for `INITIAL_PURCHASE` / `RENEWAL` on `pro` / `pro_cloud` / `pro_cloud_ai`, gated on `isFreshEvent`. The destination column is chosen per-event by `revenueColumnFor(event.environment)` (`revenuecat-webhook/revenue-routing.ts`): `f_user_financials.revenue_micros` when `environment` is exactly `"PRODUCTION"` (case-insensitive), `sandbox_revenue_micros` for anything else.
4. The two bundle branches — both `return`, so the lifetime switch never runs for a bundle.
5. `if (mirroredMetas.length === 0) return` — no lifetime entitlement attached, nothing further to do.
6. Lifetime grant / revoke for mirrored keys.

| Branch | Event type matched | Additional conditions | Handler |
| --- | --- | --- | --- |
| Bundle purchase | `NON_RENEWING_PURCHASE` (alias `NON_SUBSCRIPTION_PURCHASE`) | `event.product_id` present **and** `mirroredMetas.length === 0` | `handleNonSubscriptionPurchase` → bundle credit |
| Bundle refund | `CANCELLATION` | `event.product_id` present **and** `mirroredMetas.length === 0` | `handleBundleRefund` → clawback |

RevenueCat sends `NON_RENEWING_PURCHASE`; `NON_SUBSCRIPTION_PURCHASE` is a type RC does not send and is retained only as an accepted alias so a delivery already in flight cannot fall into the hole that name created — the branch originally matched only the alias, so every bundle purchase fell through to the mirrored-key gate and was dropped after the buyer had been charged. Because the branch `return`s, a mis-typed match is not a harmless no-op.

The `product_id` + empty-`mirroredMetas` pair is the discriminator, **not** the type alone. Both bundle branches use the same shape:

| `NON_RENEWING_PURCHASE` shape | Discriminator | Routes to |
| --- | --- | --- |
| Bundle IAP | carries `product_id`, no mirrored entitlement key | `handleNonSubscriptionPurchase` (step 4, returns) |
| Founders-edition lifetime | carries `founders_edition` in `entitlement_id` / `entitlement_ids` | falls through to `handleLifetimeGrant` (step 6) |

Without that guard the bundle branch would swallow the lifetime: the SKU lookup would miss, and the `return` would skip the grant entirely.

Only entitlements in `WEBHOOK_MIRRORED_LOOKUP_KEYS` (lifetime + `developer`) are mirrored to the DB — recurring subs are log-only because the gate chain reads entitlements live from RC. Grants (`INITIAL_PURCHASE` / `NON_RENEWING_PURCHASE` / `TEMPORARY_ENTITLEMENT_GRANT`) insert with a `source` from `attributeSource()` (`developer` / `manual_admin` / `employee_perk` / `founders_edition_purchase`); revocations (`CANCELLATION` → `cancel_reason`, `EXPIRATION` → `rc_expiration` fallback) are idempotent via the partial `UNIQUE (email_hash, rc_entitlement) WHERE revoked_at IS NULL`.

**Cloud-grace tracking** no longer keys on the `EXPIRATION` event type. `entitlement_ids` on a webhook are the entitlements OF THAT PRODUCT, not the customer's full set, and Google Play downgrades are DEFERRED — `PRODUCT_CHANGE` fires immediately but is informational, and the entitlements are REPLACED at `RENEWAL` with NO `EXPIRATION` for the old cloud entitlement — so keying on `EXPIRATION` missed every plan-switch downgrade. Instead, any recurring-sub webhook is treated as a **trigger**: the handler re-reads the authoritative RC set via `getActiveEntitlementKeys(authUserId, { bypassCache: true })` and diffs it against the stored `last_known_entitlements` through `pickHighestRecurringCloudTier`.

| Transition | Action |
| --- | --- |
| had cloud, no longer (`hadCloud && !hasCloud`) | open the window — set `cloud_grace_started_at` + `cloud_grace_tier` to the tier they held (guarded on the window not already being open so a redelivered webhook can't push the deadline out) |
| holds cloud now (`hasCloud`) | clear the pair (active / resubscribed / upgraded) |
| neither | snapshot `last_known_entitlements` only |

Every route out of cloud — expiry, a deferred plan switch landing at renewal, a refund, a chargeback, a dashboard revoke — collapses into the first case. `CANCELLATION` needs no special handling any more: RC fires it while the entitlement is still live, so the authoritative fetch still shows cloud and it lands in "has cloud". `developer`, `lifetime`, and `pro` are deliberately excluded — a hard cutoff with no grace window — because `RECURRING_CLOUD_KEYS` (`pro_cloud`, `pro_cloud_ai`) is the allowlist behind `pickHighestRecurringCloudTier`, so their removal is never a cloud transition; the `canonical_users_cloud_grace_tier_values` CHECK constraint further pins the column to `pro_cloud` / `pro_cloud_ai`. Storing KEYS rather than a resolved tier is what makes the cutoff work — `developer` and `pro_cloud_ai` resolve to the same tier but must behave differently here. See [billing → RevenueCat](/rollingrecord/backend/billing/revenuecat) and [entitlement & grace](/rollingrecord/backend/gates/entitlement-and-grace) for the full model.

**Bundle IAPs** look `bundle_config` up by `normalizeBundleSku(event.product_id)` (`_shared/billing/bundle-sku.ts`) — Google qualifies a one-time product id as `sku:purchase_option`, so the raw id would miss the row and credit a charged buyer nothing. Tier is then resolved with `fetchEffectiveEntitlements(authUserId, { bypassCache: true })` against `TIER.PRO_CLOUD_AI`, not a raw RC key check, so `developer` and `lifetime_pro_cloud_ai` holders get the query + extraction half of the bundle they paid for. Credits go through `creditBundle` (idempotent on `l_credit_log UNIQUE(purchase_token)`); refunds clamp-at-zero via `refundBundle` keyed on `refund_of_token`. The bundle **revenue** write is environment-routed like the recurring-sub one, but the **credit** is not: a sandbox bundle buyer still gets their minutes, and only the revenue accounting is diverted to `sandbox_revenue_micros`. The handler always returns 2xx to RC unless a transient error (`500` → RC retries). The same `bundle_config` rows are served to the client, with the same per-tier rule, by [get-bundle-catalog](/rollingrecord/backend/edge-functions/get-bundle-catalog).

<Warning>
`revenuecat-webhook` records **revenue** (from `event.price` via `usdToMicros`) into `f_user_financials.revenue_micros` for `PRODUCTION` events and `sandbox_revenue_micros` for SANDBOX / non-production ones, so a test purchase can never inflate real income. It never writes transcription or LLM cost. Transcription cost goes to `f_user_financials.ai_cost_micros` via `assemblyai-webhook`; LLM cost goes to the same column via the AI dispatcher (`_shared/ai/client.ts::trackTokenUsage`).
</Warning>

| Webhook | `f_user_financials` column | Direction |
| --- | --- | --- |
| `revenuecat-webhook` | `revenue_micros` | money **in**, PRODUCTION events only (`event.price` → `usdToMicros`) |
| `revenuecat-webhook` | `sandbox_revenue_micros` | money **in**, SANDBOX / non-production events — excluded from real income |
| `assemblyai-webhook` | `ai_cost_micros` | cost **out** (transcription cost, incl. dev accounts) |

Both revenue call sites share the one decider, so recurring subs and bundle IAPs cannot disagree about what counts as a real sale. A sandbox purchase still does everything else a real one does — the `l_entitlement_events` audit row (which independently records the same `environment` field), cloud-grace state maintenance, the bundle credit via `creditBundle`, and the storage-cost re-stamp inside `increment_financial_counter` — it just lands in a different revenue column. The RPC's allowlist is now `('ai_cost_micros', 'revenue_micros', 'sandbox_revenue_micros')`; any other column name RAISEs `increment_financial_counter: column % is not increment-safe`. Both webhooks reach it through `incrementFinancialColumn` in `_shared/db/usage-counters.ts`.

## assemblyai-webhook

`functions/assemblyai-webhook/index.ts` calls `runGates(req, { method: Post, skipAppCheck: true, skipAppVersion: true, auth: AuthMode.WebhookSecret, secretEnvVar: "ASSEMBLYAI_WEBHOOK_SECRET", healthCheck: dbStorageAssemblyAIHealthCheck("assemblyai-webhook", "transcribe-inbox") })`. That last key is what the other two webhooks do **not** have: it opts this function into the gate-0 health probe, so a request carrying a valid `X-Health-Probe: <HEALTH_PROBE_SECRET>` short-circuits the entire chain — ahead of auth and even ahead of the method gate, so a GET probe isn't bounced by POST-only — and returns just the check result (DB liveness + the `transcribe-inbox` Storage bucket + a free AssemblyAI list-transcripts reachability call), never caller data. It is the completion callback for the async transcribe flow. The payload is `{ transcript_id, status }`; `status` must be `completed` or `error` (else `webhook_invalid_status`). `loadTranscribeJobByAssemblyAiId` resolves the job — a miss returns `200 { outcome: "already_processed" }` (idempotent duplicate delivery). It then routes to `handleCompletedStatus` or `handleErrorStatus`; an `isNoSpeechError` on the error path routes to `handleNoSpeech`, which stores an empty completed transcript and charges nothing.

`handleCompletedStatus` runs the success ladder:

1. `fetchCompletedTranscript` → the full text + per-word data.
2. `insertCompletedResult` — an **encrypted** `transcribe_results` row (PK `transcribe_job_id`; a duplicate short-circuits to `200`).
3. `deleteTranscript` — fire-and-forget cleanup on AssemblyAI's side.
4. `commitMeteredOp` — commits the metered-ms reservation persisted at submit time.
5. `incrementFinancialColumn("ai_cost_micros", usdToMicros(computeTranscriptionCostUsd(...)))` — recorded for **every** caller including devs (dev bypass is a quota exception, not a cost-visibility one).
6. `recordTranscribeHistory` — an `h_transcribe_history` row.
7. `updateTranscribeJobStatus("completed")` then `deleteTranscribeJob`.

Billing uses the server-measured reservation (`opCostMs`) as the source of truth; a missing reservation (legacy in-flight rows from the old synchronous op) charges zero rather than guessing. Deliveries return 2xx to stop retries, 5xx to trigger a retry, and avoid 4xx on the job-found path so a real job is never orphaned.
