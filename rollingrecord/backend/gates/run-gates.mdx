---
title: "The runGates() Admission Chain"
description: "The single declarative dispatcher every Edge Function routes through, running a fixed non-reorderable admission order derived from one GateConfig object."
---

Every Edge Function replaces a hand-rolled gate chain with one call: `runGates(req, config)` in `functions/_shared/gates/index.ts`. The dispatcher runs a fixed, non-reorderable sequence and returns either a short-circuit failure or a type-narrowed success context — so a mistake like "rate limit before JWT" is structurally impossible.

## The dispatcher

`runGates<C extends GateConfig>(req, config)` returns `Promise<ResolvedContext<C>>`, which is a union of two shapes:

| Outcome | Shape | Meaning |
| --- | --- | --- |
| Failure | `GateFailureCtx` — `{ response: Response }` | A gate rejected the caller; the handler returns `ctx.response` verbatim. |
| Success | mode-specific context, `response: null` | Admitted; the handler reads the fields for its auth mode. |

The success type is narrowed by `config.auth`. A `JwtGateConfig` yields `JwtSuccessCtx` with `authUserId` typed; a `WebhookSecretGateConfig` yields `WebhookSuccessCtx` with no user fields at all — reading `authUserId` on a webhook handler is a compile error, not a runtime surprise.

```ts
const ctx = await runGates(req, {
  method: HttpMethod.Post,
  auth: AuthMode.Jwt,
  entitlement: [Entitlement.ProCloudAi],
  rateLimit: { bucket: Bucket.AiEngine },
})
if (ctx.response) return ctx.response
const { authUserId, isDeveloper, isGracePeriod } = ctx
```

## Fixed admission order

For a JWT function with every option set, the chain runs in this order. For functions that opt in, the chain now begins at step 0 (the health probe); a valid probe short-circuits the ENTIRE chain — before method — to a 200/503 liveness response and never reaches the handler. The example below still shows steps 1–8 for a normal JWT call. Each gate lives in its own file under `functions/_shared/gates/`.

| Step | Gate | Runs when | Opt-out / skip | File |
| --- | --- | --- | --- | --- |
| 0 | Health probe | `config.healthCheck` set AND valid `X-Health-Probe` header | opt-in only (no `healthCheck` = disabled) | `health.ts` |
| 1 | HTTP method | always | none (`method` required) | `method.ts` |
| 2 | App Check | `!config.skipAppCheck` | `skipAppCheck: true` | `app-check.ts` |
| 3 | App Version floor | `!config.skipAppVersion` | `skipAppVersion: true` | `app-version.ts` |
| 4 | Auth | always (mode-specific) | `AuthMode.None` does no auth | `jwt.ts` / `webhook-secret.ts` |
| 5 | Entitlement fetch | JWT only | always — derives `isDeveloper` | `entitlement.ts` |
| 6 | Entitlement check | JWT only, when `entitlement: [...]` set | grace fallback via `allowGracePeriodRead` | `entitlement.ts` + `grace.ts` |
| 7 | Account-freeze check | JWT only (RR-310) | none — no bypass, even for dev | `account-frozen.ts` |
| 8 | Rate-limit sugar | when `rateLimit: { bucket }` set | skipped for developer callers | `rate-limit.ts` |

Step 5 runs for **every** JWT caller even when no `entitlement: [...]` is declared, because it is what derives `isDeveloper` for the dev-bypass path. Step 6 — the at-least-one-of match — is the part that only runs when a requirement is declared.

The fetch honors an `X-Entitlement-Refresh: 1` cache bypass: `runGates` calls `fetchEffectiveEntitlements(authUserId, { bypassCache: req.headers.get("X-Entitlement-Refresh") === "1" })`. The app sends the header right after a purchase or restore, when a cached "no" would otherwise deny someone who has just paid. The header only chooses cache-vs-RC — RevenueCat stays the sole authority — and the RC layer throttles the bypass to roughly 3 calls/min/account, so it cannot be abused.

## Why rate-limit sits last

The entitlement check (step 6) is deliberately ahead of the rate-limit step (step 8). A non-paying caller gets `403 subscription_required` on their first request rather than spending rate budget to also collect a `429`. Dev callers never reach the rate-limit step at all (chain sugar is skipped for them), so the only population that actually hits the limiter is entitled, non-developer callers — exactly the set worth rate-limiting. The account-freeze check (step 7) also precedes rate-limit so a frozen account's rejections consume no quota.

## GateConfig shapes

`GateConfig` is a discriminated union of three concrete configs, all extending `GateConfigBase` (which carries the required `method`, the `skipAppCheck` / `skipAppVersion` opt-outs, and the optional `healthCheck?: HealthCheck` uptime opt-in — see [the health-probe door](/rollingrecord/backend/gates/health-probes)). Each endpoint passes exactly one. `gates/index.ts` also re-exports the `HealthCheck` and `HealthResult` types.

| Config | `auth` | Extra fields |
| --- | --- | --- |
| `JwtGateConfig` | `AuthMode.Jwt` | `entitlement?`, `allowGracePeriodRead?`, `rateLimit?` |
| `WebhookSecretGateConfig` | `AuthMode.WebhookSecret` | `secretEnvVar?` (default `REVENUECAT_WEBHOOK_SECRET`), `rateLimit?` |
| `NoAuthGateConfig` | `AuthMode.None` | `rateLimit?` — but declaring it **throws at startup** |

`AuthMode.None` with a `rateLimit` set is not silently ignored: the dispatcher throws `Error("runGates: rateLimit sugar is not supported for AuthMode.None...")` because there is no subject-key strategy for anonymous callers yet.

## The resolved success context

| Context | Fields |
| --- | --- |
| `JwtSuccessCtx` | `response: null`, `auth`, `authUserId`, `email`, `isDeveloper`, `activeEntitlements`, `isGracePeriod` |
| `WebhookSuccessCtx` | `response: null`, `auth` — no user identity |
| `NoAuthSuccessCtx` | `response: null`, `auth` — no user identity |

`RateLimitSugar` (`bucket`, optional `gracePeriodBucket`, optional `abuseEventOnReject`) is the chain-sugar shape for "one limit, keyed on `authUserId`, after auth." On a webhook function the subject key is the prefixed string `__webhook__:<bucket>`, so all webhook callers of that bucket share one counter; there is no dev bypass in that branch.
