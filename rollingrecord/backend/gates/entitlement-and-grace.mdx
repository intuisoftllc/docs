title: "Entitlement Check, Dev Bypass & Grace Window"
description: "How the caller's effective tier is resolved with cascade, how developer bypass is derived, and the RR-358 30-day post-lapse read-grace window."
---

The entitlement stage resolves the caller's effective tier and whether they hold developer bypass, then enforces an at-least-one-of tier requirement. When that requirement fails and the function opted in, an RR-358 grace fallback can still admit a recently-lapsed subscriber for read-only data rescue.

## Fetching the effective set

`fetchEffectiveEntitlements(authUserId, opts: EntitlementFetchOptions = {})` in `functions/_shared/gates/entitlement.ts` resolves both dev-bypass status and the effective entitlement set, on two paths:

1. **`isDeveloperAccount()` first** (`functions/_shared/billing/developer.ts`) — always hits the DB, never cached, with a 3-attempt retry (`[50, 150]`ms backoff). It reads `lifetime_entitlements` for a non-revoked `developer` row and fails closed to `false`.
2. **If dev** → the set is synthesized locally by `devEntitlementSet()` (`{ developer, pro_cloud_ai, pro_cloud, pro }`), skipping RevenueCat entirely. Dev bypass therefore survives RC outages, webhook drift, and customer-id mismatches.
3. **If non-dev** → `getEffectiveEntitlementKeys(authUserId, opts)` (`functions/_shared/billing/revenuecat.ts`), RC-backed with a 5-minute per-customer cache and the tier cascade applied. An RC failure for a non-dev caller fails **closed** with `502 entitlement_check_failed`.

`runGates` sets `opts.bypassCache` from the `X-Entitlement-Refresh: 1` request header, so a client that just purchased or restored gets a live RC read instead of a stale cached "no". The header only chooses cache-vs-RC — RevenueCat stays the sole authority — and the RC layer throttles the bypass (an age floor bounding it to roughly 3 calls/min/account), so the header cannot be abused.

## The at-least-one-of check

`checkEntitlement(active, required)` returns `null` when `required` is empty or any required `Entitlement` key is in the set, else `403 subscription_required` with `required_entitlement` set to the first required key so the client can render "upgrade to `<tier>`" without guessing.

The `Entitlement` enum (`functions/_shared/gates/types.ts`) is the requireable subset — `Pro = "pro"`, `ProCloud = "pro_cloud"`, `ProCloudAi = "pro_cloud_ai"`. The cascade means a higher tier satisfies a lower requirement automatically: holding `developer` (which `ENTITLEMENTS.DEVELOPER` maps to the `pro_cloud_ai` tier with `bypassesCaps: true`) auto-satisfies any tier-gated endpoint.

## The grace window (RR-358)

When the entitlement check fails **and** the config set `allowGracePeriodRead: true`, `runGates` falls back to `checkGraceAdmission(authUserId, required)` in `functions/_shared/gates/grace.ts`. It does a single read-only row read of `canonical_users` and admits (`ctx.isGracePeriod = true`) only when all three conditions hold:

| Condition | Source | Notes |
| --- | --- | --- |
| `cloud_grace_started_at IS NOT NULL` | `canonical_users` | the user actually lapsed under a tracked tier |
| `NOW() - cloud_grace_started_at < graceWindowMs()` | `server_config.cloud_grace_days` | also refuses future-dated writes (`ageMs < 0`) |
| `cloud_grace_tier` satisfies `required` (cascade over `pro` → `pro_cloud` → `pro_cloud_ai`) | `canonical_users` | a higher-lapsed user admits to a lower endpoint; a lower-lapsed user cannot admit to a higher one |

The window length is no longer a hard-coded constant. `graceWindowMs()` in `grace.ts` reads `server_config.cloud_grace_days` via `getInt('cloud_grace_days', DEFAULT_GRACE_DAYS)` at call time — the fallback constant `DEFAULT_GRACE_DAYS = 30` is used only when `server_config` is unreadable. This one dial is what the sweeper, the warning emails, and the client banner all read, so they can never disagree about when a recording is deleted. The tier match uses the **same cascade** as active entitlements — without it, a `pro_cloud_ai`-lapsed user would be denied at a `pro_cloud` endpoint (sync-pull's requirement) and the whole grace policy would be unreachable for them. An empty `required` array admits nothing.

<Note>
Earlier notes describing a `GRACE_WINDOW_MS` constant exported from `gates/grace.ts` are stale — that constant no longer exists. The exported symbol is the async `graceWindowMs()`.
</Note>

## Grace is opt-in and read-only

Grace is enabled per endpoint and only on reads — the lapsed user is rescuing their data, not using the product normally. When admitted via grace, the rate-limit sugar swaps to `gracePeriodBucket` (typically the tighter `sync_download_grace` bucket).

| Endpoint | `allowGracePeriodRead` | `gracePeriodBucket` |
| --- | --- | --- |
| `sync-pull` | true | `sync_download_grace` |
| `sync-audio` (download) | true | `sync_download_grace` |
| `sync-reserve` (write) | false | — |
| `sync-push` / `sync-group-exclude` (write) | false | — |
| `sync-reconcile` / `user-sync-preferences` | false | — |

## Defense in depth

Only the RC webhook writes `cloud_grace_started_at` / `cloud_grace_tier`, filtered to `pro_cloud` / `pro_cloud_ai` lapses, and it clears both columns on renewal / uncancellation / initial purchase / product change so resubscribed users never hit the grace branch. The daily `subscription_lapse_cleanup` sweeper clears rows older than `server_config.cloud_grace_days` (no longer a hard-coded 30), and three CHECK constraints — `canonical_users_cloud_grace_paired`, `canonical_users_cloud_grace_started_at_in_past`, and `canonical_users_cloud_grace_tier_values` — keep the two columns paired, restrict the tier to `pro_cloud` / `pro_cloud_ai`, and forbid future-dated grace timestamps.

The lapse sweeper now HARD-DELETEs the lapsed user's 13 `c_*` tables plus `user_blueprints` (migration `20260824120000_lapse_cloud_reset.sql`) rather than tombstoning — a tombstone would propagate to the user's devices and destroy their local library if they merely stopped paying. It stamps a new, never-cleared `canonical_users.cloud_wiped_at` instead, which `sync-pull` surfaces as a `cloud_reset` status so a returning device re-uploads its content. See [sync-pull](/rollingrecord/backend/sync/pull) and the [cron sweepers](/rollingrecord/backend/database/cron-sweepers) for the full treatment.
