Rate limiting is a standalone callable, not a fixed slot in the chain. `checkRateLimit(bucket, authUserId, isDeveloper, weight)` in `functions/_shared/gates/rate-limit.ts` reads the bucket's config, runs an atomic increment RPC, and returns a gate result the caller pattern-matches. `runGates` offers optional chain sugar around it for the common case; handlers that need per-operation or non-`authUserId` limits call it directly.

## The check

`checkRateLimit(bucket, authUserId, isDeveloper = false, weight = 1)` returns a `RateLimitGateResult` — `{ response }` to return immediately, or `{ response: null, result }` when admitted. Its logic:

- **Dev bypass** — `isDeveloper === true` admits without touching the counter (see [dev bypass scope](/rollingrecord/backend/gates/dev-bypass-scope)).
- **Kill-switch** — a `rate_limit_config` row with `enabled = false` admits without counting, so a bucket can be disabled live without a deploy.
- **Atomic increment** — otherwise it calls the `check_and_increment_rate_limit` RPC and returns admitted or `429 rate_limited`.

Windows are fixed and anchor to the first request after a reset, not to clock-hour boundaries. The optional `weight` (default 1) lets a caller consume more than one slot per call — a weighted increment that would exceed the cap is rejected as a whole, never partially admitted.

## Configuration and fallback

`getBucketConfig(bucket)` reads `rate_limit_config` (`max_requests`, `window_sec`, `enabled`) keyed on `bucket_key`, with a per-isolate `configCache`. On a missing row or DB error it falls back to the in-code `BUCKET_DEFAULTS` map — a `Record<Bucket, { max; windowSec; enabled }>` — with `enabled: true` by default, so a missing row still **enforces** at the code default rather than opening the gate.

Several fallbacks are held at deliberately **half the live ceiling** so a missing-row fallback always errs below the real limit, never above it: `sync_pull` 275 vs live 550, `search` 300 vs 600, `indexing` 150 vs 300, `embedding_cache` 300 vs 600.

## Fail-closed and minimal leakage

An RPC error fails **closed**: `checkRateLimit` returns `500 database_error` with a `bucket` tag rather than admitting — fail-open would melt every user's limit on a single DB hiccup. On a rejection the `429` body from `rateLimitedResponseBody()` is deliberately minimal, `{ error, bucket, reset_at_sec }` — `max`, `count`, `window_sec`, and `retry_after` are all withheld so the ceiling can't be reverse-engineered.

## Near-limit signal

The RPC also returns `near_limit_crossed` (added by migration `20260601000000_rate_limit_near_limit_flag.sql`) — `true` the first time a call crosses 90% of `max` in a window. On that crossing `checkRateLimit` fire-and-forgets a `NearLimitApproach` (`near_limit_approach`, default weight 2) abuse event; a log failure never blocks the primary request. The chain-sugar `abuseEventOnReject` path separately logs an abuse event on a *rejection* for security-sensitive buckets — `RateLimitHit` (`rate_limit_hit`, weight 1) for most, and now `BugReportFlood` (`bug_report_flood`, weight 1) for `bug-report`, which wires `abuseEventOnReject: AbuseEventType.BugReportFlood` so a rejected bug-report burst is recorded on the account's history. Its weight is the floor deliberately — the overwhelmingly likely cause is a user who just found several things wrong and filed them all, so a single hit must never push anyone up the top-offenders list.

## Storage and sweeping

`rate_limit_config` (one row per bucket: `bucket_key`, `max_requests > 0`, `window_sec > 0`, `enabled`, `description`, `updated_at`) is service-role only and edited live via the dashboard to tune ceilings or flip a kill-switch — it replaced per-bucket rows in `server_config` (RR-291). `rate_limit_counters` (`auth_user_id`, `bucket_key`, `window_start_sec`, `count`, PK `(auth_user_id, bucket_key)`) is written **only** by the RPC, which row-locks and uses `ON CONFLICT` for concurrency. Both are defined in `migrations/20260508000000_baseline.sql`. The `prune_rate_limit_counters` `pg_cron` sweeper (`migrations/20260628000000_prune_rate_limit_counters_cron.sql`) hard-deletes counter rows whose window started more than 86400s (24h) ago — 24h is the longest window across all buckets, so such a row is expired under every configuration.

## Chain-sugar vs standalone

| Path | When | Skipped for dev? |
| --- | --- | --- |
| `rateLimit: { bucket }` on the gate config | one limit, keyed on `authUserId`, after auth (resolve-identity, sync-pull / push / reserve / reconcile, sync-audio, user-sync-preferences, recovery-code-generate) | yes (chain sugar not run for dev) |
| standalone `checkRateLimit()` in the handler | per-op / multi-dimensional / non-`authUserId` subject (ai-engine, extract-results, indexing, account-otp, get-user-key, delete-user, support-ops) | yes (the `isDeveloper` arg short-circuits) |

Adding a bucket is a three-part change in one commit: the `Bucket` enum member, a `BUCKET_DEFAULTS` entry, and a `rate_limit_config` seed-row migration.
