---

`supabase/config.toml` declares every Edge Function and disables the platform's built-in Supabase-JWT check on each one, so each function runs its own admission chain instead. It contains **zero** cron scheduling — every recurring job lives in a `pg_cron` `cron.schedule(...)` call inside a migration or in the single `Deno.cron()` in `transcribe-drain`.

## `verify_jwt = false` on every function

`config.toml` (path relative to `supabase/`) holds 32 `[functions.<name>]` blocks, and all 32 set `verify_jwt = false`. Omitting the block is **not** neutral: a function directory with no `[functions.<name>]` entry silently inherits `verify_jwt = true`, which rejects a Clerk-signed Bearer token before `runGates()` ever runs — the exact bug the newly-added `bug-report` and `recovery-code-generate` blocks fix. Disabling the platform check is what lets `runGates()` (`functions/_shared/gates/`) perform the app's own admission chain — App Check, app-version floor, auth, entitlement, rate limit — rather than having Supabase reject a request before any of that code runs. The rationale is stated once in a header comment above `[functions.resolve-identity]`:

> `verify_jwt = false` disables Supabase's built-in JWT verification — we perform our own auth using Firebase App Check (and RevenueCat for user-scoped endpoints), so Supabase's JWT check would block legitimate requests before our code runs.

<Note>
That header comment predates the Clerk auth migration. User-facing endpoints today verify a **Clerk** Bearer JWT (`functions/_shared/gates/jwt.ts`) in addition to App Check; RevenueCat is used for the entitlement fetch, not for JWT verification. The comment names App Check and RevenueCat but not Clerk.
</Note>

<Warning>
The default is the trap. A brand-new `AuthMode.Jwt` function with no `[functions.<name>]` block does **not** run open — it inherits Supabase's built-in `verify_jwt = true` and rejects the Clerk-signed Bearer token before any gate runs, because Supabase cannot validate a Clerk JWT. `recovery-code-generate` did exactly this until this commit declared its block; the `bug-report` block carries the same rationale comment. Every function directory must have an explicit `verify_jwt = false` block — its absence is a silent auth outage, not a safe fallback.
</Warning>

The replacement auth is **not** uniform. Only user-facing endpoints run a Clerk-JWT check. Webhooks and server-to-server callers authenticate with a shared bearer secret or an HMAC signature — the second column below names each one. See [Environment Variables & Secrets](/rollingrecord/backend/operations/env-and-secrets) for the secret values and [Gates](/rollingrecord/backend/gates/run-gates) for the chain itself.

<Note>
One function directory has **no** `config.toml` entry: `functions/transcribe-drain`, which is driven by `Deno.cron` and has no external HTTP surface, so the platform's `verify_jwt` default never affects it. `functions/recovery-code-generate` used to be undeclared too — this commit added its block, because it is an `AuthMode.Jwt` function that had been silently inheriting `verify_jwt = true` and rejecting Clerk tokens. It is, however, superseded: the comment on the `[functions.recovery-code]` block states `recovery-code-generate` "has been superseded by this one and should be deleted from both Supabase branches before next deploy," so the block declaration is a stopgap for a function on its way out, not an endorsement of a supported endpoint.
</Note>

## Local-dev CLI configuration

The rest of `config.toml` is the standard Supabase CLI local-development configuration — the `[api]`, `[db]`, `[auth]`, `[storage]`, and `[edge_runtime]` blocks (ports, `deno_version = 2`, `edge_runtime` `policy = "per_worker"`, storage `file_size_limit = "50MiB"`, all auth providers disabled locally). This is generic CLI boilerplate, not RollingRecord-specific, and governs only the local emulator.

## Scheduling lives in migrations, not config.toml

`config.toml` declares no schedules. Every recurring server job is a `pg_cron` job registered by `cron.schedule('name', '<expr>', $cron$…$cron$)` inside a migration under `migrations/`, plus one `Deno.cron("transcribe-drain", "* * * * *", …)` in `functions/transcribe-drain/index.ts` — the only `Deno.cron` in the codebase. Cron jobs that need to invoke an Edge Function do so with `net.http_post`, carrying a bearer secret read from Vault or a GUC.
