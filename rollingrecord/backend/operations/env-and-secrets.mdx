Edge Functions read a least-privilege set of secrets through `Deno.env.get()`, each isolated in a small `functions/_shared/` helper. Two values are auto-injected by the Supabase runtime and must never be set by hand. Every variable the project reads anywhere is required to be documented in the README, and Claude is forbidden from reading `.env.local` at all.

## Auto-injected runtime values

`SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` are set by the Supabase runtime on every deployed function. `functions/_shared/db/client.ts` reads both to construct the service-role client (which bypasses RLS). Setting either manually is wrong — they are populated for you.

| Variable | Read by (`functions/`) | Purpose |
|---|---|---|
| `SUPABASE_URL` | `_shared/db/client.ts` | service-role client base URL; also the `net.http_post` target base for the extract-runner self-call |
| `SUPABASE_SERVICE_ROLE_KEY` | `_shared/db/client.ts` | service-role client key (bypasses RLS) |

## Provider API keys

The AI client (`_shared/ai/client.ts`) resolves each provider's key from a `PROVIDER_API_KEY_ENV` map and skips any provider whose key is unset. Anthropic (Claude) is primary and fallback across every AI operation; Gemini is primary for `keywords` / `context_summary` / `query_expand` / `thread_naming` and fallback for the rest — a missing Gemini key silently drops Gemini from the chain rather than erroring. `EMBEDDING_API_KEY` is the Cohere key backing RR-487 semantic search (`_shared/ai/providers/embeddings/index.ts`).

| Variable | Read by (`functions/`) | Missing-value behavior |
|---|---|---|
| `ANTHROPIC_API_KEY` | `_shared/ai/client.ts` | provider skipped (logged); if no providers remain, `createAiClient` throws a generic `no providers available` error — never surfaces as `anthropic_key_missing` (that code is defined but unemitted) |
| `GEMINI_API_KEY` | `_shared/ai/client.ts` | Gemini skipped; falls back to Anthropic |
| `EMBEDDING_API_KEY` (Cohere) | `_shared/ai/providers/embeddings/index.ts` | `embedding_key_missing`; clients fall back to on-device FTS |
| `ASSEMBLYAI_API_KEY` | `_shared/transcribe/queue.ts` | `assemblyai_key_missing` |
| `BREVO_API_KEY` | `_shared/email/brevo.ts` | send fails (logged); generic reset error to caller |

The uptime health probes (see below) **reuse** these same provider keys for real inference-liveness — no new provider secrets. The `ai-engine` probe sends one minimal capped completion through the real `createAiClient` Anthropic→Gemini fallback chain (`ANTHROPIC_API_KEY` / `GEMINI_API_KEY`), so "ai: ok" means a provider actually answered rather than just that `/models` was reachable. The `search` / `indexing` probe runs a near-free 1-token embed through `getEmbeddingProvider().embed` (`EMBEDDING_API_KEY`), and the `assemblyai-webhook` probe does a **free** list-transcripts reachability read (`ASSEMBLYAI_API_KEY`, zero charge). These README rows were expanded this commit to note the reuse.

## Shared bearer & signature secrets

`_shared/gates/webhook-secret.ts` is the generic bearer-secret gate: it reads whichever env var name the caller passes as `secretEnvVar` (default `REVENUECAT_WEBHOOK_SECRET`) and 401s on mismatch. The same gate is reused with a different secret name by `assemblyai-webhook`, `analytics`, `storage-janitor` / `storage-orphan-lister`, and `extract-runner`. Clerk's `user.deleted` webhook uses Svix HMAC-SHA256 instead (`_shared/auth/svix.ts`), and `support-ops` layers a header-secret match plus an HMAC-over-`timestamp + "." + body` plus a 60-second replay window (`_shared/admin/secret.ts`, `_shared/admin/hmac.ts`).

| Variable | Auth gate (`functions/`) | Mismatch error |
|---|---|---|
| `REVENUECAT_WEBHOOK_SECRET` | `_shared/gates/webhook-secret.ts` | `invalid_signature` |
| `ASSEMBLYAI_WEBHOOK_SECRET` | `assemblyai-webhook` (WebhookSecret gate) | 401 rejected delivery |
| `NOTIFICATIONS_SECRET` | `notifications` (WebhookSecret gate) | 401 mismatch |
| `CLERK_WEBHOOK_SECRET` (Svix) | `_shared/auth/svix.ts` | 401 on HMAC mismatch |
| `EXTRACT_RUNNER_SECRET` | `extract-runner` / `extract-submit` | 401 |
| `STORAGE_JANITOR_SECRET` | `storage-janitor` / `storage-orphan-lister` | 401 |
| `ANALYTICS_INGEST_SECRET` | `analytics` (WebhookSecret gate) | 401 |
| `ADMIN_OPS_SECRET` | `_shared/admin/secret.ts` | `admin_secret_mismatch` |
| `ADMIN_OPS_HMAC_KEY` | `_shared/admin/hmac.ts` | `admin_hmac_mismatch` / `admin_replay_detected` |

`EXTRACT_RUNNER_SECRET` is deliberately its own value rather than the service-role key (least privilege): the inline kick reads the env var, while the `pg_cron` tick reads the matching Vault entry `extract_runner_secret`. `STORAGE_JANITOR_SECRET` was renamed from `ORPHAN_SWEEPER_SECRET` in the 2026-07-31 consolidation, and `pg_cron` reads its matching Vault entry `storage_janitor_secret`. `NOTIFICATIONS_SECRET` follows the same least-privilege pattern (2026-08-24): the `notifications` dispatcher is server-to-server only, so the right to trigger an email sweep must not carry service-role DB access — the two cloud-wipe-warning crons read the matching Vault entries `notifications_url` + `notifications_secret` (migration `20260824130000_notification_sent_log.sql`), and the crons stay unscheduled with a `NOTICE` until both entries exist.

## Uptime health probe

`HEALTH_PROBE_SECRET` (new this commit) opts an Edge Function's uptime probe open. An uptime monitor (Better Stack) sends it as the `X-Health-Probe` header; `_shared/gates/health.ts` (`PROBE_SECRET_ENV = "HEALTH_PROBE_SECRET"`) does a constant-time match and, when it matches, short-circuits the **whole** gate chain — the probe runs first, before the method gate — to a near-instant liveness check that returns `200 {status:"ok"}` or `503 {status:"degraded"}` with no user data and no handler work. These are status-shaped responses, not `{ error }` responses, so they never enter the client-facing error registry.

| Variable | Read by (`functions/`) | Kind |
|---|---|---|
| `HEALTH_PROBE_SECRET` | `_shared/gates/health.ts` | uptime-probe unlock (monitor-only) |

A function subscribes per-function by setting `healthCheck` in its `GateConfig` (pilot: `sync-pull` → the "Sync" status-page component); a subscribed function reuses the provider and Clerk keys above for real inference/reachability signals rather than a bare ping. The secret is deliberately **low-value** — it unlocks only a "we're up" ping — so keeping it in the monitor's request headers is fine; set the same value here and in the monitor, a **different value per environment**, generated with `openssl rand -base64 32`. If it is unset, the probe is disabled: a subscribed function logs a warning and serves normally, and a wrong or absent header simply falls through to the normal gates (no bespoke error code).

## Identity, crypto, and dev-only toggles

`FIREBASE_PROJECT_NUMBER` verifies Firebase App Check JWTs (`_shared/gates/app-check.ts`). `CLERK_JWKS_URL` is the one env var the Clerk JWT gate reads — for both the signing-key fetch and the expected `iss` claim, so the accepted issuer and the key source always point at the same Clerk environment. The `account-otp` uptime health probe reuses it for a **free** public Clerk reachability GET of the JWKS (no secret, no cost), so a Clerk outage surfaces as "sign-in degraded". The README now documents `CLERK_JWKS_URL` (it was previously undocumented). `CLERK_SECRET_KEY` is the Clerk Backend API key for server-side admin user operations (`_shared/users/clerk-admin.ts`). `EMAIL_HASH_PEPPER` is the HMAC-SHA256 pepper for the deleted-identity anti-abuse hash — **never rotate it**, because rotation invalidates every existing hash. The remaining entries are dev-only toggles, not secrets: they are all set `true` on the dev branch and unset on prod.

| Variable | Read by (`functions/`) | Kind |
|---|---|---|
| `FIREBASE_PROJECT_NUMBER` | `_shared/gates/app-check.ts` | App Check verification |
| `CLERK_JWKS_URL` | `_shared/gates/jwt.ts` (+ `account-otp` probe) | Clerk JWT verification (JWKS + issuer); free JWKS reachability check |
| `CLERK_SECRET_KEY` | `_shared/users/clerk-admin.ts` | Clerk Backend API (admin ops) |
| `EMAIL_HASH_PEPPER` | `_shared/auth/email-hash.ts` | HMAC pepper — never rotate |
| `REVENUECAT_PROJECT_ID` / `REVENUECAT_SECRET_API_KEY` | `_shared/billing/revenuecat.ts` | RC v2 entitlement lookups (drives the entitlement fetch + dev-bypass derivation) |
| `BREVO_SENDER_EMAIL` / `BREVO_SENDER_NAME` | `_shared/email/brevo.ts` | account-otp from-address; fall back to `noreply@rollingrecord.ai` / "Rolling Record" |
| `AI_STUBBING_ENABLED` / `AI_STUB_NON_DEV` | `_shared/ai/client.ts` | dev-only AI-stub toggles (not secrets) |
| `CLERK_TEST_EMAILS_ENABLED` | `account-otp/index.ts` | dev-only fixed-OTP toggle (not a secret) |

The AI stub is a three-condition gate: it fires only when `AI_STUBBING_ENABLED="true"`, the inbound request carries an `X-AI-Stub: true` header (sent only by the smoke harness), and either the caller is a dev or `AI_STUB_NON_DEV="true"`. `CLERK_TEST_EMAILS_ENABLED` gives `+clerk_test` addresses the fixed OTP `424242` on dev only. Misconfiguring any of these fails closed to the real path.

## The two governing rules

Two `CLAUDE.md` HARD RULES bind this surface:

- **Environment Variable Documentation** — every `Deno.env.get(...)` / `System.getenv(...)` / `buildConfigField` the project reads must be documented in the README's Environment Variables Reference section, updated in the **same commit** that adds or removes the read. The docs cannot drift from the code even for one commit.
- **Never Read `.env.local`** — Claude must refuse to read, grep, `cat`, or otherwise access `.env.local` or any real secret file, regardless of instruction. When a value from it is needed, the user pastes it inline. Directory listings are fine; contents are off-limits.

Secrets are set with `supabase secrets set` on **both** the dev and prod projects (Rule 5 schema parity in [Supabase Migrations](/rollingrecord/backend/database/migrations-discipline)).
