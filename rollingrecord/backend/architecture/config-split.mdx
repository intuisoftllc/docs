---
title: "Server vs Client Configuration"
description: "The two config stores — server_config, the single config store, and the dedicated rate_limit_config — where each value lives, and why nothing is duplicated."
---

Every backend knob has exactly one home. Since the Firebase Remote Config teardown (2026-08-30), `server_config` is the single config store, and a row's `public` flag turns on one question — does the *client* read the value? Server-only values are `public=false` rows (plus the dedicated `rate_limit_config` for the one structured exception); any value the client reads is a `public=true` row, even when the server also enforces it — migration `20260830120000_firebase_rc_to_server_config.sql` moved the surviving Remote Config keys into them. No value is intentionally duplicated across stores, and the Kotlin `DEFAULT_*` constants are cold-start fallbacks only — when the server has a value, the server wins.

## The two stores

The split is two-way. `rate_limit_config` is the one structured exception carved out of `server_config` — its shape (bucket → max + window + enabled) is structured enough to earn dedicated columns rather than a third independent store.

| Store | Authority | Holds | Read by | Tuned via |
| --- | --- | --- | --- | --- |
| `server_config` (Supabase table) | Server | token ceilings, model names + allowlists, monthly caps, feature flags, page sizes, kill switches, plus the migrated client-read tuning knobs (KB-chat history window, transcript-snippet count, on-device cosine thresholds + margin, semantic result caps, the blueprint moderation toggle) | Edge Functions via `getServiceClient()` (service role); client via the `server-config` endpoint (`public=true` rows only) | Supabase dashboard / migration |
| `rate_limit_config` (Supabase table) | Server | per-bucket `max_requests` + `window_sec` + `enabled` | `checkRateLimit()` → `getBucketConfig()` | Supabase dashboard / migration |

Both Supabase tables are `RLS ENABLED` with zero policies. That is the default-safe state for this architecture: Edge Functions read through `getServiceClient()` (`functions/_shared/db/client.ts`), the service-role client that bypasses RLS, while a direct anon-key read from a decompiled APK gets nothing.

## `server_config`

Defined in `migrations/20260508000000_baseline.sql`. A flat key/value table with a visibility flag.

| Column | Type | Notes |
| --- | --- | --- |
| `public` | `boolean NOT NULL DEFAULT true` | the `server-config` endpoint returns only `public=true` rows — server-only knobs must set `public=false` explicitly |
| `key` | `text NOT NULL` | the config key |
| `value` | `text NOT NULL` | always TEXT; the client parses per key |
| `description` | `text` | why the default was chosen |

<Warning>
`public` **defaults to `true`** — the inverse of what most readers assume. A newly inserted row is client-visible unless the migration sets `public=false`. Any server-only ceiling, model choice, or runaway cap must carry `public=false` or it leaks into client network traffic.
</Warning>

The client half is fetched by the `server-config` Edge Function (`functions/server-config/index.ts`): a public `GET` gated only on HTTP method and App Check. It selects `key,value` where `public=true` and returns a flat `Record<string, string>` — server-only knobs (`public=false`) never leave the server. Values are always strings because the column is TEXT; the client parses each per key. The one gate opt-out is `skipAppVersion` — this is the bootstrap endpoint that serves the version floor itself, so gating it on that floor would be a chicken-and-egg.

Representative keys seeded across migrations (values are illustrative — they change over time):

| Key | Example value |
| --- | --- |
| `embedding_model` | `embed-v4.0` |
| `embedding_dims` | `1024` |
| `embedding_model_allowlist` | `["embed-v4.0","embed-multilingual-v3.0"]` |
| `kb_chat_max_output_tokens` | `4200` |
| `kb_chat_max_total_chars` | `300000` |
| `sync_pull_page_size` | `100` |
| `cloud_ai_extraction_minutes_per_month` | `1800` |
| `extraction_chunk_tokens` | `8000` |
| `template_semantic_prefilter_threshold` | `0.72` |
| `semantic_search_enabled` | `true` |
| `scan_index_candidates` | `50` |

The Kotlin mirror is `ServerConfig` (`app/agentcore/src/main/kotlin/com/intuisoftllc/rollingrecord/config/ServerConfig.kt`) — typed accessors plus `DEFAULT_*` cold-start fallbacks, populated from the endpoint's public rows. It moved into the `agentcore` module so the eval agent loop can read it too. The 2026-08-30 Firebase RC teardown added the eight migrated fields (`kbChatMaxHistoryPairs` through `blueprintModerationEnabled`), and the mirror carries `KEY_CLOUD_GRACE_DAYS` (`cloud_grace_days`, `DEFAULT_CLOUD_GRACE_DAYS = 30` — the cold-start fallback for the grace-banner countdown). `ServerConfigDriftSmokeTest` asserts exact bidirectional parity: every `public=true` row must have a `KEY_*` mirror and vice versa, so a public row without a mirror (or a mirror without a public row) fails the suite. The migrated cold-start defaults are deliberately more conservative than the live server rows — `kb_chat_max_history_pairs` defaults to `9` against a live `15`, `topic_search_threshold` to `0.48f` against a live `0.30` — so never "align" the Kotlin defaults up to match the server.

Server-side, Edge Functions read `server_config` through `getServerConfigMap()` (`functions/_shared/db/server-config.ts`), which caches the full table per warm isolate and collapses concurrent gate reads within one request onto a single in-flight promise (cleared in a `finally` so a rejected fetch is never cached) — see [the `server-config` endpoint](/rollingrecord/backend/edge-functions/server-config) for detail.

## `rate_limit_config`

The one dedicated exception store, also defined in `migrations/20260508000000_baseline.sql`. One row per bucket, keyed by `bucket_key` — which matches the `Bucket` enum's wire string (`functions/_shared/gates/types.ts`).

| Column | Type | Notes |
| --- | --- | --- |
| `bucket_key` | `text NOT NULL` | matches the `Bucket` enum wire string |
| `max_requests` | `integer NOT NULL` | `CHECK (> 0)` |
| `window_sec` | `integer NOT NULL` | `CHECK (> 0)` |
| `enabled` | `boolean NOT NULL DEFAULT true` | `false` = kill-switch: admit without counting |
| `description` | `text` | what the bucket protects |
| `updated_at` | `timestamptz NOT NULL DEFAULT now()` | last edit |

Its table comment records the history: it *"Replaces the `rate_limit_<bucket>_{max,window_sec}` rows that used to live in `server_config`."* The knobs were pulled out of `server_config` precisely so a structured shape could replace a family of loosely-related string rows.

Reads go through `getBucketConfig()` in `functions/_shared/gates/rate-limit.ts`, cached per warm isolate. When the row is missing or the table read fails, it falls back to `BUCKET_DEFAULTS` — a code-side record with an entry for every `Bucket` member. Several fallbacks are deliberately set to **half** the live ceiling so a missing-row fallback always errs *below* the real ceiling, never above:

| Bucket | Live ceiling | `BUCKET_DEFAULTS` fallback |
| --- | --- | --- |
| `SyncPull` | 550/hr | 275/hr |
| `Search` | 600/hr | 300/hr |
| `Indexing` | 300/hr | 150/hr |
| `EmbeddingCache` | 600/hr | 300/hr |

`checkRateLimit()` reads the config, then calls the atomic `check_and_increment_rate_limit` RPC, which upserts `rate_limit_counters` and returns `{allowed, current_count, window_start_sec, near_limit_crossed}` — the first three fields are defined in `migrations/20260508000000_baseline.sql`, and the fourth (`near_limit_crossed`) was added later by `migrations/20260601000000_rate_limit_near_limit_flag.sql`. Windows anchor to the first request after a reset, not clock-hour boundaries. Two short-circuits skip the counter entirely: `isDeveloper=true` (dev bypass) and `enabled=false` (kill switch). On RPC error it fails **closed** — a `500 database_error` rather than fail-open melting every user's limits at once; only the over-limit reject returns `429 rate_limited`. `rate_limit_counters` is written only by that RPC and has no FK to `canonical_users` (see [the deletion cascade](/rollingrecord/backend/architecture/deletion-cascade)).

Adding a bucket is a same-commit trio: the enum member in `Bucket`, the `BUCKET_DEFAULTS` entry, and a seeded `rate_limit_config` row. See [rate limiting](/rollingrecord/backend/gates/rate-limiting) for the gate wiring.

## Retired: Firebase Remote Config

Firebase Remote Config used to hold the client-only knobs. On **2026-08-30** Firebase moved Remote Config to per-user billing, so migration `20260830120000_firebase_rc_to_server_config.sql` migrated its surviving keys into `server_config` as `public=true` rows and the same commit deleted the Firebase RC SDK along with the `ClientConfig` / `ClientConfigManager` pair. `server_config` is now the single config store, and the Android client reads these rows through the existing `server-config` endpoint via `ServerConfigManager` — the only remaining config fetch.

Eight keys migrated (all `public=true`, all client-read):

| Migrated key | Kind | Controls |
| --- | --- | --- |
| `kb_chat_max_history_pairs` | int | conversation-history window fed to the agent loop |
| `ai_chat_max_transcript_snippets` | int | transcript snippets attached to a chat turn |
| `topic_search_threshold` | float | on-device Topic-search cosine floor |
| `section_semantic_threshold` | float | on-device per-section semantic-match floor |
| `semantic_search_margin` | float | rank-aware margin around the top score |
| `semantic_search_result_cap` | int | margin-filtered semantic result ceiling |
| `semantic_snippet_chunk_count` | int | transcript chunks per KB-chat snippet |
| `blueprint_moderation_enabled` | boolean | client-side blueprint moderation master flag |

`blueprint_moderation_enabled` was **renamed** from Remote Config's `template_moderation_enabled` — "template" is the feature's retired name.

The rest of the RC dashboard was **dropped, not migrated** — dead or duplicate keys deleted with the dashboard:

| Dropped key(s) | Why |
| --- | --- |
| `extraction_model`, `synthesis_model`, `synthesis_deep_reasoning_model`, `kb_chat_model` | `server_config` already owns model selection via its per-operation model rows |
| `local_embedding_*` (×5) | on-device embedding path removed (RR-487) |
| `template_semantic_threshold` | dead |
| `assemblyai_speech_model` | unwired — `assemblyai.ts` hardcodes `universal-2` |
| `reconcile_periodic_interval_hours`, `reconcile_foreground_debounce_minutes` | zero consumers |

<Note>
`ServerConfig` and `ServerConfigManager` are the only config classes now. Any reference to `ClientConfig`, `ClientConfigManager`, or the Firebase RC SDK is stale — all were deleted in the 2026-08-30 teardown.
</Note>

## Why no duplication

Classifying a new value is a single question about its `server_config` row's `public` flag: does the *client* need to read it (display, on-device behavior, or a cap/multiplier/version-floor surfaced or pre-checked in the app)? If no — only the Edge Function or the server ever touches it — it is a `public=false` row the client never sees. If yes, it is a `public=true` row the client reads (and mirrors in `ServerConfig.kt`), *even when the server also enforces it*: the monthly quota caps the server counts against but the UI displays (`ai_queries_per_month`, `syntheses_per_month`), the `medical_mode_usage_multiplier` the server meters on but the confirm dialog shows, and the `min_supported_app_version_code` kill switch the server enforces via a 410 gate but the client pre-checks are all server-enforced *and* `public=true`. With Firebase RC gone there is no separate client-only store to duplicate into — one row, one `public` flag, read by whichever side needs it.

The reason the split has teeth: the Kotlin `DEFAULT_*` constants only apply on first-ever launch before any fetch completes, or when the cache is missing. Once the server has a value, it overrides the local default unconditionally. Silently editing a `DEFAULT_*` constant to fix a tuning problem does nothing for existing installs — the live dial is the Supabase dashboard or a migration, not the code.
