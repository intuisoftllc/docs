Three cooperating anti-abuse primitives sit behind the account surface: an append-only behavioral-signal log, a deletion-to-resignup usage carryover that stops delete-then-re-register from resetting monthly caps, and the account-freeze gate that turns a flagged account away before it can spend quota.

## Abuse-event log

`l_user_abuse_event` is an append-only log written fire-and-forget by `logAbuseEvent()` in `functions/_shared/users/abuse-log.ts` on "should-have-known-better" server failures. Callers invoke it without `await` and attach a `.catch(...)`, so a log-write failure never cascades into a user-visible error — the system would rather lose a signal row than deny a legitimate request. Each row carries a severity `weight`, plus `source_ip` (`cf-connecting-ip` / `x-forwarded-for`), `user_agent`, `app_version`, and `device_hash` for fingerprint attribution.

The table has **no FK** to `canonical_users` and `auth_user_id` is nullable (pre-signup events). As a long-retention `l_*` forensics log (3-year retention, swept by `prune_log_tables`) it is deliberately **not** in `delete-user`'s `TABLES_TO_WIPE` — the log survives user deletion so top-offenders and dispute forensics still have the signal months later.

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `uuid` | `gen_random_uuid()` |
| `auth_user_id` | `text` (nullable) | NULL for pre-signup events |
| `event_type` | `text NOT NULL` | free-form, no CHECK |
| `weight` | `integer NOT NULL DEFAULT 1` | severity |
| `details_json` | `jsonb` | event payload |
| `source_ip` / `user_agent` / `app_version` | `text` | extracted from the Request |
| `device_hash` | `text` | per-device fingerprint (RR-340) |
| `created_at` | `timestamptz NOT NULL DEFAULT now()` | |

### Event types and weights

`AbuseEventType` and `DEFAULT_WEIGHTS` centralize the known slugs. The `event_type` column is free-form TEXT, so a new slug needs no migration — the constant set just keeps callers honest.

| Constant | Slug | Default weight |
| --- | --- | --- |
| `SizeMismatch` | `size_mismatch` | 5 |
| `InvalidSizeBytes` | `invalid_size_bytes` | 3 |
| `JwtInvalid` | `jwt_invalid` | 2 |
| `AppCheckFailed` | `app_check_failed` | 3 |
| `AdminHmacMismatch` | `admin_hmac_mismatch` | 10 |
| `AdminSecretMismatch` | `admin_secret_mismatch` | 10 |
| `AdminPermissionDenied` | `admin_permission_denied` | 1 |
| `RateLimitHit` | `rate_limit_hit` | 1 |
| `NearLimitApproach` | `near_limit_approach` | 2 |
| `BugReportFlood` | `bug_report_flood` | 1 |
| `FrozenUserClerkDeletion` | `frozen_user_clerk_deletion` | 10 |

`bug_report_flood` sits at the **floor** weight of 1: a caller who hit the bug-report submission ceiling (10/hour) is a soft signal that — by design — must never on its own push an account up the top-offenders list. The likely explanation is a user who found several things wrong and filed them all, so it is useful only in aggregate (the same account tripping it every hour for a day is worth a look; one hit is worth nothing). `frozen_user_clerk_deletion` sits at the **ceiling** weight of 10: a FROZEN account (`canonical_users.frozen_at` set) that was deleted out-of-band via Clerk, logged as a deliberate evidence-destruction signal (see [Account-freeze gate](#account-freeze-gate) below).

### Admin reads

Two helpers back support-ops operations, both gated by `can_read_user_audit`:

- `getUserAbuseSignals()` — recent events for one user, newest first (limit default 50, cap 500, optional `since`).
- `getAbuseTopOffenders()` — ranks callers by `SUM(weight)` DESC over a window (default 24h). The aggregation runs in **application code** (an in-memory group-by over a 20k-row scan cap), not a SQL RPC or view, to keep the surface additive. It returns `totalWeight`, `eventCount`, `distinctTypes`, and `lastSeenAt`.

<Note>
Caller-supplied strings written to Postgres `TEXT` columns pass through the pure sanitizer `sanitizeDbText()` / `sanitizeDbTextOrNull()` (`functions/_shared/text/db-text.ts`) at the write boundary — it strips U+0000 and the rest of the C0 controls (keeping `\t` / `\n`), removes bidi overrides, and normalizes CRLF to LF, so an unstorable NUL can't fail an insert and a bidi trick can't make a stored value read one way in the console and another in the row. On the admin-audit surface it guards `l_admin_audit.ticket_ref` (sanitized, then sliced to 64 chars in support-ops). See [support-ops operations](/rollingrecord/backend/support-ops/operations-catalog) for that field.
</Note>

## Re-signup carryover

`l_deleted_identity` snapshots a deleted user's current-period usage counters so a returning user can't wipe their monthly caps by deleting and re-registering. It is keyed by `(email_hash, period)` — a salted `HMAC(email)` plus the `YYYY-MM` period, **not** `auth_user_id`, because a re-signup gets a net-new `auth_user_id`. `functions/_shared/users/deleted-identity-history.ts` owns both sides of the protocol.

| Step | Caller | Effect |
| --- | --- | --- |
| delete | `delete-user` (`wipeUser` step) | `snapshotUsageForDeletion()` reads the current-period `usage` row and inserts counters into `l_deleted_identity` before `usage` is hard-deleted |
| re-signup | `resolve-identity` | `carryForwardOnResignup()` MAX-merges the counters into the new user's `usage` row, then deletes the history row |
| no match | `resolve-identity` | `no_history` — the normal fresh-signup path |

Both writes take the MAX of any existing and incoming values (`upsertWithMax()` on a snapshot PK conflict, `Math.max` per column on carryover) so anti-abuse always keeps the worst-case cap usage. `carryForwardOnResignup()` returns `no_history`, `carried_forward`, or `failed`; the snapshot is best-effort and never blocks deletion.

`USAGE_COUNTER_COLUMNS` is the authoritative runtime list of columns that participate: `transcription_ms`, `ai_queries`, `syntheses`, `deep_reasoning_syntheses`, `keywords_count`, `context_summary_count`, `thread_naming_count`, `template_moderation_count`, `save_user_template_count`, `list_user_templates_count`, and `delete_user_template_count`. Any new usage counter must be added both here and to the `l_deleted_identity` schema, or it silently drops out of the snapshot/carryover.

## Account-freeze gate

`runAccountFrozenGate()` (`functions/_shared/gates/account-frozen.ts`, RR-310) is a generic soft-block checked on every JWT-authenticated Edge Function. It reads `canonical_users.frozen_at` / `frozen_reason` **after** JWT and **before** the rate-limit step, so a frozen account's rejections cost no quota. A non-null `frozen_at` returns `403 account_frozen` with the `reason` in the body.

- **Fails open** — a DB read error or a missing row admits the request rather than locking every user out on a transient glitch.
- **No bypass** — there is no `skipFrozenCheck` option and no admin / super-admin exemption; freeze that could self-lift is not freeze.
- **Not abuse-logged for the ordinary turn-away** — a frozen account being rejected on a normal request is the freeze working, not a signal worth recording. One frozen path is different: [`clerk-webhook`](/rollingrecord/backend/edge-functions/webhooks)'s `user.deleted` handler QUARANTINES a frozen user rather than wiping — no data touched, a `200` so Svix stops retrying — and logs the ceiling-weight `frozen_user_clerk_deletion` event. Reaching an out-of-band deletion path while frozen is the recorded signal, not the ordinary turn-away.

`frozen_at` (`TIMESTAMPTZ`) and `frozen_reason` (`TEXT`) live on `canonical_users`, with a partial index `idx_canonical_users_frozen WHERE frozen_at IS NOT NULL`. They are set and cleared by the support-ops `freeze_user_account` / unfreeze operations. See [Account-Freeze Gate](/rollingrecord/backend/gates/account-frozen) for the full gate semantics.

<Note>
The `account_frozen_attempt` abuse event was **retired**. `runAccountFrozenGate` no longer logs frozen rejections, `AbuseEventType` no longer has the member, and `migrations/20260812000000_drop_account_frozen_attempt_events.sql` purged the already-logged rows — high-volume, low-signal bloat that skewed the top-offenders aggregate.
</Note>
