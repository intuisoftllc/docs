title: "Recovery Codes"
description: "The two-op generate/acknowledge recovery-code flow, its one-per-account rule, and the superseded one-shot generator it replaced."
---

A recovery code is a 16-digit (four groups of four) per-user secondary credential, generated **once** per account and stored only as an argon2id hash in `canonical_users.recovery_code_hash`. `functions/recovery-code/index.ts` (RR-315 revised) is a two-operation flow — `generate` then `acknowledge` — that guarantees the client actually received the plaintext before it is permanently hashed. It supersedes the older one-shot `functions/recovery-code-generate/index.ts`.

## Operations

Both operations run a JWT gate chain and read `recovery_code_hash` + `recovery_code_pending` off `canonical_users`. Rate limits are applied per-operation so each bucket tunes independently. The `runGates()` config also registers `dbHealthCheck("recovery-code")`, so the two-op `/recovery-code` hosts an **Account & Sign-in** uptime probe: a request carrying a valid `X-Health-Probe` header short-circuits before the handler to a read-only DB-liveness read. The probe is on the two-op `recovery-code` only — the legacy `recovery-code-generate` has none.

| Operation | Success | Errors |
| --- | --- | --- |
| `generate` (fresh) | `200 { recovery_code }` (display form) | `database_error` |
| `generate` (pending already set) | `200` same `{ recovery_code }` — idempotent retry | — |
| `generate` (hash already set) | — | `recovery_code_already_exists` (409) |
| `acknowledge` (match) | `200 { acknowledged: true }`, writes hash + clears pending | — |
| `acknowledge` (mismatch) | — | `recovery_code_mismatch` (422) |
| `acknowledge` (no pending) | — | `recovery_code_not_pending` (409) |
| either (bad operation) | — | `recovery_code_invalid_operation` (400) |
| either (no `canonical_users` row) | — | `not_found` (404) |

`not_found` means `resolve-identity` hasn't created the caller's `canonical_users` row yet (sign-up just landed); the client retries once the row exists.

Both operations also **fail closed** before touching the row: if `RECOVERY_CODE_PENDING_KEY` is unset or malformed, `loadPendingKey()` returns null and the function returns `server_misconfiguration` (500) rather than fall back to storing plaintext. On `acknowledge`, a pending ciphertext that exists but will not decrypt (key rotated, or not bound to this caller) returns `internal_error` (500) — deliberately *not* `recovery_code_not_pending`, because the client treats `not_pending` as "already acknowledged, proceed" and would wrongly believe a code was saved.

## The delivery guarantee

`generate` seals the display-formatted code as AES-256-GCM ciphertext into `recovery_code_pending_ct` / `recovery_code_pending_iv` (guarded by atomic `IS NULL` `WHERE` clauses against races) and returns the plaintext to the caller. If the first response is lost to a network error, a retry decrypts and returns the **same** stored code — no new code is minted. `acknowledge` proves delivery: the client echoes back the exact code, the server decrypts the pending ciphertext and compares, and on a match hashes the code with argon2id into `recovery_code_hash` and clears every pending column in the same update. Only after acknowledgment is the code replaced by the hash.

The pending code is never stored as plaintext. During the window between generate and acknowledge — which an abandoned onboarding can leave open indefinitely — the code sits only as owner-bound ciphertext, keyed by a secret that lives outside the database. See [Encryption at rest](#encryption-at-rest) below.

## Encryption at rest

`functions/_shared/auth/recovery_code_pending.ts` holds the at-rest crypto for the pending code. It reuses the DEK-layer helpers from `functions/_shared/crypto/envelope.ts` (`encryptWithDek` / `decryptWithDek` — plain AES-256-GCM, 12-byte random IV, no AAD) with a dedicated standalone key rather than the KEK/Vault wrapping layer:

| Symbol | Role |
| --- | --- |
| `sealPendingCode(key, authUserId, displayCode)` | Encrypts the plaintext `<authUserId>:<displayCode>`; fresh random IV per call; returns `{ ct, iv }` for the `_ct` / `_iv` columns |
| `openPendingCode(key, authUserId, ct, iv)` | Decrypts and **verifies the owner prefix**; throws on a bad auth tag or a mismatched owner, which callers treat as "no usable pending code" |
| `decodePendingKey(base64)` | Pure base64 decode + 32-byte size assertion (unit-testable) |
| `loadPendingKey()` | Reads `RECOVERY_CODE_PENDING_KEY` from the environment; returns `null` when unset or malformed so the caller fails closed |

**Why a dedicated key, not Vault.** The threat this closes is a reader of the database itself — SQL editor / dashboard, a leaked service-role key, or the daily off-platform backups — copying a pending code that becomes a permanent support identity proof once acknowledged. A Vault secret is readable through SQL by anyone with DB-admin access, which is exactly that reader, so the key lives in the `RECOVERY_CODE_PENDING_KEY` Edge Function secret (outside the DB). A DB read therefore yields ciphertext only. The secret is 32 random bytes, base64 (`openssl rand -base64 32`), set on both dev and prod; rotating it only strands codes pending at that exact moment, and the next `generate` treats an unopenable ciphertext as absent and mints a fresh code.

**Owner binding.** The sealed plaintext is `<auth_user_id>:<display code>`, and `openPendingCode` rejects any ciphertext whose prefix is not the active caller. Someone with DB *write* access therefore cannot copy their own pending ciphertext onto another user's row to plant a code they already know.

### Legacy plaintext migration

`canonical_users.recovery_code_pending` (the old `TEXT` plaintext column) is intentionally left in place. The function's `readPending()` resolves a row's pending code to one of four states — `none`, `undecryptable`, `encrypted`, or `legacy` — and on `generate` a `legacy` value is re-sealed into the encrypted pair (and the plaintext nulled) on first touch, returning the **same** code so a user mid-onboarding is never handed a different one:

```
// [BACKFILL] Encrypts a code that was left pending as PLAINTEXT in the
// legacy `recovery_code_pending` column before encryption shipped, and
// nulls the plaintext. Returns the SAME code ... Remove this branch
// once no row has a non-NULL recovery_code_pending and the column has
// been dropped.
```

Dropping the legacy column is a separate, destructive migration (Rule 9 — written confirmation required); until then the `legacy` branch and the column read in `USER_COLUMNS` stay.

## Code generation & hashing

`functions/_shared/auth/recovery_code.ts` holds the pure helpers (no network, DB, or env):

| Symbol | Role |
| --- | --- |
| `generateRecoveryCode()` | 16 digits via uniform sampling (rejects bytes `>= 250` to avoid `byte % 10` bias); returns `{ display, raw }` |
| `hashRecoveryCode()` | argon2id via `npm:hash-wasm@4.11.0` |
| `verifyRecoveryCode()` | argon2id verify — backs the support-ops validate op |
| `normalizeRecoveryCode()` | strips whitespace, asserts exactly 16 digits (throws otherwise) |
| `formatRecoveryCode()` | regroups raw digits into four groups of four |

`DEFAULT_HASH_OPTIONS` has four fields: 3 iterations, 64 MiB memory (`memorySize` 65536), parallelism 1, and `hashLength` 32. The `hashRecoveryCode()` `argon2id()` call passes `outputType` `"encoded"` as a separate argument, not part of that constant. The encoded string embeds the algorithm parameters and salt inline (`$argon2id$v=19$m=65536,t=3,p=1$...`), which is why `recovery_code_hash` is stored as `TEXT`, not `BYTEA` — `argon2Verify` reads params and salt back out of the string, so no separate salt column is needed.

## The superseded one-shot

`functions/recovery-code-generate/index.ts` is the original one-shot generator: it generates a code, hashes it with argon2id immediately, stores only the hash via an atomic `UPDATE ... WHERE recovery_code_hash IS NULL`, and returns the plaintext exactly once. It never stores plaintext. It is still deployed but **legacy** — a dropped network response under this design lost the code permanently, which is precisely the bug the two-op `/recovery-code` fixes. Both functions refuse to re-issue once a hash exists, and both draw on the same `RecoveryCodeGenerate` bucket.

The legacy function previously had **no** `[functions.recovery-code-generate]` block in `supabase/config.toml`, so it silently inherited Supabase's built-in `verify_jwt = true` — which rejects the Clerk-signed JWT before `runGates()` ever runs, a latent break on the still-deployed endpoint. A `[functions.recovery-code-generate]` block with `verify_jwt = false` now makes the function's own `runGates()` Clerk-JWT check authoritative, matching every other `AuthMode.Jwt` function. The legacy function itself carries no code change — only the config declaration was added.

## One code per account

Once `recovery_code_hash` is set, neither function will issue another — the user is expected to keep the code they were given at first sign-up. The only replacement path is the support-ops Tier-3 `regenerate_recovery_code` escape hatch; the user cannot rotate the code themselves.

The complement holds too: an account whose `recovery_code_hash` is still NULL is not stranded. The server surfaces that state to the client as `has_recovery_code` on the [get-user-key](/rollingrecord/backend/edge-functions/get-user-key) response, which the client already fetches every session — so an account that missed the sign-up window (onboarding skipped, a crash mid-flow, a second device) gets re-prompted to run `generate` / `acknowledge` on a later session instead of silently never having a code. The server, not a device-local flag, is the authority on whether the code exists.

<Note>
Neither `/recovery-code` nor `/recovery-code-generate` reads, wraps, or rewraps the DEK. They only manage `recovery_code_hash` / `recovery_code_pending`. Any DEK-rewrap-on-recovery behavior lives in the support-ops account-recovery operations and [key management](/rollingrecord/backend/storage/key-management), not here.
</Note>

## Rate limits

| Bucket | Max | Window | Notes |
| --- | --- | --- | --- |
| `recovery_code_generate` | 60 | 3600s | shared by the legacy one-shot and the two-op `generate` |
| `recovery_code_acknowledge` | 60 | 3600s | extra headroom for network-error retries |

Legitimate callers hit each bucket once in the account lifetime; the buckets exist only to throttle stolen-JWT probing.
