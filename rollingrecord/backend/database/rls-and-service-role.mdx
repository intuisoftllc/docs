---
title: "RLS & Service-Role Model"
description: "Why every table enables RLS with no policies, and how Edge Functions reach the data while direct callers get nothing."
---

Every table runs with Row Level Security enabled and zero policies — the default-safe state for this architecture. Edge Functions reach data through a service-role client that bypasses RLS; a direct anon-key or user-JWT caller resolves to zero rows. There is no client-direct table access by design — every read and write routes through an Edge Function behind the gate chain.

## Who can reach a row

| Caller | Key | RLS effect |
| --- | --- | --- |
| Edge Function | service role (`SUPABASE_SERVICE_ROLE_KEY`) | Bypasses RLS — full access |
| Direct anon caller | anon key (extractable from the APK) | RLS on + no policies → zero rows |
| Direct authenticated caller | user JWT | RLS on + no policies → zero rows (no client-direct access by design) |

Because RLS is enabled with no permissive policy, the gate chain — not RLS policies — is the actual authorization layer. `runGates()` (`supabase/functions/_shared/gates/index.ts`) / `GateConfig` (`supabase/functions/_shared/gates/types.ts`) fronts every Edge Function with a fixed admission order (method → App Check → app-version → JWT → entitlement fetch → entitlement check → optional rate-limit).

## The service-role client

`getServiceClient()` (`supabase/functions/_shared/db/client.ts`) is the single service-role client factory, with supabase-js pinned at `2.45.4`. It reads the auto-injected `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY`, disables session persistence and auto-refresh, and bypasses RLS. Its header comment is explicit: never expose it to client-facing code.

## RLS on every table, no policies

The baseline (`supabase/migrations/20260508000000_baseline.sql`) issues `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` for every table and defines no `CREATE POLICY` anywhere. The tables also carry `GRANT ALL ... TO anon`, `TO authenticated`, and `TO service_role`, but with RLS enabled and no permissive policy those anon/authenticated grants resolve to nothing — only the service role reaches rows. The grant is present; the policy that would make it usable is deliberately absent.

## Function EXECUTE grants (SECURITY DEFINER)

RLS protects tables, not functions — and a `SECURITY DEFINER` function owned by `postgres` (which has `rolbypassrls`) runs with full privileges and ignores RLS entirely, so a caller who can `EXECUTE` one bypasses the closed-RLS model completely. Supabase's baseline ships `ALTER DEFAULT PRIVILEGES ... GRANT ALL ON FUNCTIONS TO anon` and `TO authenticated`, so every function created in `public` after the baseline shipped world-callable. PostgREST exposes public-schema functions returning `void`/`jsonb` as `POST /rest/v1/rpc/<name>`, and the anon key is compiled into the APK — so "granted to anon" means "callable by anyone with the app."

`REVOKE ALL ... FROM PUBLIC` is **not** sufficient. The `ALTER DEFAULT PRIVILEGES` grants `TO anon` and `TO authenticated` are separate ACL entries that a `PUBLIC`-only revoke leaves intact — `enforce_user_blueprints_quota` proved this, doing the `PUBLIC`-only revoke in its own migration yet still showing an `anon` grant in production. The fix (`supabase/migrations/20260828120000_revoke_public_execute_on_secdef_functions.sql`) revokes `EXECUTE` from all three — `PUBLIC`, `anon`, **and** `authenticated` — then `GRANT`s to `service_role`. Copy that name-all-three shape for every new `SECURITY DEFINER` function.

That migration locked down 16 `SECURITY DEFINER` functions. The one that mattered is `support_ops_restore_tombstones(p_auth_user_id, p_group, p_grace_days)` — an admin cross-user un-delete that took an arbitrary user id and was reachable **unauthenticated** with no authorization in front of it. The rest (prune/purge sweepers, trigger functions PostgREST cannot expose, `rls_auto_enable`) were low-impact and revoked only so the privilege state is uniform and "is this one safe?" stops being a per-function judgment call. Legitimate callers keep working: `pg_cron` runs these as the owner `postgres`, and Edge Functions call them as `service_role`.

## Deletion integrity is what makes closed-RLS safe

A closed-RLS model is only complete if account deletion still reaches every row. That guarantee comes from `auth_user_id` FK + CASCADE, not from RLS. Every user-data table carries `auth_user_id TEXT NOT NULL` with `fk_<table>_user REFERENCES canonical_users(auth_user_id) ON DELETE CASCADE`, so deleting one `canonical_users` row cascades the whole account. Cross-row FKs use CASCADE (session → recording) or SET NULL (category).

A few tables deliberately have **no** FK to `canonical_users` and are cleaned explicitly by `wipeUser()` (`supabase/functions/_shared/users/wipe.ts`) instead of by CASCADE:

| No-FK table | Why it floats |
| --- | --- |
| `usage` | Anti-abuse: counters survive a deletion race to be snapshotted first |
| `query_sessions` | Ephemeral, often written before the caller's `canonical_users` row exists |
| `l_credit_log` | Financial-audit survival across deletion races |
| `user_credits` | Bundle / admin-grant balances survive long enough for an explicit wipe |

Storage objects never CASCADE either, so `wipeUser`'s `BUCKETS_TO_WIPE` removes those separately. The model is therefore not "CASCADE handles everything" — it is "CASCADE plus an explicit wipe list for the floating tables and buckets."
