title: "server_config & rate_limit_config"
description: "The two server-authoritative config tables, their schemas, the seed-row pattern, and how Edge Functions read them."
---

Server-authoritative config lives in two tables. `server_config` is a flat key/value store read through typed accessors; `rate_limit_config` is a dedicated structured table — one row per rate-limit bucket — read through `checkRateLimit()`. Both are reached only by the service-role client, and both are seeded idempotently from migrations.

## `server_config`

A flat key/value/description table with a `public` flag. Public rows are readable by the client for display; the value is always stored as `TEXT` and parsed by the reader.

| Column | Type | Purpose |
| --- | --- | --- |
| `public` | `BOOLEAN DEFAULT true` | Whether the client may read this row for display |
| `key` | `TEXT` (PK) | The config key |
| `value` | `TEXT` | Stored as text, parsed by the reader |
| `description` | `TEXT` | What it controls and why the default was chosen |

RLS is enabled with no policies. Edge Functions read it through `getServerConfigMap()` and four typed getters in `supabase/functions/_shared/db/server-config.ts`:

| Accessor | Parse | Use |
| --- | --- | --- |
| `getInt(key, fallback)` | `parseInt` | Integer ceilings, caps |
| `getNumber(key, fallback)` | `parseFloat` | Fractional values (e.g. usage multipliers) |
| `getBool(key, fallback)` | `raw === "true"` | Feature flags, kill switches |
| `getString(key, fallback)` | raw | Model names, string config |

`getServerConfigMap()` fetches the whole table once and caches it for 5 minutes per warm instance, failing loud (throwing) on a DB error so a config read can't silently return stale zeros. Concurrent callers within one request share a single query: it also holds the in-flight fetch **promise** (`inFlight` in `supabase/functions/_shared/db/server-config.ts`), so gate callers that all arrive before the first fetch resolves join it instead of each firing their own — production logs had shown six full-table `server_config` reads inside 3ms on one request while the 5-minute cache was working exactly as written. The promise is cleared in a `finally`, so a rejected fetch is never cached and the next caller retries against the DB. As of RR-164, `server_config` no longer exposes an enforced `allowed_models` allowlist — `getAllowedModels()` was removed and each operation reads its own model key directly (e.g. `extraction_model`, `kb_query_model`).

### The single config store

`server_config` is the single server-authoritative config store since Firebase Remote Config was retired (Firebase moved Remote Config to per-user billing). `supabase/migrations/20260830120000_firebase_rc_to_server_config.sql` folds RC's surviving client-read knobs into eight new `public = true` rows, each read by the Android client through `ServerConfigManager` and mirrored by a `KEY_*` constant in `ServerConfig.kt` — `ServerConfigDriftSmokeTest` enforces exact parity between `public = true` rows and those mirrors.

| Key | Value | Client read |
| --- | --- | --- |
| `kb_chat_max_history_pairs` | `15` | Prior Q/A pairs included in KB-chat history sent to Claude |
| `ai_chat_max_transcript_snippets` | `6` | Max recordings the AI retrieves transcript snippets from per turn |
| `topic_search_threshold` | `0.30` | Min cosine-similarity floor for Topic search |
| `section_semantic_threshold` | `0.32` | Min cosine-similarity floor for per-section KB search |
| `semantic_search_margin` | `0.02` | Rank-aware margin: results within this of the top score are kept |
| `semantic_search_result_cap` | `8` | Max results from margin-filtered semantic search |
| `semantic_snippet_chunk_count` | `3` | Transcript chunks the snippet tool returns per recording |
| `blueprint_moderation_enabled` | `true` | Master enable for the on-device blueprint content-moderation pipeline |

The same migration **renames** `template_moderation_enabled` → `blueprint_moderation_enabled` (`template` is the feature's retired name). A ninth `public = true` row, `cloud_grace_days` (`30`, `supabase/migrations/20260825120000_cloud_grace_window.sql`), is the single dial for the cloud-data retention window — read by `subscription_lapse_cleanup()`, by the 7-day / 1-day `cloud_wipe_warning` emails, and by the client's grace-banner countdown — replacing a value formerly hard-coded in three places.

Three more `public = true` rows were added later, each mirrored by a `KEY_*` constant in `ServerConfig.kt` (and so enforced by `ServerConfigDriftSmokeTest`):

| Key | Value | Client read |
| --- | --- | --- |
| `interstitials_per_session` | `1` | Max full-screen (interstitial) ads shown per app session on the Free tier (RR-521); on-device fallback 1 (`supabase/migrations/20260915120000_interstitials_per_session_config.sql`) |
| `full_screen_ad_min_interval_sec` | `240` | Minimum seconds between any two full-screen ads (app-open OR interstitial) on Free, client-enforced; on-device fallback 240 (`supabase/migrations/20260919120000_full_screen_ad_min_interval_config.sql`) |
| `support_code_ttl_minutes` | `60` | Single-use support-code lifetime in minutes. ONE row read by both sides: `generate-support-token` sets the real token TTL from it, the client renders the "expires in N minutes" copy from it, so the displayed number is the enforced number (`supabase/migrations/20260926120000_support_code_ttl_config.sql`) |

Both ad rows are stored in seconds/counts (not milliseconds) to match the `rate_limit_config` `window_sec` convention and stay readable in the table editor; the client converts. `full_screen_ad_min_interval_sec` covers both full-screen formats with one row so the two formerly-separate hard-coded `MIN_INTERVAL_MS` constants cannot drift.

### Private rows read only by SQL

`bug_report_retention_days` (`90`, drives `prune_closed_bug_reports`) and `bug_report_stale_days` (`60`, drives `mark_stale_bug_reports`) are `public = false`. Both were first inserted (`supabase/migrations/20260817160000_bug_report_triage.sql`, `supabase/migrations/20260817200000_bug_report_stale_status.sql`) **without** naming the `public` column, so they defaulted to `true` and were wrongly served to clients — failing `ServerConfigDriftSmokeTest`, which flags any public row lacking a `ServerConfig.kt` mirror. `supabase/migrations/20260824140000_bug_report_config_private.sql` `UPDATE`s both to `public = false`. The teaching point: the `public` flag governs **only** what the client-facing `server-config` endpoint exposes. A `pg_cron` SQL read (`prune_closed_bug_reports` / `mark_stale_bug_reports`) never consults `public` at all, so these knobs stay readable by the sweepers while hidden from clients.

The feature-request sweepers added their own private pair, and this time the `public = false` was named explicitly to avoid the bug-report mistake:

| Key | Value | Read by |
| --- | --- | --- |
| `feature_request_retention_days` | `180` | `prune_closed_feature_requests()` — double `bug_report_retention_days` (a declined request is a product decision someone will ask about later) |
| `feature_request_stale_days` | `120` | `mark_stale_feature_requests()` — double `bug_report_stale_days` (an unanswered feature request has not decayed the way an unreproduced bug has) |

Both from `supabase/migrations/20260925120000_feature_requests.sql`. Burst protection added three more private rows — the global defaults inherited by every rate-limit bucket (`supabase/migrations/20260930120000_rate_limit_burst_protection.sql`):

| Key | Value | Read by |
| --- | --- | --- |
| `rate_limit_burst_mode` | `enforce` | the burst gate (`rate-limit.ts` → `getBurstGlobals`); inherited when a bucket's `burst_mode` is `NULL` |
| `rate_limit_burst_pct` | `40` | burst allowance as % of `max_requests` (clamped 1..100 in code) |
| `rate_limit_burst_window_sec` | `60` | burst window length in seconds (clamped 1..300 in code) |

And the net-revenue estimate added three private fallbacks read only by `revenuecat-webhook` through `_shared/billing/net-revenue.ts` (`supabase/migrations/20261004120000_net_revenue.sql`):

| Key | Value | Read by |
| --- | --- | --- |
| `revenue_play_commission_fallback_pct` | `0.15` | store commission share used only when a RevenueCat event has no `commission_percentage` |
| `revenue_tax_fallback_pct` | `0` | tax share used only when an event has no `tax_percentage` |
| `revenuecat_fee_pct` | `0.01` | RevenueCat's fee as a share of gross, subtracted from every purchase's net |

None of these ten private rows has (or is allowed) a `ServerConfig.kt` mirror — `public = false` rows must NOT mirror, which `ServerConfigDriftSmokeTest` also enforces in the other direction.

## `rate_limit_config`

The one exception to "server-authoritative values live in `server_config`" — rate limits have a structured shape (bucket → max + window + kill-switch) that earns its own table.

| Column | Type | Purpose |
| --- | --- | --- |
| `bucket_key` | `TEXT` (PK) | Matches the `Bucket` enum wire string |
| `max_requests` | `INT` | Ceiling per window (`CHECK > 0`) |
| `window_sec` | `INT` | Window length in seconds (`CHECK > 0`) |
| `enabled` | `BOOLEAN DEFAULT true` | Kill-switch — `false` admits without counting |
| `burst_mode` | `TEXT` (`off` / `shadow` / `enforce`) | Per-bucket burst-protection mode; `CHECK` constraint `rate_limit_config_burst_mode_check` rejects other strings. `NULL` = inherit `server_config.rate_limit_burst_mode` |
| `burst_pct` | `SMALLINT` | Burst allowance as % of `max_requests` (clamped 1..100 in code). `NULL` = inherit |
| `burst_window_sec` | `INTEGER` | Burst window length in seconds (clamped 1..300 in code). `NULL` = inherit |
| `description` | `TEXT` | What the bucket protects and why the ceiling was chosen |
| `updated_at` | `TIMESTAMPTZ` | Last edit |

The three `burst_*` columns (added by `supabase/migrations/20260930120000_rate_limit_burst_protection.sql`) are all nullable, and `NULL` means inherit the global default. Out-of-range `burst_pct` / `burst_window_sec` values are clamped in code rather than rejected, so a typo cannot take an endpoint down; only `burst_mode` is constrained at write time. Every bucket that existed at launch was set to `burst_mode = 'shadow'` (measure-first) by `supabase/migrations/20260930140000_rate_limit_burst_shadow_all_buckets.sql`. See [Rate Limiting & Buckets](/rollingrecord/backend/gates/rate-limiting) for the burst model.

Read through `getBucketConfig()` in `supabase/functions/_shared/gates/rate-limit.ts`, which caches the row (burst columns included) per warm instance and falls back to `BUCKET_DEFAULTS` on a missing row or DB error. `checkRateLimit()` dev-bypasses, honors the `enabled` kill-switch, resolves the effective burst settings, then calls the atomic `check_and_increment_rate_limit_v2` RPC, which enforces the sustained AND burst windows in one row-locked transaction; a normal rejection returns a minimal 429 `rate_limited` body of `{error, bucket, reset_at_sec, scope}` (`scope` is `"burst"` or `"window"`), while an RPC failure (or a no-row result) fails **closed** with a `500` `database_error` body of `{error, bucket}`. The registry of valid `bucket_key` strings is the `Bucket` enum in `supabase/functions/_shared/gates/types.ts`; each member needs both a `BUCKET_DEFAULTS` entry and a seeded `rate_limit_config` row in the same commit.

### Representative buckets

`BUCKET_DEFAULTS` is the fallback ceiling. For a few buckets the code fallback is deliberately held at half the live ceiling so a missing-row fallback always errs *below* the real limit.

| `bucket_key` | max | window_sec | Note |
| --- | --- | --- | --- |
| `ai_engine` | 60 | 3600 | All ai-engine ops |
| `feedback` | 5 | 3600 | Bug reports + feature requests (shared endpoint); seeded 5, live ceiling raised to 10. Replaced the retired `bug_report` bucket |
| `sync_pull` | 275 | 3600 | Live ceiling 550; fallback held at half |
| `sync_push` | 240 | 3600 | Batched `c_*` writes |
| `search` | 300 | 3600 | Live ceiling 600; fallback held at half |
| `delete_user` | 2 | 3600 | Account deletion; live ceiling raised to 5 |
| `account_otp_send` | 20 | 3600 | Forgot-PIN email code |
| `account_otp_verify` | 30 | 3600 | OTP verify |
| `sync_download_grace` | 100 | 86400 | Lapsed-subscription download grace; live ceiling raised to 550/day |

## `rate_limit_counters`

The per-`(user, bucket)` fixed-window counter table: `auth_user_id`, `bucket_key`, `window_start_sec` (`BIGINT`), `count` (`INT`), PK `(auth_user_id, bucket_key)`. It has no FK to `canonical_users` and is written **only** by the rate-limit RPC. Burst protection added four nullable state columns to the **same row** (`supabase/migrations/20260930120000_rate_limit_burst_protection.sql`): `burst_window_start_sec` (`BIGINT`, the current burst sub-window's start), `burst_count` (`INT`, weighted count in the current sub-window), `burst_prev_count` (`INT`, previous sub-window's count, decays linearly in the sliding estimate), and `burst_logged_start_sec` (`BIGINT`, de-dupes the `burst_limit_hit` log to one row per sub-window).

The current RPC is `check_and_increment_rate_limit_v2` (`p_auth_user_id`, `p_bucket_key`, `p_max`, `p_window_sec`, `p_weight` default 1, plus `p_burst_mode` / `p_burst_max` / `p_burst_window_sec`). It atomically evaluates the sustained AND burst windows under a `FOR UPDATE` row lock and returns `allowed`, `current_count`, `window_start_sec`, `near_limit_crossed`, and the burst outcome (`burst_blocked`, `burst_would_block`, `burst_reset_sec`, `burst_log`). Windows anchor to the first request after a reset, not to clock-hour boundaries, and a weighted increment that would cross either cap is rejected as a whole, consuming nothing. The original single-window `check_and_increment_rate_limit()` is untouched and still present as the deploy-order fallback when the v2 function has not yet been migrated.

## Seed-row pattern

Config rows land in migrations with idempotent inserts so a migration re-runs cleanly on a reset preview DB. `rate_limit_config` seeds use `INSERT ... ON CONFLICT (bucket_key) DO NOTHING` (e.g. `supabase/migrations/20260703150000_account_otp_rate_limits.sql`); `server_config` seeds use `ON CONFLICT (key) DO NOTHING` or `DO UPDATE` (e.g. `supabase/migrations/20260703170000_raise_storage_quotas.sql`, which stamps the authoritative storage caps). Live ceilings are edited in the dashboard; the code fallbacks stay at or below the live value by design. `server_config` also feeds derived logic — `supabase/migrations/20260527100000_create_f_user_financials.sql` seeds `storage_cost_s3_micros_per_gb_month` (21000) and `storage_cost_pg_micros_per_gb_month` (125000), read by `compute_storage_cost_micros`.

## Config tables at a glance

| Table | Shape | Read by | PK |
| --- | --- | --- | --- |
| `server_config` | `public` / `key` / `value` / `description` (value is `TEXT`) | `getInt`/`getNumber`/`getBool`/`getString` over `getServerConfigMap` (5-min cache) | `key` |
| `rate_limit_config` | `bucket_key` / `max_requests` / `window_sec` / `enabled` / `burst_mode` / `burst_pct` / `burst_window_sec` / `description` | `checkRateLimit` → `getBucketConfig` | `bucket_key` |
| `rate_limit_counters` | `auth_user_id` / `bucket_key` / `window_start_sec` / `count` / 4 `burst_*` state cols | `check_and_increment_rate_limit_v2()` RPC only | `(auth_user_id, bucket_key)` |
