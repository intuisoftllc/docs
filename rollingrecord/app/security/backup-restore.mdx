Portable Backup & Restore is a Free-tier, fully offline feature that writes a user's entire library to a single self-contained file and restores it on any install. The file is an **RRB2 portable container** (`PortableBackupContainer`, `app/crypto/PortableBackupContainer.kt`) encrypted with a key derived from a user-chosen **backup PIN** — not the account DEK — so it restores on a fresh install with no sign-in. It replaces the DEK-bound `.rrbackup` container (`RrBackupContainer`) and the debug-only `DevBackupManager` ZIP tool, both of which still exist in the codebase but are retiring. Nothing in this path touches the network, Supabase, or the account key.

## The RRB2 container format

`PortableBackupContainer` reads and writes the container: a plaintext header followed by one payload, encrypted or verbatim. The header is plaintext by design so a file picker can recognise the file (`MAGIC` = ASCII `"RRB2"`), an importer can reject an unsupported container before any crypto (`FORMAT_VERSION = 1`), and the IVs/salt are non-secret. Nothing about the library contents is readable from the header.

| Field | Size | Contents |
| --- | --- | --- |
| magic | 4 bytes | ASCII `"RRB2"` (`MAGIC`) |
| formatVersion | 4 bytes | big-endian `Int` (`FORMAT_VERSION = 1`) |
| flags | 1 byte | bit 0 = encrypted (`FLAG_ENCRYPTED`) |
| kdfIterations | 4 bytes | big-endian `Int` — encrypted only |
| kdfSalt | 16 bytes | PBKDF2 salt — encrypted only |
| wrapIv | 12 bytes | GCM IV wrapping the content key — encrypted only |
| wrappedContentKey | 48 bytes | `AES-256-GCM(contentKey)` = 32 ciphertext + 16 tag — encrypted only |
| payloadIv | 12 bytes | GCM IV for the payload — encrypted only |
| payload | rest | `AES-256-GCM(payload)` under the content key, or the payload bytes verbatim |

The encryption is **envelope encryption**: a fresh random 32-byte content key encrypts the payload (streamed via the shared `encryptStream`), and that content key is itself wrapped under a KEK derived from the PIN. The envelope lets a future build additionally wrap the same content key with the account key (a "restore without the PIN while signed in" convenience) with no re-encrypt and no format change — not in v1.

`writeEncrypted(payload, out, pin, iterations)` derives the KEK, wraps a fresh content key, writes the header, and stream-encrypts the payload. `writePlaintext(payload, out)` writes the header with `flags = 0` and copies the payload verbatim (the opt-out "no PIN" export). `readHeader(container)` validates the magic and version and leaves the stream at the first payload byte — the UI uses it to peek whether a picked file is encrypted before asking for a PIN. `read(container, payloadOut, pin)` decrypts (or copies) the whole payload.

## The PIN-derived key

`BackupPinKdf` (`app/crypto/BackupPinKdf.kt`) turns the low-entropy backup PIN into the 32-byte KEK that wraps the content key. It uses `PBKDF2WithHmacSHA256` — the same primitive the app-lock verifier uses, so no new dependency — deliberately chosen over HKDF because a PIN is low entropy and needs a slow KDF to blunt offline brute force against a leaked backup file.

`CURRENT_ITERATIONS = 600_000` is far higher than the app-lock verifier's count (a backup is not latency-sensitive, so a 1–2s derive is acceptable and multiplies an attacker's cost). The iteration count is written into each archive's header, so raising it later never breaks an older archive: that archive decodes with the iteration count, salt, and PIN it was made with. `KEY_BYTES = 32`, `SALT_BYTES = 16`; `randomSalt()` mints a fresh salt per archive and `deriveKey(pin, salt, iterations)` returns the KEK.

## What is in the archive

The payload inside the container is a ZIP with a fixed layout, assembled by `RecordingsArchiveExporter` (`data/backup/archive/RecordingsArchiveExporter.kt`):

| Entry | Contents |
| --- | --- |
| `manifest.json` | the normalized `BackupArchive` (categories + sessions + recordings) |
| `audio/<recordingId>.<ext>` | each recording's audio bytes, stored (not re-compressed) |
| `transcripts/<recordingId>.json` | an `ArchiveTranscript` for every `DONE` transcript |

The archive DTOs live in the pure-JVM crypto module (`app/crypto/BackupArchive.kt`) so they can never reference a Room `@Entity` — the format is the archive's public contract. `BackupArchive` carries `archiveVersion` (`CURRENT_ARCHIVE_VERSION = 1`, `MIN_SUPPORTED_ARCHIVE_VERSION = 1`), `exportedAt`, and the three normalized spines. The per-recording entry `ArchiveRecording` is deliberately self-describing: alongside the real ids it carries denormalized names (`categoryName`, `sessionName`), bookmarks (`marks`), and a `hasTranscript` flag.

`ArchiveRecording` doubles as the on-disk **sidecar**. `RecordingSidecarWriter` (`data/backup/archive/RecordingSidecarWriter.kt`) writes a small `<audioPath>.meta.json` file next to each recording (suffix `SIDECAR_SUFFIX = ".meta.json"`, mirroring the existing `.waveform2` sidecar). The Room DB is always the source of truth; sidecars are a derived mirror, written write-behind on save and metadata edits and fully regenerated from the DB at export time via `refreshAll()`. They are only ever read back when the DB is unavailable — the disaster / no-DB recovery path. Because a lone sidecar carries the denormalized category and session names, it can recreate its recording with no categories table and no top-level manifest. `buildArchiveRecording(entity)` is the single DB-to-DTO mapper, shared between the sidecar writer and the exporter so the mapping lives in exactly one place.

## Export

`RecordingsArchiveExporter.export(out, pin, onProgress)` runs on `Dispatchers.IO` and returns an `ExportResult(recordingCount, transcriptCount, totalAudioBytes, encrypted)`:

1. `sidecarWriter.refreshAll()` — refresh every on-disk sidecar from the DB so a future dead-DB export still has metadata.
2. Read all categories, sessions, and recordings through the scoped DAOs, map them to the archive DTOs, and build the `BackupArchive` manifest.
3. Assemble a temp ZIP in `cacheDir`: `manifest.json`, then each recording's audio (skipping files that no longer exist on disk) and each `DONE` transcript.
4. Stream the temp ZIP into `out` — `writeEncrypted` when a PIN is supplied, `writePlaintext` when the PIN is null or blank.

Peak extra disk is roughly the library's audio size (audio is stored, not recompressed); `out` is a SAF `content://` stream the caller owns and closes.

## Import and dedup

`RecordingsArchiveImporter.import(container, pin, onProgress)` (`data/backup/archive/RecordingsArchiveImporter.kt`) inverts the exporter. It decrypts (or copies) the container payload into a temp ZIP via `PortableBackupContainer.read`, reads `manifest.json`, and gates the `archiveVersion` in both directions (too old or too new → `BackupArchiveVersionException`, whose `tooNew` flag drives an "update the app" message).

The merge policy is an **idempotent restore**, so restoring into an empty library brings everything back and re-importing the same file adds nothing:

- A recording or session whose id already exists **live** is skipped (never duplicated).
- A recording that exists but is **trashed** is the one exception — it is deleted locally (no tombstone, so no cloud deletion propagates) and re-inserted from the backup, so audio, category, transcript, and marks all come back cleanly.
- Categories are matched by **name** (reuse an existing "Work", create only when absent), since `createCategory` mints its own id. Every category in the archive is pre-created up front so even empty categories survive.
- Transcripts upsert by `recordingId` (inherently idempotent).

Inserts go through the real repositories, so a restored recording re-enqueues cloud sync, regenerates its waveform, and gets a fresh `.meta.json` sidecar — exactly as if it had just been recorded. Failures are per-item (logged and counted), never aborting the batch. The result is an `ImportResult` counting recordings imported/skipped, categories created, sessions, transcripts, and marks.

## The screen

`V2BackupRestoreScreen` (`ui/v2/screens/backup/V2BackupRestoreScreen.kt`), reached from **Help & Support → a row under Privacy** (nav route `V2BackupRestore`), presents a single card with Back up and Restore buttons, driven by `V2BackupRestoreViewModel`. Both flows are fronted by an **app-lock re-verify gate** — when App Lock is enabled with a PIN, the user must re-verify with that PIN or a fingerprint before exporting or restoring (`gateRequired()` is false, so the gate is skipped, when App Lock is off).

The export flow runs: gate → a two-step set-PIN sheet (4–8 digits, or **Skip** to write an unencrypted archive) → name the backup → the SAF `CreateDocument` picker (default name `yyyy-MM-dd_Backup`, saved with a `.rrbackup` extension and `application/octet-stream` MIME) → the progress sheet. The restore flow runs: gate → `OpenDocument` → `peek()` (which calls `readHeader` to classify the file as `ENCRYPTED`, `PLAINTEXT`, or `INVALID`) → an enter-PIN sheet for an encrypted archive or a confirm sheet for a plaintext one → the progress sheet.

The result sheet shows a progress bar during the operation and a green check or an error on completion; dismissing it mid-run cancels. A cancelled or failed export best-effort deletes the partial SAF document; a cancelled import is safe to re-run because it is idempotent. Users on Pro+Cloud and up see a note that cloud recordings already back up automatically and that this manual backup covers recording data only (AI context and chats are excluded). The view model maps the container's typed exceptions to localized messages: a wrong or missing PIN re-opens the PIN step, `BackupArchiveVersionException` shows the too-old / update-required copy, and `BackupCorruptException` / `PortableBackupFormatException` show the corrupt-file error.

## Failure posture

A wrong PIN fails GCM tag verification while unwrapping the content key, before the payload is ever decrypted (`BackupPinIncorrectException`). An encrypted container opened with no PIN throws `BackupPinRequiredException`. A tampered or truncated payload fails at end-of-stream (`BackupCorruptException`), and a bad magic or unsupported version throws `PortableBackupFormatException` — all subtypes of the sealed `PortableBackupException`. The importer stages everything to a temp ZIP and only commits per-item inserts on a clean read, so any container-level failure leaves the existing library untouched.

## Legacy `.rrbackup` and DevBackup

The previous production path — `BackupExporter` / `BackupRestorer` (`data/backup/`) over the DEK-bound `RrBackupContainer` + `BackupManifest` (`app/crypto/`) — and the debug-only `DevBackupManager` ZIP tool both remain in the tree but are superseded by the RRB2 portable format and slated for removal. Unlike RRB2, the `.rrbackup` container is keyed off `HKDF(DEK, "rr-db-backup-v1")` and so only restores while signed in as the owning account.
