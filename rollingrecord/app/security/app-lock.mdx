title: "App Lock"
description: "The lifecycle-driven lock overlay (AppLockController + V2LockOverlay) that gates the whole app on background/foreground transitions and cold start, never mid-use."
---

App Lock (RR-492) draws a full-screen unlock overlay over the entire app whenever the account is locked. Locking is driven purely by lifecycle transitions — never mid-use — and the recording engine keeps running underneath it. The lock is a UI layer, not an encryption gate.

## `AppLockController` and `LockPhase`

`AppLockController` (`data/applock/AppLockController.kt`) is a process singleton — app-scoped so its state survives the per-user Koin scope teardown on sign-out and account switch. It exposes one flow, `phase: StateFlow<LockPhase>`, that the UI host consumes. Because App Lock settings are per-**user**, the session layer feeds the current account's snapshot in rather than the controller reaching into the user scope.

| Phase | When | UI shown |
| --- | --- | --- |
| `UNLOCKED` | Signed out, disabled, or unlocked this session | Normal app, fully interactive |
| `RESOLVING` | Active session, cold-start settings snapshot still loading | Blocking frosted scrim (no keypad) — fail-closed, content blurred |
| `LOCKED` | Signed-in + enabled, triggered by lifecycle or cold start | `V2LockOverlay` (keypad / biometric / lockout countdown) |

`RESOLVING` is the fail-closed window: a fast tap can't reach the local, no-auth content before the lock decision lands. The initial phase is seeded synchronously from `AppLockArmedCache` so a cold start never flashes interactive content.

The controller is fed by the session and settings layers through: `onUserSignedIn(authUserId)`, `onFreshLogin()`, `onUserSignedOut()`, `updateSettings(enabled, autoLockMs)`, and `onUnlocked()`. Four of those — everything except `onUnlocked()` — are driven from `App.observeAuthForAppLock` (`App.kt`), which collects `authRepository.authState` on `Dispatchers.Main.immediate`. `onUnlocked()` comes from the UI layer instead: `V2LockOverlayViewModel` on a correct PIN or a successful biometric, and `V2App`'s forgot-PIN exit (`V2ForgotPinFlow`'s `onExitToApp`). `onUserSignedIn` fires for **both** a login and a restored session — which is exactly why a second signal is needed to tell them apart (see below). Lifecycle hooks are `start()` / `stop()`, `onActivityStopped()` / `onActivityStarted()`, plus a `ProcessLifecycleOwner` observer and a `SCREEN_ON` / `SCREEN_OFF` `BroadcastReceiver`.

## Lifecycle-driven locking

The lock timer conceptually starts on login: a fresh sign-in never immediately locks. On entering background or screen-off the controller records `SystemClock.elapsedRealtime()`; on returning to foreground (or screen-on) it locks iff `enabled && signedIn` **and** the elapsed time is `>=` the auto-lock delay. A delay of `0` (Immediate) locks directly on background.

Two things make this robust:

- **Cold-start re-lock.** A force-quit + relaunch or a restored session re-locks unconditionally when the account is armed. `updateSettings` resolves `coldStart && signedIn && enabled` straight to `LOCKED` (logging `"app lock: locked on cold start"`), so quitting the app can't bypass the lock. Note that this branch does **not** consult `autoLockMs` — the delay governs lifecycle transitions, not cold start. `onFreshLogin()` exempts a genuine interactive login.
- **Never mid-use.** The `coldStart` flag is consumed by the first settings snapshot of a session, so a later mid-session change — first-time PIN setup, or the server sync flipping `enabled` on — can never trigger the cold-start re-lock. Enabling App Lock while actively using the app arms the *next* background/foreground cycle; it doesn't slam the lock over the settings page the user is standing on.

The lock decision gates on `enabled` only. App Lock is "enabled" only when a PIN is set, so `enabled` implies a PIN; the PIN verifier (which syncs from the server and can lag) is used solely to verify an entered PIN, never to decide whether to show the lock. There is no `hasPin` term anywhere in the decision — the runtime gate for the background/foreground hooks is `shouldGuard() = signedIn && enabled && !locked && !autoLockSuppressed`, and gating on the verifier is what once let a cold start slip through while it was still loading.

### Restored session vs interactive login

Both a force-quit relaunch and a person who just typed an OTP surface as the same `AuthState.SignedIn` emission, so the difference has to be recorded where it is actually known. `App.observeAuthForAppLock` makes the call on one line:

```kotlin
if (authRepository.consumeInteractiveSignIn() || hasBeenSignedOut) {
    appLockController.onFreshLogin()
    hasBeenSignedOut = false
}
```

| Signal | Written by | When | Effect |
| --- | --- | --- | --- |
| `AuthRepository.interactiveSignIn` | `markInteractiveSignIn()`, the **first** statement of `verifySignInOtpV2`, `verifySignUpOtpV2`, and `signInWithGoogle` | Before the credential attempt | `consumeInteractiveSignIn()` reads-and-clears it → `onFreshLogin()`, never locks |
| `hasBeenSignedOut` | `App.observeAuthForAppLock`, only when a `SignedOut` follows a confirmed `SignedIn` (`hasBeenSignedIn`) | An in-process logout | `onFreshLogin()` |
| Neither | — | A restored session | `coldStart` stays `true`; the first `updateSettings` snapshot re-locks if the account is armed |

Two details are load-bearing:

- **The flag is written before the credential attempt, not after.** Clerk flips its user flow the instant `attemptFirstFactor` / `attemptVerification` / `signInWithOAuth` succeeds, so a flag set afterwards can lose the race with the observer already collecting that emission. A failed attempt leaves it set, which is harmless — it is only ever read when a sign-in actually lands.
- **The in-process sign-out alone is not enough.** Launching straight to the login screen — the normal case after a clean sign-out, and every fresh install — never sets `hasBeenSignedOut`, because the `SignedOut` that arrives is Clerk's cold-start-init transient, which `hasBeenSignedIn` deliberately ignores. Without the interactive flag an ordinary login was read as a restored session and met with the lock screen the moment the account's settings loaded, seconds after the user authenticated — and regardless of the auto-lock delay, since the cold-start re-lock does not consult it.

The ordering per sign-in is: `AuthState.SignedIn` → `onUserSignedIn(authUserId)` (phase → `RESOLVING`) → the classification above → optionally `onFreshLogin()` (phase → `UNLOCKED`, `coldStart` cleared) → later, the first `updateSettings` snapshot resolves `RESOLVING` into `LOCKED` or `UNLOCKED`.

### `MainActivity` drives the controller directly

`MainActivity.onStop` / `onStart` call `appLockController.onActivityStopped()` / `onActivityStarted()` directly, in addition to the `ProcessLifecycleOwner` path. This is load-bearing: `ProcessLifecycleOwner` debounces `ON_STOP` by ~700ms, which made "Immediate" auto-lock silently miss a brief background + return. The activity callbacks fire immediately (the single activity is portrait-locked, so there are no rotation-recreate false triggers), and the two paths are idempotent — the background timestamp is consumed once and locking is guarded by the current phase.

## `AppLockArmedCache`

`AppLockArmedCache` (`data/applock/AppLockArmedCache.kt`) is a per-account, synchronously-readable `SharedPreferences` cache (`app_lock_armed_prefs`) of whether an account has App Lock **armed** (enabled + PIN). It is the only App Lock state available before the async per-user DataStore snapshot loads, so the controller seeds its initial `LockPhase` from it. `seedLocked()` returns the fail-closed initial phase; `setActiveUser` / `clearActiveUser` maintain a `last_active_user` pointer (the user isn't known at process construction), and `setArmed(userId, armed)` caches each account's armed state independently.

## Server sync — how a PIN set on another device activates here

`AppLockRepository.refreshFromServer(forceRefresh = false)` (`data/applock/AppLockRepository.kt`) is the last-write-wins reconcile against `user_crypto`. It runs under a `refreshMutex`, and it reads the server state through `dekHolder.fetchUserKey(forceRefresh)` — i.e. through the app-scoped `UserKeyProvider` — so the App Lock PIN sync, the sign-in DEK provision, and the recovery-code presence check all ride **one** `get-user-key` round-trip. See [DEK & Database Key Lifecycle](/rollingrecord/app/security/dek-and-db-key) for that single-flight.

A thrown fetch (offline, or App Check / DEK not ready during a fresh-install "setting up your account") or a non-`Success` result returns `false` — a **retryable miss**, not a failure. `lastRefreshSuccessMs` is stamped only on success, so a failed refresh keeps retrying on every subsequent trigger; `REFRESH_THROTTLE_MS = 60_000L` skips re-fetches within a minute of the last success, and a pending local push bypasses the throttle entirely (this reconcile is the path that pushes it up, so it must never be starved).

| Trigger | Call | Notes |
| --- | --- | --- |
| Sign-in | `refreshFromServer()` in a bounded retry loop | `APP_LOCK_SYNC_MAX_ATTEMPTS = 6` × `APP_LOCK_SYNC_RETRY_DELAY_MS = 5_000L` (`App.kt`) — ~30s of coverage, stopping the moment the pull succeeds. The retry budget exists because the first attempt on a fresh install races account setup. |
| Connectivity restore | `refreshFromServer(forceRefresh = true)` | `forceRefresh` bypasses **both** the `UserKeyProvider` and `SessionDekHolder` 5-minute TTLs, so a reconnect observes a PIN changed on another device rather than a cached snapshot. |
| Settings write | `setAutoLockMs` / `setPin` push | Pushes the local verifier + `auto_lock_ms` up; the server assigns the fresh LWW stamp other devices adopt. |

The two `refreshFromServer` triggers live inside `observeAuthForAppLock`'s session-scope gate: a `launch(Dispatchers.IO)` child that collects `userSessionManager.sessionIdFlow` and only resolves `userSession().get<AppLockRepository>()` once the session id matches the signed-in `authUserId`. (That same gated block also hosts the `combine(isEnabled, autoLockMs)` collector that feeds `AppLockController.updateSettings` — a settings *read*, not the push below.) The settings **write** is not in there at all: `setAutoLockMs` / `setPin` are called from the user-facing UI — `V2SecurityViewModel` and `V2ForgotPinViewModel` — on the session-scoped repository those screens already hold, and both route to `pushToServer`. Resolving earlier grabbed the **anonymous** scope's repository — wired to `anonymous.preferences_pb` — so the controller watched the wrong file all session and a first-time PIN setup never armed the lock until a process restart.

## Auto-lock delay presets

The delay is chosen in `V2AutoLockSheet` (`ui/v2/screens/security/components/V2AutoLockSheet.kt`) and rendered on the Security row via `autoLockLabel`.

| Label | Millis |
| --- | --- |
| Immediate | `0` (locks directly on background) |
| 30 seconds | `30000` |
| 1 minute | `60000` |
| 5 minutes | `300000` |
| 10 minutes | `600000` (`DEFAULT_APP_LOCK_AUTO_LOCK_MS`, the default) |
| 30 minutes | `1800000` |
| 1 hour | `3600000` |

The default was raised from 1 minute to 10 minutes: per its KDoc in `UserSettingsDataSource` (`data/local/UserSettingsDataSource.kt`), App Lock protects a recorder, not a bank vault — a one-minute delay mostly re-authenticates the owner after every glance while barely slowing an attacker with the device in hand. `DEFAULT_APP_LOCK_AUTO_LOCK_MS` lives in `UserSettingsDataSource.kt`; existing installs that already chose a value keep it, and stricter presets (Immediate / 30s / 1m) remain in the picker.

## Auto-lock suppression

`setAutoLockSuppressed(Boolean)` temporarily disables auto-lock for windows where locking would be self-defeating. It is in-memory only, so a process death drops it and the cold-start re-lock still applies.

| Site | Why |
| --- | --- |
| `V2OtpCodeStep` (`ui/v2/components/V2OtpCodeStep.kt`) | Fetching the emailed OTP requires leaving the app; locking on return would dismiss the very sheet the user must finish — an unresolvable loop |
| `V2RecordingScreen` | Active recording — never lock mid-use |

A Compose `DisposableEffect` flips suppression on while the step is shown and off when it leaves, so the unlock window lasts only that long.

## `V2LockOverlay`

`V2LockOverlay` (`ui/v2/screens/security/lock/V2LockOverlay.kt`) is the full-screen unlock UI drawn over the blurred app while `phase == LOCKED`. It is a frosted scrim (`V2Theme.colors.lockScrim`) that consumes all touches and the system back button. Layout: a masked account badge top-left, a red logout affordance top-right, a centered `V2PinKeypad` (or `LockoutContent` countdown while timed out), and "Need help?" / "Forgot PIN?" links pinned to the bottom.

The biometric sheet runs at the `FragmentActivity`; the overlay requests it via `onRequestBiometric: (userInitiated: Boolean, onResult: (BiometricAuthResult) -> Unit) -> Unit` and feeds the result back to the VM. The `userInitiated` flag distinguishes the two callers: the reconciler auto-prompt passes `userInitiated = false` (it must not disturb a possibly-showing sheet), while the user tapping the fingerprint button passes `userInitiated = true` — a tap proves no system sheet is covering the screen, which lets the gate treat a stuck in-flight state as stale and relaunch it. A declarative reconciler decides "should the sheet be showing?" against "is it showing?" — the sheet re-offers itself once per foreground stint (`episodeAnswered` resets on every `ON_RESUME`), `SystemCancelled` results retry up to a cap of 3, and a 250ms settle delay avoids the keyguard-dismiss animation stealing the prompt. The overlay takes `onLogout`, `onNeedHelp`, `onForgotPin`, `onRequestBiometric`, `biometricSuppressed`, and `onCancelBiometric`.

The gate's in-flight guard is no longer a one-way door: it records `inFlightSinceMs` and relaunches the prompt (rather than only re-pointing the callback) when `userInitiated` is `true` OR the in-flight age exceeds `STALE_IN_FLIGHT_MS = 60_000L`. This recovers from an androidx launch dropped in the saved-state window, which previously left biometrics permanently dead until force-close. See [PIN & Biometrics](/rollingrecord/app/security/pin-and-biometrics) for the full gate behavior.

### `V2LockOverlayViewModel`

`V2LockOverlayViewModel` (`ui/v2/screens/security/lock/V2LockOverlayViewModel.kt`) drives the keypad. It owns the transient PIN buffer (never surfaced — only its length reaches the UI), the `TITLE` ⇄ `DOTS` ⇄ `ERROR` status swap (`LockTop`), biometric results, and a live lockout countdown derived from `AppLockRepository.lockoutUntil`. Its entry points are `onDigit` / `onDelete` / `onOk` / `onBiometricResult`. On a correct PIN it calls `AppLockController.onUnlocked()` and lets the host dismiss via the phase flow — it never signals dismissal directly. Crucially, it resolves its user-scoped dependencies at **use** time through `UserSessionManager.currentScope` (never captured at construction), so the Activity-cached VM survives sign-out/sign-in of the same account. `UNLOCK_VERIFY_TIMEOUT_MS` (8000) bounds a cold-start unlock whose DEK leg falls through to a network fetch, so the OK tap can never look silently dead. `abbreviateAccountLabel()` masks the email badge.

### `V2PinKeypad`

`V2PinKeypad` (`ui/v2/screens/security/lock/V2PinKeypad.kt`) is the custom numeric keypad — it **never** raises the OS keyboard (a locked device shows only this pad). A 3×4 grid renders 1–9 then DELETE · 0 · OK; OK is inert until `okEnabled` (length 4–6), and the fingerprint button appears only when `showBiometric`. It is purely presentational, routing `onDigit` / `onDelete` / `onOk` / `onBiometric` out to the VM. `V2PinDots` renders the filled-of-6 dot row.

## Hosting and lock-aware surfaces

`V2App` (`ui/v2/V2App.kt`) hosts the overlay: it injects `AppLockController`, collects `phase`, blurs `V2MainNavHost` by 20dp when `appLocked || resolvingLock`, renders the `RESOLVING` shield scrim, and draws `V2LockOverlay` when `appLocked && sessionActive`. It wires `onRequestBiometric` to `AppLockBiometricGate.current`, forwarding the `userInitiated` flag into `gate.authenticate(...)`; `AppLockBiometricGate` owns the app's one and only `BiometricPrompt` — construction, not concurrency, is the invariant. A second `BiometricPrompt(...)` built anywhere in the activity silently steals the gate's callback slot for the activity's life and breaks unlocking with nothing logged (the sheet shows, the finger is accepted, the result is dropped into a dead callback). The `SingleBiometricPromptTest` (`data/applock/SingleBiometricPromptTest.kt`) is a structural guard — a source-scan asserting exactly one `BiometricPrompt(` construction site, in `AppLockBiometricGate`. `V2App` also sets `biometricSuppressed = showForgotPin || showLockLogoutConfirm` and hosts `V2ForgotPinFlow` above the lock. See [PIN & Biometrics](/rollingrecord/app/security/pin-and-biometrics) for the gate's callback-ownership rule in depth.

Any surface that renders in its own window can react to the same signal via `AppLockUi` (`ui/v2/components/AppLockUi.kt`): `rememberAppLocked(): Boolean` observes `AppLockController.phase == LOCKED` inside composition and backs `V2ModalBottomSheet` / `V2AlertDialog`, while `DismissOnAppLock` dismisses a raw `Dialog` the instant App Lock engages so it can't float over the lock.
