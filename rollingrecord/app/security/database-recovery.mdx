---
title: "Database Recovery States"
description: "How the app routes a database that can't be opened: narrow key-mismatch wipe, fatal error, or recoverable DEK-unavailable."
---

When the encrypted database can't be opened, `DatabaseModule` classifies the failure and routes it to one of four observable outcomes that `V2App` renders at the root. Only a genuine key mismatch is ever safe to wipe; a missing DEK — including a server-refused key for a frozen account — is refused before the DB is even opened; every other failure is fatal and leaves the file untouched. Audio files on disk are never touched by any path.

## The recovery states

`RecoveryState` (`states/DatabaseRecoveryState.kt`) is a sealed class with five cases, and `DatabaseRecoveryState` is an object exposing `state: StateFlow<RecoveryState>` plus the flag setters.

| `RecoveryState` | Trigger | V2 surface | Data on disk |
| --- | --- | --- | --- |
| `KeyMismatchWiped` | SQLCipher couldn't decrypt an opened DB (genuine corruption / reinstall leftover) | `V2DatabaseRecoveryDialog` (re-import audio) | DB wiped; audio intact |
| `FatalError(errorCode, message)` | Schema / migration / unknown open failure | `V2FatalDbErrorScreen` (no reset) | Untouched |
| `DekUnavailable(reason)` | Per-user DEK unresolvable **before** open | `V2DekUnavailableScreen` (retry) | Untouched — not opened, not wiped |
| `AccountFrozen(authUserId)` | Account frozen (server 403 `account_frozen`) and this device has **no** local DEK | `V2AccountFrozenScreen` (Contact support / Sign out) | Untouched — not opened, not wiped |
| `None` | Normal | App tree | — |

The setters are `flagRecoveryNeeded()`, `flagFatalError(code, message)`, `flagDekUnavailable(reason)`, `flagAccountFrozen(authUserId)`, and `clearRecovery()`.

## Open-failure classification

`classifyOpenFailure(e)` in `di/DatabaseModule.kt` walks the exception's cause chain (lowercased, joined) and returns a `DbOpenFailure`. Only `KEY_MISMATCH` is wipe-safe.

| `DbOpenFailure` | Message signatures matched | Action | DB wiped? |
| --- | --- | --- | --- |
| `KEY_MISMATCH` | `file is not a database` / `file is encrypted or is not a database` | `handleKeyMismatch` → wipe + rebuild under current key | **yes** |
| `SCHEMA_MISMATCH` | `room cannot verify` / `identity hash` / `expected:` + `found:` | `handleFatalDbError` → fatal screen | no |
| `MIGRATION_MISSING` | `migration from … was required but not found` | `handleFatalDbError` → fatal screen | no |
| `UNKNOWN` | anything else | `handleFatalDbError` → fatal screen | no |

`verifyDatabaseConnection(db)` opens `openHelper.writableDatabase` to force the SQLCipher decrypt + schema check. `openVerifiedOrRecover(context, db, rebuildKey)` wraps it: on failure it routes `KEY_MISMATCH` to `handleKeyMismatch(rebuildKey)` and every other class to `handleFatalDbError`. It also contains the `[DEV] DevFlags.forceFatalDbErrorOnOpen` hook, which is consumed and then throws a synthetic schema-mismatch to exercise the fatal screen end-to-end (a no-op in release).

## The key-mismatch wipe path

`handleKeyMismatch` is the **only** path that wipes. Crucially, it resolves the rebuild key *before* any destructive wipe — so if the DEK became unavailable in the interim, `freshPassphrase()` throws `DekUnavailableException` with the file still untouched. It then reports to Crashlytics with `db.open.wipe = true`, calls `flagRecoveryNeeded()`, closes the stale handle, `wipeDbFiles()` (main + `-wal` + `-shm`), and rebuilds under the **current** session key — device-bound for anonymous, DEK-derived for signed-in. Rebuilding under the same current key is required: a fresh random key would loop `KEY_MISMATCH` forever, since the committed structure metadata expects a specific key on the next open.

## The fatal path

`handleFatalDbError` handles `SCHEMA_MISMATCH`, `MIGRATION_MISSING`, and `UNKNOWN`. It logs, reports to Crashlytics with `db.open.wipe = false` plus the fatal type and message, calls `flagFatalError(failure.name, message)`, closes the stale handle, and rethrows an `IllegalStateException`. The DB file is **not** touched — the data is intact on disk — and `V2App` renders the fatal screen.

## DEK-unavailable: refused before open

`DekUnavailableException` (private in `di/DatabaseModule.kt`) is thrown by `buildAppDatabaseForSession` when the per-user DEK can't be resolved. It is thrown **before** `buildRoomDatabase` / `verifyDatabaseConnection`, so a missing or wrong DEK is structurally incapable of reaching `classifyOpenFailure` → `handleKeyMismatch`. It pairs with `flagDekUnavailable(reason)`; the `App.kt` warmup swallows the throw, and `V2App` renders `V2DekUnavailableScreen` instead of mounting the nav host. This RR-321 gate means the wipe now requires **both** a `KEY_MISMATCH` classification **and** a successfully-resolved key — the old "any DB error wipes everything" behavior no longer applies.

A **hung** DEK fetch lands in the same recoverable branch, not the wipe path. `buildAppDatabaseForSession` bounds its inline `SessionDekHolder.requireDek()` self-heal at 45s (`INLINE_DEK_FETCH_TIMEOUT_MS`); a timeout leaves `persisted == null`, which routes to the recoverable `DekUnavailable` state and is structurally never `classifyOpenFailure` / `handleKeyMismatch`. The `DekUnavailable` throw also emits a deduped Crashlytics non-fatal carrying structured cross-account diagnostics (`dek.crossAccount`, the owner fingerprints, the KEK version). `flagDekUnavailable(reason)` still receives only the `reason` string — the diagnostics map goes to Crashlytics, not the `RecoveryState` — so the `RecoveryState` shape above is unchanged.

## Account frozen: terminal, no local DEK

`RecoveryState.AccountFrozen(authUserId)` is the one DB-open outcome that isn't about key material being lost or corrupt — it's about the server **refusing** to hand over the key. When a **new** device signs into a frozen account there is no local DEK to fall back on, the server's key fetch returns 403 `account_frozen`, and the DB can never open. `flagAccountFrozen(authUserId)` routes this to a dedicated surface rather than the generic `DekUnavailable` retry, because the cause is known and **terminal**: retrying can't resolve a frozen account. The DB file is **neither opened nor wiped** — the data on disk is intact — and the state clears on a later successful sign-in once the account is unfrozen.

The branch in `V2App` sits **above** the `DekUnavailable` branch so a known-frozen cause never falls through to the generic "can't unlock" retry. The user stays **signed in** on this surface: `authUserId` identifies the frozen session and lets the support email attach that account's log even though the database never opened.

`V2AccountFrozenScreen` (`ui/v2/screens/recovery/V2AccountFrozenScreen.kt`) mirrors the soft overlay's snowflake + `StatusFrozen` + shared `frozen_overlay_body` copy so the two frozen surfaces read as one family, and shows the admin `reason` (read live from `AccountHealthRepository.frozenState`) in a muted card when present. Its two honest actions replace the overlay's "OK":

- **Contact support** (`SheetPrimaryButton`) opens `sendUnlockSupportEmail` with the `recovery_frozen_support_body` template and the explicit `authUserId`, attaching the account's diagnostic log.
- **Sign out** (an understated secondary control) is the escape hatch to the login screen (e.g. to sign into a different account). It is guarded against a double-tap and swaps the whole surface to a `recovery_frozen_signing_out` spinner, then drives the session teardown directly: `signOut()`, `AuthUserStore.clearCurrentUserId`, `UserSessionManager.switchTo(null)`, and finally `clearRecovery()`. Teardown runs **before** `clearRecovery()` on purpose — the normal auth observer that would react to `SignedOut` isn't composed while a recovery surface is up, and clearing first would re-compose the tree with the stale signed-in user, re-fire the DB warm-up JWT-less, and strand it on the generic DEK-unavailable screen. **The local database is not deleted** — the data stays on disk for a later successful (unfrozen) sign-in.

<Note>
`AccountFrozen` is the terminal, **no-DEK** counterpart to the dismissible [soft frozen overlay](/rollingrecord/app/auth/account-health) (`V2FrozenOverlay`). The overlay requires the DB to already be open (a returning device that holds the DEK), keeps full local access, and offers only an informational **OK**; this screen is for a device that can't open the DB at all, so it offers Contact support / Sign out instead. Both read the same persisted freeze signal and share the snowflake treatment.
</Note>

## The five root surfaces

`V2App` (`ui/v2/V2App.kt`) collects `DatabaseRecoveryState.state` and branches:

- **`FatalError`** replaces the surface with `V2FatalDbErrorScreen` (`ui/v2/screens/recovery/V2FatalDbErrorScreen.kt`). It has **no reset/wipe button** — only an error-code box, Contact support (`mailto:support@rollingrecord.ai`), Copy error, and an Export-recordings-to-zip bailout (`RecordingsZipExporter`), plus a reinstall reminder.
- **`AccountFrozen`** shows `V2AccountFrozenScreen` (`ui/v2/screens/recovery/V2AccountFrozenScreen.kt`) — a new device signing into a frozen account, no local DEK. It sits **above** the `DekUnavailable` branch so a known-frozen cause never falls through to the generic retry, and offers Contact support / Sign out (no reset). The local DB is **not** deleted. See [Account frozen: terminal, no local DEK](#account-frozen-terminal-no-local-dek) above.
- **`DekUnavailable`** shows `V2DekUnavailableScreen` (`ui/v2/screens/recovery/V2DekUnavailableScreen.kt`); Retry re-resolves the DEK and, on success, calls `clearRecovery()` and recreates the activity. The screen also takes an `onSignOut` param — a **Sign out** action (`common_sign_out`) rendered as an understated secondary control below Retry, disabled while `isRetrying`. It was added because the screen was otherwise a dead end: an account whose key can't resolve on **this** device previously stranded the whole app behind a Retry that never succeeds, even though a different account would open fine. In `V2App` the handler calls `AuthRepository.signOut()` (which rebuilds the user session scope), then `DatabaseRecoveryState.clearRecovery()`, then recreates the activity. It does **not** delete the local database — the state is scoped to one account and the data stays on disk for a later successful resolve.
- **`KeyMismatchWiped`** overlays `V2DatabaseRecoveryDialog` (`ui/v2/screens/recovery/V2DatabaseRecoveryDialog.kt`) over the nav host (the data is recoverable, unlike the fatal path). The dialog is a non-dismissable 4-state flow (Scanning → Results → Importing → Done) that re-imports orphaned audio, reusing the UI-agnostic V1 `DatabaseRecoveryViewModel` + `RecoveryUiState` — only the V2 surface is restyled.

The fourth surface is the **open still in flight**. Independently of `RecoveryState`, `V2App` collects `SessionDatabaseState.readySessionId` (`states/SessionDatabaseState.kt`) and renders `V2SessionLoadingScreen` (`ui/v2/screens/startup/V2SessionLoadingScreen.kt`) in place of `V2MainNavHost` until `readySessionId == sessionId` — the readiness gate that keeps Main out of a cold `AppDatabase` factory (see [DEK & Database Key Lifecycle](/rollingrecord/app/security/dek-and-db-key)).

<Note>
`V2SessionLoadingScreen` has **no failure branch, by design**. Every way the open can fail already raises a `DatabaseRecoveryState` state — `FatalError`, `DekUnavailable`, or `KeyMismatchWiped` — and the root handles those *above* this point with their own dedicated surfaces. `SessionDatabaseState.markReady` is called only on a successful build, so a throw simply leaves the loading surface up while the recovery branch takes over the root. If the user is looking at this screen, the open is genuinely still in progress.
</Note>
