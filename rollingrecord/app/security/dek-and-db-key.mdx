---
title: "DEK & Database Key Lifecycle"
description: "How the per-user DEK is fetched, cached, Keystore-wrapped, and derived into the SQLCipher database key."
---

Every account has one 32-byte Data Encryption Key (DEK). It is fetched from the `get-user-key` Edge Function, cached in RAM for the session, persisted Keystore-wrapped for offline opens, and derived — via `HKDF(DEK, "rr-db-key-v1")` — into the raw key SQLCipher uses to open the local database. Because the derivation is deterministic, the same account opens the same encrypted database on any device.

## The account DEK: `get-user-key`

`UserKeyApi` (`data/remote/userkey/UserKeyApi.kt`) is an internal Retrofit interface with a single `POST functions/v1/get-user-key` (`FN_GET_USER_KEY`) call. The body is an empty `{}` — identity comes from the Bearer JWT stamped by the shared `aiengine` OkHttp client (App Check + Bearer + app-version interceptors), which this endpoint reuses rather than duplicating transport plumbing. The endpoint lazy-provisions the `user_crypto` row on first call.

`UserKeyApiClient` (`data/remote/userkey/UserKeyApiClient.kt`) wraps that call in `fetch()`, returning a `UserKeyFetchResult`: `Success(dekBase64, kekVersion, …, hasRecoveryCode)`, `SubscriptionRequired(entitlement)` (default `pro_cloud`), `RateLimited`, or `Transient(reason, cause)` for network / 5xx / decode failures. It is the one-shot fetcher, with exactly one side effect: on every 200 it calls `onboardingSignalsProvider().setServerSaysNoRecoveryCode(!decoded.hasRecoveryCode)` so that *whichever* caller triggered the round-trip records the recovery-code answer. Caching is not its job — the shared cache belongs to `UserKeyProvider` (its own KDoc still points at `SessionDekHolder`; that predates the provider).

`GetUserKeyResponse` (`data/remote/userkey/model/GetUserKeyResponse.kt`) is the internal `@Serializable` shape. `dek` is base64 and decodes to exactly 32 bytes; `kek_version` is informational. The same response also carries RR-492 App-Lock PIN sync fields (`pin_verifier_ct` / `pin_verifier_iv`, `pin_settings.auto_lock_ms`, `pin_updated_at`), all nullable and defaulted — the endpoint is not DEK-only. The model mirrors the `smoketest` `UserKeyResponses` type by convention.

The response also carries `has_recovery_code` — the server-authoritative answer to `canonical_users.recovery_code_hash IS NOT NULL`, read by `get-user-key` (`supabase/functions/get-user-key/index.ts`) alongside the DEK because the client already makes this call on every session. It maps to `GetUserKeyResponse.hasRecoveryCode` and is carried forward as `UserKeyFetchResult.Success.hasRecoveryCode`. **Both default to `true`**, matching the server's own fallback when the `canonical_users` select errors: a missing or unreadable field must never make the client conclude the user has no recovery code and put a blocking screen in front of someone who does. The answer is recorded inside `UserKeyApiClient.fetch` rather than at any one call site, so all three callers below report it — see [Recovery Codes](/rollingrecord/app/security/recovery-codes).

## `UserKeyProvider` — the app-scoped single flight

`UserKeyProvider` (`data/remote/userkey/UserKeyProvider.kt`) is an app-scoped, owner-stamped, single-flight front for `UserKeyApiClient.fetch()`. It exists because at an interactive sign-in `get-user-key` is hit by **three** callers that race concurrently — its KDoc records that "server logs showed all three firing within ~225ms, every one starting before any had returned" — and they live in three different lifetimes:

| Caller | File | Lifetime | Consumes |
| --- | --- | --- | --- |
| `AuthRepository.fetchAndPersistDek` | `data/auth/AuthRepository.kt` | App-scoped, runs **before** the `UserSessionScope` exists | `dek` / `kek_version` for the blocking sign-in DEK gate |
| `AppLockRepository.refreshFromServer` (via `SessionDekHolder.fetchUserKey`) | `data/applock/AppLockRepository.kt` | Session-scoped | The `pin_*` verifier / auto-lock LWW reconcile |
| `V2App`'s recovery-code presence check | `ui/v2/V2App.kt` | A composable — can only reach **root-scope** singletons | `has_recovery_code` |

A session-scoped coalescer cannot dedupe those: caller 1 fires while no session scope exists and caller 3 cannot see the session scope at all. Caching the result *after* the first call returns is also too late for a concurrent burst. So the provider lives at the app level — the first caller starts the fetch, the others block on its `Mutex` and read the fresh cache. One network call instead of three, against a `Bucket.UserKeyGet` ceiling of 40 requests per hour (see [get-user-key](/rollingrecord/backend/edge-functions/get-user-key)).

`fetch(authUserId, forceRefresh = false)` runs its whole body under the mutex. It serves the cache only when **all four** of these hold:

| Condition | Why |
| --- | --- |
| `forceRefresh == false` | `forceRefresh` is the explicit "observe a cross-device change now" escape hatch |
| `cached != null` | Only `UserKeyFetchResult.Success` is ever stored |
| `cachedOwner == authUserId` | Owner stamp — never serve one account's key material to another |
| `SystemClock.elapsedRealtime() - cachedAt < TTL_MS` | `TTL_MS = 5 * 60 * 1000L` (5 minutes) |

A **failure is never cached**, so each caller retries on its own path rather than all inheriting one transient error — that is what lets the App Lock fresh-install retry loop eventually succeed.

`cached`, `cachedOwner`, and `cachedAt` are `@Volatile` so `clearForUserSwitch()` can null them **without** taking the mutex: a user switch is on the sign-in critical path and must not block behind an in-flight fetch holding the lock for a full round-trip. Owner-stamping — not the clear — is what guarantees cross-account safety, so a best-effort clear is enough: a missed clear degrades to a cache **miss**, never a cross-account key leak. The provider is registered as a `single` in `di/NetworkModule.kt` and listed in the explicit `UserScopedCacheRegistry` in `di/UserSessionModule.kt`, so `UserSessionManager.switchTo` wipes it before opening the new session scope (see [User session scope](/rollingrecord/app/architecture/user-session-scope)).

Unlike `SessionDekHolder`'s mirror, this cached copy **keeps** its `dekBase64`: a cache hit must be able to hand the DEK to the sign-in provisioning gate, which has no other source for it.

## `SessionDekHolder` — the session cache

`SessionDekHolder` (`data/session/SessionDekHolder.kt`) is a `Closeable` scoped in the `UserSessionScope`, constructed with `userKeyProvider` (not the API client) and the scope's `authUserId`. It caches the plaintext DEK in RAM for the session and resolves `requireDek()` through three tiers under a `Mutex`:

| Tier | Source | Network? | Notes |
| --- | --- | --- | --- |
| 1 | In-RAM `cachedDek` | no | Populated by a prior call this session |
| 2 | `DekKeyStore.loadDek` (Keystore-wrapped) | no | Makes the DB openable **offline** after the first fetch |
| 3 | `fetchUserKeyLocked(forceRefresh = false)` → `UserKeyProvider.fetch` → `UserKeyApiClient.fetch` | yes | On success, persists via `DekKeyStore` for the next cold start |

The session mutex still collapses N concurrent cold-start callers *inside this session*, but it is no longer the single-flight owner — two of the three sign-in callers can't see the session scope, so that job moved up to `UserKeyProvider`.

### The session-local response mirror

`fetchUserKey(forceRefresh = false)` is the session-scoped read of the **full** `get-user-key` response (`mutex.withLock { fetchUserKeyLocked(forceRefresh) }`). `fetchUserKeyLocked` serves `cachedUserKey` while it is fresher than `USER_KEY_TTL_MS` (`5 * 60 * 1000L`, mirroring the provider's TTL); otherwise it calls `userKeyProvider.fetch(authUserId, forceRefresh)`. On a `Success` it stores the response **DEK-redacted** — `cachedUserKey = fetched.copy(dekBase64 = "")` — stamps `cachedUserKeyAt`, and calls `applyDekLocked(fetched)`. The DEK plaintext lives only as bytes in `cachedDek`; there is no reason to hold the base64 secret for the whole TTL window.

So there are two cache layers with the same 5-minute window: `UserKeyProvider` (app-scoped, keeps `dekBase64`, owner-stamped) and this DEK-redacted mirror (session-scoped, so repeat in-session reads don't even re-enter the provider). `forceRefresh` bypasses **both**, which is how App Lock's connectivity-restore re-sync observes a PIN set on another device. Only `Success` is cached at either layer.

`applyDekLocked(fetched)` is the one place a fetched DEK is applied: it base64-decodes, checks `decoded.size == DEK_BYTES` (32), persists via `DekKeyStore.persistDek(context, authUserId, dek, kekVersion)`, sets `cachedDek` / `cachedKekVersion`, and clears `lastDekError`. On failure it zero-fills, records `decode_failed` or `invalid_dek_size` in `lastDekError`, and leaves `cachedDek` null.

`requireDek()` returns a `DekResult`: `Available(dek, kekVersion)`, `SubscriptionRequired(requiredEntitlement)` (non-cloud features stay usable), or `Unavailable(reason)` where `reason` is one of `rate_limited`, `network_error`, `decode_failed`, `invalid_dek_size`, or an upstream code. On the tier-3 `Success` branch it returns `cachedDek` if `applyDekLocked` populated it, else `Unavailable(lastDekError ?: "invalid_dek")` — the `lastDekError` field is what lets the specific decode/size failure surface even when the response itself came from cache. `currentDekFingerprint()` returns the `SHA-256` hex of the resolved DEK, or `null` when it can't be resolved. The holder proactively warms the DEK when a network with internet capability becomes available. `invalidate()` zero-fills the RAM copy (keeping the persisted one); `close()` zero-fills, unregisters the `ConnectivityManager` callback, and cancels the refresh scope. Both also drop `cachedUserKey` / `cachedUserKeyAt` / `lastDekError`, so the next read re-resolves. The plaintext DEK is never persisted in the clear or logged.

## `DekKeyStore` — Keystore-wrapped persistence

`DekKeyStore` (`data/local/security/DekKeyStore.kt`) is the on-device, per-user (`authUserId`-keyed) store of the DEK plus the metadata the key layer needs. It uses two Keystore layers: an `EncryptedSharedPreferences` file (master-key alias `rr_dek_prefs_master_key`) whose entries are themselves an AES-256-GCM Keystore-wrapped DEK (wrapping-key alias `rr_dek_master_key`). Every preference key is suffixed `__<authUserId>` so two accounts on one device never collide.

| Key | Holds |
| --- | --- |
| `dek_ct` / `dek_iv` | Keystore-wrapped DEK ciphertext + GCM IV (base64) |
| `dek_fp` | `SHA-256(DEK)` hex fingerprint |
| `dek_kek_version` | Server KEK version the DEK was wrapped under |
| `db_structure_version` | `1` (legacy random passphrase) or `2` (DEK-derived) |
| `db_keyed_dek_fp` | Fingerprint of the DEK the DB is **currently** encrypted under |

Reads (`loadDek`, `getDekFingerprint`, `getDbStructureVersion`, `getDbKeyedDekFingerprint`) swallow Keystore failures and return `null` / the default — a missing DEK is a recoverable "re-fetch / sign-in" state, never a corruption signal, so it can never reach the wipe path. `persistDek` is best-effort. `commitRekey` is synchronous and **propagates** failure, since a half-written commit would desync the stored fingerprint from the on-disk cipher key. Constants: `DB_STRUCTURE_VERSION_LEGACY = 1`, `DB_STRUCTURE_VERSION_DEK_DERIVED = 2`, `DEK_BYTES = 32`.

Two diagnostic helpers classify a DEK mismatch that bare hashes cannot. `ownerOfFingerprint(context, fingerprint)` returns the locally-known `authUserId` whose persisted DEK has that `SHA-256` fingerprint (else `null`), and `knownAccountCount(context)` counts the distinct accounts with a persisted DEK on this device. Together they separate three cases: (1) the mismatch resolved **another account's** key — a cross-account bug with no benign explanation; (2) the fingerprint is unknown to the device — a server-side re-provision of this account's key; (3) the DB directory was keyed by a different account. Both helpers log only `SHA-256` fingerprints / `authUserId`s / counts / booleans — never key material or user content. `persistDek` uses the same lookup: when the persisted fingerprint changes it logs `newFpOwner` and a `crossAccount` boolean alongside the old and new fingerprints.

## The signed-in database key

For a signed-in session the SQLCipher passphrase is resolved by `DatabaseKeyTransition` (`data/local/security/DatabaseKeyTransition.kt`). Its `resolvePassphraseOrTransition(context, authUserId, dek, dekFingerprint, kekVersion = -1)` structurally validates the DEK, derives `HKDF(DEK, "rr-db-key-v1")` into the raw-key literal `x'<64 hex>'` (SQLCipher uses the 32 bytes verbatim — no KDF — which is what makes the DB deterministic across devices), reads the persisted structure version and keyed fingerprint, and delegates the branch to the pure `decideTransition`. `kekVersion` — the KEK generation the live DEK was wrapped under, `-1` when unknown — is threaded through purely for diagnostics: it appears in the DEK-unavailable failure log so a server-side KEK rotation is distinguishable from a DEK re-provision without correlating two systems by hand.

`decideTransition(dbFileExists, structureVersion, keyedFp, liveFp)` (`data/local/security/DatabaseKeyTransitionDecision.kt`) is Android-free and unit-tested. It returns a `TransitionDecision`:

| Decision | Precondition | Action |
| --- | --- | --- |
| `CreateFreshV2` | no DB file | Room creates a fresh DB under `HKDF(DEK)`; commit v2 metadata |
| `SteadyStateV2` | structure v2 & `keyedFp == liveFp` | Open as-is, no re-key |
| `Unavailable("keyed_fp_unreadable")` | structure v2 & `keyedFp == null` | Refuse — can't prove the key; recoverable |
| `Unavailable("dek_changed_old_key_unavailable")` | structure v2 & `keyedFp != liveFp` | Refuse; recoverable |
| `Unavailable("legacy_db_unsupported")` | a non-v2 file exists | Refuse; RR-489 removed the legacy re-key |

On any `Unavailable` branch, `Result.DekUnavailable` carries a structured `diagnostics: Map<String, String>` alongside `reason`, holding the same moment-of-failure facts the log line reports: `dek.user`, `dek.keyedFp`, `dek.liveFp`, `dek.keyedFpOwner`, `dek.liveFpOwner`, `dek.knownAccounts`, `dek.crossAccount`, `dek.kekVersion`, and `dek.structureVersion`. Every value is a UUID, a `SHA-256` hex, a count, or a boolean — no key material and no user content. The caller in `DatabaseModule` attaches these to a Crashlytics non-fatal, so the facts that decide whether a mismatch is a client bug or a server-side re-provision arrive without waiting for a user to send their log file.

<Warning>
`DatabaseKeyTransition` performs **no KEK rotation and no in-place re-key**. RR-489 removed the old legacy(v1) → DEK-derived(v2) re-key entirely: the transition now only *resolves* a passphrase, and a database that isn't provably v2 fails **safe** — the file is left 100% untouched and routed to the recoverable DEK-unavailable surface, never wiped. Re-wrapping the DEK under a new KEK generation does not change the DEK plaintext, so `HKDF(DEK)` — and therefore the SQLCipher key — is stable across KEK versions; there is no local re-key on rotation.
</Warning>

## The anonymous database key

The signed-out (anonymous) database is never cloud-portable and has no account DEK, so it stays on a random device-bound passphrase produced by `DatabaseKeyManager` (`data/local/security/DatabaseKeyManager.kt`) — a **live** path, not legacy. `getOrCreatePassphrase(context)` generates a 256-bit `SecureRandom` passphrase once, wraps it with an AES-256-GCM Keystore key (alias `rr_db_master_key`) inside `EncryptedSharedPreferences` (`rr_security_prefs`, master alias `rr_prefs_master_key`), and unwraps it on later launches. If the Keystore is unavailable it throws `DatabaseKeyException` — there is no in-app recovery; the user must clear app data.

## `buildAppDatabaseForSession` orchestration

`buildAppDatabaseForSession` in `di/DatabaseModule.kt` runs before Room opens the file. For the anonymous segment it uses the `DatabaseKeyManager` passphrase directly. For a signed-in segment it heals any interrupted restore swap, resolves the persisted DEK via `DekKeyStore.loadDek` (with an off-main-thread inline `SessionDekHolder.requireDek()` self-heal for the cold-start race), runs `DatabaseKeyTransition` with `kekVersion = persisted.kekVersion`, and either opens on `Result.Ready` or — on `Result.DekUnavailable` — calls `DatabaseRecoveryState.flagDekUnavailable(reason)` and throws `DekUnavailableException` **without opening or wiping** the DB. The freshly unwrapped DEK copy is zero-filled after derivation.

The inline `SessionDekHolder.requireDek()` self-heal is **bounded at 45s** (`INLINE_DEK_FETCH_TIMEOUT_MS = 45_000L`, via `withTimeout`). It runs `runBlocking` **inside** the Koin session-scope factory, so a hung fetch would hold the session-scope lock — and therefore every thread resolving any user-scoped dependency, including Main — hostage (the ANR class of 2026-08-30). On timeout `persisted` stays `null`, which routes to the recoverable `DekUnavailable` path and never the wipe path. On the `DekUnavailable` branch, `DatabaseModule` also emits a **deduped** (one per `user` + `reason` per process) Crashlytics non-fatal via `reportDekUnavailableToCrashlytics(...)` carrying the diagnostics map.

That hazard is now **structurally avoided**, not merely bounded. The `scoped<AppDatabase>` binding in `databaseModule` publishes readiness on every successful build — `buildAppDatabaseForSession(...).also { SessionDatabaseState.markReady(sessionId) }`, where `sessionId` is the Koin scope's own `id` (`UserSessionManager` creates each session scope with `scopeId = newSessionId`, so reading it here costs no I/O and can't race a re-pointed `AuthUserStore`). `SessionDatabaseState` (`states/SessionDatabaseState.kt`) exposes `readySessionId: StateFlow<String?>`, and `V2App` withholds `V2MainNavHost` — whose composition synchronously resolves five session-scoped repositories on Main — until `readySessionId == sessionId`, rendering `V2SessionLoadingScreen` (`ui/v2/screens/startup/V2SessionLoadingScreen.kt`) meanwhile while a `Dispatchers.IO` boot effect does the warm-up. Main therefore never enters a cold factory: by the time the nav host composes, every one of those resolutions is a cheap read of an already-constructed instance. `markReady` fires **only** on success (a throw must leave the root on its loading or recovery surface), and the signal is keyed by session id rather than a bare boolean so a sign-out invalidates it automatically — `UserSessionManager.switchTo` also calls `SessionDatabaseState.clear()` when it swaps the scope.

## The DEK-unavailable surface

When the DEK can't be resolved, `V2DekUnavailableScreen` (`ui/v2/screens/recovery/V2DekUnavailableScreen.kt`) is rendered at the root instead of the nav host. It is recoverable: the DB is neither opened nor wiped, and `onRetry` re-attempts the open once the DEK is resolvable (the retry button is disabled while `isRetrying`). See [Database Recovery States](/rollingrecord/app/security/database-recovery) for the full routing.
