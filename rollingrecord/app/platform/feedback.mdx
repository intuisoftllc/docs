title: "Feedback"
description: "The two-kind feedback flow — bug reports and feature requests — sharing one screen, one endpoint, and one rate-limit bucket, with a best-effort log bundle attached to bug reports only."
---

Feedback is a single two-step V2 compose flow that files **two kinds** of submission: a bug report and a feature request. Both are reached from Help & Support, both are free on every tier, and both run through the same screen, the same `feedback` Edge Function, and the same rate-limit bucket. The only real asymmetry is diagnostics: a bug report can attach a merged app-log bundle, a feature request cannot. The client is a thin stack — `V2FeedbackScreen` over `V2FeedbackViewModel`, a Retrofit `FeedbackApi`, a `FeedbackApiClient` that files then best-effort uploads, and a `FeedbackLogBundler` that merges on-device logs into one hashed file.

## The two kinds

`FeedbackKind` (`data/remote/feedback/FeedbackKind.kt`) is the wire contract that decides which table the submission lands in. The kind is fixed at navigation time and carried unchanged through the whole flow — it is a constructor parameter on the ViewModel, never a mutable field, so a user cannot type a bug report and file it as a feature request.

| Kind | `wire` | `acceptsLogs` | Lands in |
| --- | --- | --- | --- |
| `BUG` | `bug` | `true` | the bug queue |
| `FEATURE` | `feature` | `false` | `feature_requests` |

`acceptsLogs` mirrors `acceptsLogAttachment(kind)` on the server: it is not a preference, it is a fact about the destination table — `feature_requests` has no log columns, so only `BUG` ever bundles a log.

The server treats the two wire fields differently, and the client mirrors that split deliberately:

- **Kind is rejected, not defaulted.** An unrecognized `kind` fails the whole submission with `feedback_invalid_kind`. The two kinds live in different tables, and guessing would file a feature request into the bug queue where nobody looking for it would see it. `FeedbackKind.fromWire` is nullable for the same reason — the only producer of the string is this app's own navigation, so a miss is a bug here, and substituting `BUG` would show the bug flow to someone who tapped "Request a feature".
- **Area is normalized, not rejected.** An unknown area is coerced to `other` server-side, so a client that ships a new area ahead of a deploy still files successfully (see [Feedback areas](#feedback-areas)).

Both wire values must match `SUBMISSION_KINDS` and `SUBMISSION_AREAS` in `supabase/functions/_shared/submissions/sanitize.ts`.

## Free on every tier

Filing feedback is how the app learns it is broken or missing something, and the free tier is where sign-in, permission, and onboarding failures concentrate — so neither kind is metered by tier (see the Help & Support block in `app/app/src/main/java/com/intuisoftllc/rollingrecord/data/models/UserTier.kt`). Abuse is bounded instead by `Bucket.Feedback` (`supabase/functions/_shared/gates/types.ts`), whose default ceiling in `supabase/functions/_shared/gates/rate-limit.ts` is `max: 5, windowSec: 3600` — five submissions per hour, **shared across both kinds** because they share the one endpoint. Because the ceiling is the only control, it is what stands in for entitlement gating, and keeping it in the gate chain is what makes even a malformed body count against it.

## Entry points

`V2HelpSupportScreen` (`app/app/src/main/java/com/intuisoftllc/rollingrecord/ui/v2/screens/helpsupport/V2HelpSupportScreen.kt`) renders **two** rows in its "Get Help" section, siblings to Contact Support:

| Row | String key | Icon | Callback |
| --- | --- | --- | --- |
| Submit a bug | `bug_report_entry` | `ic_bug` | `onSubmitBug` |
| Request a feature | `feature_request_entry` | `ic_feature_request` | `onRequestFeature` |

Two rows rather than one "Send feedback" row that then asks which: the user already knows which one brought them here, and making them answer again is a step for the app's benefit. Both sit alongside Contact Support as its structured siblings — same diagnostics, but each files a filterable row instead of an email thread so submissions can be triaged by area.

Navigation routes through `V2Feedback(val kind: String)` (`ui/v2/navigation/V2MainRoutes.kt`). `V2MainNavHost` wires `onSubmitBug` to `V2Feedback(FeedbackKind.BUG.wire)` and `onRequestFeature` to `V2Feedback(FeedbackKind.FEATURE.wire)`, then in the `composable<V2Feedback>` destination resolves the string with `FeedbackKind.fromWire`. A null result pops the back stack rather than falling back to a default — a screen that closes is a far more findable failure than one that quietly shows the wrong flow.

## The screen

`V2FeedbackScreen` (`app/app/src/main/java/com/intuisoftllc/rollingrecord/ui/v2/screens/feedback/V2FeedbackScreen.kt`) is one screen serving both kinds — nothing in the file branches on the kind. The current step is **derived** from the area (`onStepTwo = area != null`), not tracked separately, so there is one source of truth for "which step am I on" and back cannot desync it. Three private composables render the three states:

| Composable | Role |
| --- | --- |
| `PickAreaStep` | Step 1 — a `V2SettingsCard` of `V2SettingsNavRow` items, one per `FeedbackArea` entry, under the standard `LibraryDetailHeader` bar |
| `DescribeStep` | Step 2 — a fixed-height `240dp` `OutlinedTextField` styled like `V2TaskFormSheet`, a diagnostics `V2SettingsToggleRow`, and the reset flow's `PrimaryButton` |
| `SentStep` | Terminal success screen — the kind's icon, success copy, and a bottom-pinned Done; its `BackHandler` routes to `onDone` |

The description field's height (`DESCRIPTION_FIELD_HEIGHT = 240.dp`) is fixed on purpose: a weighted height collapsed the field the moment the keyboard claimed the space, so long text scrolls inside the field and the page scrolls to reach the toggle underneath. There is no character counter — the 12,000-char ceiling exists to bound a hostile payload, not to ration the user.

Submitting opens a `ConfirmActionSheet` (`ui/v2/components/ConfirmActionSheet.kt`) rather than sending straight away: the submission is one-way (no edit, no recall once filed), so the last thing the user sees is the area icon and label it will be filed under plus a two-line excerpt (`bodyMaxLines = 2`) of their own words. On step 2 the `BackHandler` returns to the area list instead of leaving the flow and keeps the typed description intact (`clearArea()` nulls the area but not the text), so changing your mind about the area costs nothing.

### Per-kind copy

Every string and icon that differs between the two kinds is one row of `FeedbackCopy` (`ui/v2/screens/feedback/FeedbackCopy.kt`): the entry label, step-1 title and area prompt, the field label and hint, the diagnostics toggle label and subtitle, the confirm-sheet title and send label, the success title and body, and the glyph (`ic_bug` vs `ic_feature_request`). The `feedbackCopy(kind)` `when` is exhaustive, so a third kind cannot be added without supplying its strings. This table lives in the UI package on purpose — `FeedbackKind` is a wire contract and must not grow presentation concerns.

## Feedback areas

`FeedbackArea` (in `V2FeedbackViewModel.kt`) is the nine-way taxonomy, shared by both kinds: for a bug it is where the problem happened, for a feature request it is where the feature would live, and both answer the same triage question. Each entry carries a `wire` value, a `labelRes`, and an `iconRes`:

| Enum | `wire` | Label string | Icon |
| --- | --- | --- | --- |
| `RECORDING` | `recording` | `common_recording` | `ic_mic` |
| `PLAYBACK` | `playback` | `common_playback` | `ic_play` |
| `LIBRARY` | `library` | `common_library` | `ic_library` |
| `TRANSCRIPTION` | `transcription` | `common_transcription` | `ic_wave` |
| `CONTEXTS_AI` | `contexts_ai` | `feedback_area_contexts_ai` | `ic_brain` |
| `CLOUD_SYNC` | `cloud_sync` | `feedback_area_cloud_sync` | `ic_cloud` |
| `ACCOUNT_BILLING` | `account_billing` | `feedback_area_account_billing` | `ic_profile` |
| `APP_LOCK` | `app_lock` | `common_app_lock` | `ic_app_security` |
| `OTHER` | `other` | `feedback_area_other` | `ic_info` |

The `wire` values must match `SUBMISSION_AREAS` in `supabase/functions/_shared/submissions/sanitize.ts`. Adding an entry is safe in either order — the server normalizes anything unknown to `other`. Renaming an existing `wire` value is **not** safe: submissions from installed clients would silently start landing in `other`.

## `V2FeedbackViewModel`

The ViewModel holds the kind (constructor parameter) plus four state flows — `area` (`StateFlow<FeedbackArea?>`), `description`, `includeDetails` (default `true`), and `submitState` — and derives a fifth. `submitState` is a `FeedbackSubmitState`: `Idle`, `Submitting`, `Sent`, or `Error(messageRes)`.

`includeDetails` is named for what it gates rather than for the log, because what it gates depends on the kind: for a bug report it is the merged app log **and** the device details, for a feature request it is the device details alone. Both kinds ask, so a user filing a feature request never sends device details without being asked just because that flow happens to carry no log.

`canSubmit` is a `StateFlow<Boolean>` — a `combine` of `_area` and `_description` — deliberately **not** a plain getter. As a getter reading `_description.value` it was invisible to Compose: nothing about it was observable state, so the Submit button captured `false` on first composition and never re-enabled. It enables when `area != null` and the trimmed length is at least `MIN_DESCRIPTION_CHARS`.

| Constant | Value | Meaning |
| --- | --- | --- |
| `MIN_DESCRIPTION_CHARS` | `10` | Client-only floor — stops a stray tap or a one-word "broken". The server still accepts anything non-empty |
| `MAX_DESCRIPTION_CHARS` | `12_000` | Mirrors `MAX_DESCRIPTION_CHARS` in `sanitize.ts`; `onDescriptionChanged` truncates rather than rejects |
| `TIER_LOOKUP_TIMEOUT_MS` | `1_500` | How long to wait for the tier before filing without it |

`entitlementRepository` is session-scoped, so it is resolved from `userSessionManager.currentScope` on every read rather than injected once — a sign-out while the screen is open would otherwise leave the ViewModel holding a repository from a dead scope.

`submit()` builds the log bundle off `Dispatchers.IO` **only when** `includeDetails` is on **and** `kind.acceptsLogs` is true, resolves the tier (bounded by `TIER_LOOKUP_TIMEOUT_MS`, with an `"UNKNOWN"` fallback) **only when** diagnostics are on — no point waiting on a lookup it would discard — then maps `FeedbackApiClient.Result` onto `submitState`.

## Wire API

`FeedbackApi` (`data/remote/feedback/FeedbackApi.kt`) is the Retrofit interface for the `feedback` Edge Function. The function name is declared once as `FN_FEEDBACK = "feedback"`, used for the `@POST("functions/v1/" + FN_FEEDBACK)` path and the `@EdgeTag(FN_FEEDBACK)`. The kind travels in the body, not the path, so one endpoint serves both kinds. It rides the shared `aiengine` OkHttp stack (base URL + App Check + Bearer JWT + app-version interceptors) — only the path differs.

`FeedbackRequest` is the wire body:

| Field | Wire name | Notes |
| --- | --- | --- |
| `kind` | `kind` | Chosen kind's `wire` value; the one field with no server-side fallback |
| `area` | `area` | Chosen area's `wire` value; server normalizes unknown to `other` |
| `description` | `description` | The user's text |
| `clientMetadata` | `client_metadata` | `Map<String,String>` of device details; empty when diagnostics are declined |
| `attachLogs` | `attach_logs` | Whether a log is being sent |
| `logSha256` | `log_sha256` | Nullable digest of the bundle |
| `logBytes` | `log_bytes` | Nullable bundle size |

`FeedbackResponse` returns `submission_id` (the row id in whichever table the kind routed to), the echoed `kind`, and an optional `upload_url`. A null `upload_url` is **not** an error — it means no log is being sent (the user declined, the kind carries no logs, or the server couldn't mint one), and the submission is already stored by the time the response returns.

## `FeedbackApiClient`

`FeedbackApiClient` (`data/remote/feedback/FeedbackApiClient.kt`) files the submission, then — on success and only when a bundle exists — does a best-effort `uploadLog()`: a `PUT` of the merged log to the returned signed URL via a **separate bare `uploadClient`**. That upload never throws.

The ordering is the point: the row is written server-side **before** the log exists. So once `submit()` returns success, the submission is safe — a log upload that then fails, times out, or is killed with the app leaves a complete, readable report behind, it just has no attachment. The user is told their submission was sent, because it was. Reversing that order would mean a network blip at the last step discards everything they typed. The upload failure is logged (`save = true`) and swallowed; the bundle file is deleted after the submit either way.

`deviceMetadata` — `app_version_code` / `app_version_name` / `build_type` / `android_release` / `android_sdk` / `device_manufacturer` / `device_model` / `tier` / `locale` — is attached **only when** `includeDiagnostics` is true, and strictly device/app state: no recording titles, no transcript text, nothing the user authored. Tier is the field that earns its place on a feature request: "a Free user wants a cloud feature" and "a Cloud+AI subscriber wants a cloud feature" are different signals about the same ask. `includeDiagnostics` is passed separately from `logBundle` on purpose — a null bundle means "no log is being sent", which happens both when the user declined *and* when bundling simply failed, and inferring consent from a failure would silently strip a consenting user's diagnostics.

`Result` is a sealed interface: `Success`, `RateLimited`, `Offline`, `Failure`. `Timeout` is grouped with `Offline` — to the person filing the submission both mean "try again when the connection is better".

## `FeedbackLogBundler`

`FeedbackLogBundler` (`data/remote/feedback/FeedbackLogBundler.kt`) is an `object` that merges `FileLogger`'s rotating segments into one `cacheDir` file, `feedback-logs.txt`. Only `FeedbackKind.BUG` ever reaches it — a feature request has no log to send and the compose screen never shows the toggle for that kind.

It reads a **distinct** set of two segments — the active auth-user segment plus the `anonymous` (pre-sign-in) segment — each clearly delimited with `BEGIN`/`END` markers. The anonymous segment is included because auth and sign-in bugs are written there, and that segment is unreachable from both the in-app log viewer and the support-email export, which only ever read the current user's files. Within a segment, files are read oldest-first.

The result is capped at `MAX_BUNDLE_BYTES = 8 * 1024 * 1024` (8 MiB — the destination bucket allows 25 MiB, so a legitimate upload can never be rejected for size). When the sources exceed the cap it trims from the **front** (`trimToTail`) to keep the newest tail, since a bug is reported after it happens and the tail is what describes it. `build(context)` returns a `Bundle(file, sha256, byteCount)` with a streamed SHA-256 so a multi-megabyte bundle never lands in memory whole, and it never throws — a failure returns `null`, and the caller submits without an attachment.

## Wiring

`FeedbackApi` and `FeedbackApiClient` are wired in `app/app/src/main/java/com/intuisoftllc/rollingrecord/di/NetworkModule.kt`. `FeedbackApi` is created from the `named("aiengine")` Retrofit. `FeedbackApiClient` is built with a **bare** `OkHttpClient` (a 2-minute `callTimeout`, no interceptors) for the signed-URL log upload, so the `PUT` does not carry `Authorization` or App Check headers — the signature is the whole authorization, and stamping the user's JWT onto a Storage host would be wrong. This is the same pattern as the `audio_signed_url` upload client.

`V2FeedbackViewModel` is a parameterized factory in `ViewModelModule.kt` (`viewModel { (kind: FeedbackKind) -> ... }`): the kind is passed in via `parametersOf(kind)` from the screen, and because each kind is its own nav destination, each gets its own `ViewModelStoreOwner` and its own instance.
