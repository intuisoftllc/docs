The `evalmode` package (`src/debug/` only) is a faithful Kotlin port of the Python `evals/` harness, decided 2026-07-29, that runs entirely on-device inside the debug build. Its system under test is the **literal production KB-chat loop** — not a re-implementation — so a run exercises the same `AgentLoop`, real Room, real `AndroidToolExecutor`, and live `ai-engine` a user's chat would. It is reached from `DevModeScreen`'s "AI evals" row via the `EvalMode` route.

## Composition root

`EvalComponent` (`evalmode/EvalComponent.kt`) is the debug-only composition root. `createViewModel()` pulls the handful of app-level singletons it needs — `Context`, `UserSessionManager`, `RevenueCatManager`, `AuthRepository`, `AiEngineClient` — from the global Koin instance and constructs the `EvalViewModel` graph directly. There is **no debug Koin module and no `App.kt` change**; the whole harness stays in `src/debug`.

## Fail-closed access

Evals seed fixtures into — and run the real production path against — the signed-in account's **live Room database**, and they cost real money (live `ai-engine` calls plus direct-Anthropic judge calls). `EvalAccess` (`evalmode/access/EvalAccess.kt`) is therefore fail-closed: `check()` returns `Authorized` only when all three hold.

| Guard | Source of truth | `DeniedReason` when unmet |
| --- | --- | --- |
| Signed in | `AuthRepository.currentAuthState()` | `NOT_SIGNED_IN` |
| Holds the `developer` RC entitlement | `RevenueCatManager` active entitlements | `NOT_AUTHORIZED` |
| Email is a Clerk test account (contains `+clerk_test`) | the signed-in email | `NOT_TEST_ACCOUNT` |

The `+clerk_test` marker is the load-bearing data-safety guard: because seeded fixtures live in whatever account is signed in, requiring a dedicated throwaway test identity guarantees a run can never touch or corrupt a real user's data. Any `Denied` result renders the access screen — no run, no seeding, no spend.

## Run pipeline

`Runner` (`evalmode/core/Runner.kt`) orchestrates a run. After the access check it loads the cases, then drives each through a four-stage pipeline with bounded parallelism.

| Stage | Component | Outcome |
| --- | --- | --- |
| access | `EvalAccess.check` | `Authorized`, or `Denied` → the access screen |
| corpus | `CorpusStrategy.prepare` | `Ready` (run) or `Skip` (SKIP with an actionable reason) |
| execute | `OnDeviceSystemUnderTest.call` | `ActualOutput` from the real `ask()` loop, or an error → `SYSTEM_ERROR` |
| judge | `SuiteRegistry.judgeFor` → `Judge.evaluate` | a `Verdict`; a null judge records `UNCERTAIN` |
| record | `CaseProgress` + `CostLedger` | terminal status; a FAIL/UNCERTAIN on a case tagged `is_flake` becomes `FLAKED` |

A `Semaphore` caps in-flight cases at `EvalConfig.MAX_CONCURRENCY` (4). If **any** case declares fixtures, `Runner` forces `effectiveConcurrency = 1` for the whole run — seeded cases share the one per-user DB, so parallel execution could let one case's real search surface another's seeded rows. Shared run state lives in a `ConcurrentHashMap` and a `MutableStateFlow`, and cost in a lock-free `CostLedger`; all three are thread-safe, per the eval-harness thread-safety rule. The run supports resume from an OS-kill checkpoint (`resumeDone` / `resumeCostUsd`). A thrown SUT error records `SYSTEM_ERROR`; a null judge records `UNCERTAIN`; both keep the pipeline running end to end.

## `OnDeviceSystemUnderTest`

`SystemUnderTest` (`evalmode/core/SystemUnderTest.kt`) is the production-call surface — a port of the Python `system.py` ABC, whose docstring explicitly anticipated an in-process implementation ("call the logic directly without an HTTP round-trip"). `OnDeviceSystemUnderTest` (`evalmode/systemundertest/OnDeviceSystemUnderTest.kt`) is that implementation made real: it resolves the same `ContextCardRepository` the KB-chat ViewModel uses from `UserSessionManager.currentScope` and calls `ask(...)`, so the `AgentLoop`, the real `AndroidToolExecutor` (reading real Room), the live `ai-engine`, and the signed-in identity all execute for real.

To let the structural judges run on-device, the SUT drives `ask()` with a unique `threadId` and `DevFlags.captureKbChatTraces` enabled (ref-counted and atomic across parallel calls), then reshapes the captured rounds and tool calls into a synthetic `_session` block on `actual.body` — `round_count`, `terminal_reason`, `all_tool_calls`, `all_tool_results`, and a per-round `rounds` array. `session.follow_ups` are driven as successive turns on the same `threadId`, accumulating conversation history exactly as the app does, so the trace aggregates every round of the session. It sums the agent's real `ai-engine` token spend across turns and prices it as `PRODUCTION_MODEL` (Haiku) into the `CostLedger`.

| Operation | Handling |
| --- | --- |
| `kb_query` | the real on-device agent loop via `ContextCardRepository.ask` (the bulk of the suites) |
| `template_moderation` | the standalone `AiEngineClient.templateModeration` call; APPROVED/REJECTED verdict + reason surfaced into `body` |
| `extract` | returns an honest error — extraction runs server-side, so its raw `saveSection`/`saveTasks` tool calls aren't observable on-device |

`ActualOutput` carries the response `body`, latency, token counts, an optional `model` / `stopReason`, and an `error`; a non-null `error` short-circuits judging into a synthetic `system_error` FAIL.

## Cases and suites

`RawCase` (`evalmode/core/Case.kt`) is the bundled JSON shape — `id`, `input`, `expected`, `tags`, `notes`, optional `session`, `is_flake`, `preconditions` (live-suite only), and `fixtures` (seeded-suite only). `CaseLoader` (`evalmode/data/CaseLoader.kt`) reads them from the debug APK's `AssetManager` at `assets/evals/suites/<suite>/{small,med,large}/` (each file a JSON array of `List<RawCase>`) and enriches each into a `Case` with its suite, `TokenBucket`, and source path; a duplicate case id within a suite throws, naming both source assets, mirroring the Python loader. `TokenBucket` maps `SMALL` (`< 500` tokens) / `MED` (500–5,000) / `LARGE` (5,000+) to the three asset subdirectories.

`SuiteRegistry` (`evalmode/suites/SuiteRegistry.kt`) resolves the `Judge` per case (the Kotlin analog of each Python `judge_for_case`) — judge choice keys on the case's `tags` and `expected.judge_chain`, not on the suite alone. Most suites use the "standard fan-out": an `AllOf(structural judges…)` combined with the LLM tier `Cascade(MinConfidence(LlmJudge(Sonnet), 0.85), LlmJudge(Opus))`, unless the case opts out via `judge_chain`. The LLM tier self-SKIPs when `llm_rubric` is absent or the judge key is unset.

| Suite | Judge composition |
| --- | --- |
| `kb_chat` | per-tag: capability listing (`ListShape` + `Keywords` + `Contains`), factual recall (`Keywords` + `Length`), or free-text quality (LLM cascade) |
| `abstention` | standard fan-out + `FaithfulnessJudge` |
| `context_architecture` | standard fan-out (+ `ToolCallSequence`) + `Faithfulness` |
| `efficiency` | `WasteThreshold` + `RoundBudget` + `MustNotCallTool` (opt-out `waste_only`) |
| `extract_template` | `ToolCall` spine + LLM cascade + `GroundedExtraction` (opt-out `deterministic_only`) |
| `kb_chat_session` / `kb_chat_session_live` | `RoundBudget` + `MustCall`/`MustNotCall` + `ToolCallSequence` (+ `Contains`) |
| `long_recording` / `multi_recording` / `source_attribution` / `tool_correctness` | `RoundBudget` + `MustCall`/`MustNotCall` + `ToolCallSequence` + `Contains` + LLM cascade |
| `rag_real_content` | the above plus `RetrievalRecall@K` + `Precision@K` + `MRR` |
| `response_variety` | `RoundBudget` + `MustCall`/`MustNotCall` + LLM cascade |
| `security` | deterministic gate, bare LLM cascade (security-tagged), or `Keywords` |
| `template_moderation` | `BodyFieldJudge` (single-shot) |

## Corpus and fixture seeding

`CorpusStrategy` (`evalmode/core/CorpusStrategy.kt`) is the seam that resolves the Room corpus a case runs against before the SUT. `prepare(case)` returns `Ready` or `Skip(reason)`. `SeededCorpus` (`evalmode/corpus/SeededCorpus.kt`) is the active strategy: it seeds a case's `fixtures` into Room and tears them down, tracking seeded ids per fully-qualified case id in a `ConcurrentHashMap`; a case with no fixtures is pass-through, making it a safe superset of the phase-1 `PassThroughCorpus`. A `LiveCorpus` strategy is **not implemented** — it exists only as a named future Phase-6 strategy in the `CorpusStrategy` KDoc (it *would* check `case.preconditions` against the real DB and SKIP, never FAIL, when they are unmet). Today the `corpus/` package holds only `SeededCorpus` and `FixtureSeeder`, with the `CorpusStrategy` interface and `PassThroughCorpus` living in `CorpusStrategy.kt`.

`FixtureSeeder` (`evalmode/corpus/FixtureSeeder.kt`) writes a case's scratch corpus into the signed-in **test** account's real Room DB, every row a real row: a `RecordingEntity` pointing at a real Opus file (copied from `assets/evals/audio/sample.ogg`), a fabricated `DONE` `TranscriptEntity` (auto-indexed into `transcript_fts` by a DB trigger), and real `ContextEntity` + `ContextRecordingEntity` membership. Every seeded id carries the `ID_PREFIX` `eval-seed-`, and teardown deletes exactly those ids — a run can never touch a real recording. Date-sensitive fixtures can set `recorded_at_ms` or `recorded_days_ago`.

## Judges and verdicts

A `Judge` (`evalmode/core/Judge.kt`) takes a `JudgeContext` (the case, the `ActualOutput`, and the shared `CostLedger`) and returns a `Verdict`. `evaluate` is `suspend` because LLM judges make network calls; the contract forbids throwing on disagreement — a judge returns `UNCERTAIN` for ambiguity and `SKIP` for inapplicability. A `Verdict` (`evalmode/core/Verdict.kt`) has a `VerdictKind` of `PASS` / `FAIL` / `UNCERTAIN` / `SKIP`, a confidence in `[0,1]`, a reason, the judge name, a dollar cost, and optional structured details. `PASS`/`FAIL` are terminal (they halt a `Cascade`); `UNCERTAIN` and `SKIP` advance one.

The judge families ported so far:

- **Chain primitives** (`judges/Chains.kt`) — `Cascade`, `AllOf`, `AnyOf`, `Majority`, `MinConfidence`. Each is itself a `Judge`, so they nest arbitrarily. `Cascade` tries in order (PASS/FAIL halts, UNCERTAIN/SKIP advance); `AllOf` is FAIL on any FAIL, else UNCERTAIN on any UNCERTAIN, else SKIP if all SKIP; `MinConfidence` rewrites a below-threshold PASS/FAIL as `UNCERTAIN` so a cascade escalates Sonnet → Opus.
- **Deterministic** (`judges/Deterministic.kt`) — zero-cost pure judges: `ExactMatchJudge`, `ContainsJudge`, `KeywordsJudge`, `RegexJudge`, `LengthJudge`, `ListShapeJudge`, `BodyFieldJudge` (asserts body scalar fields; used by `template_moderation`), and `ToolCallJudge` (asserts `body.tool_calls` counts and `saveSection` title constraints — the `extract_template` spine). Each SKIPs when its `expected` key is absent, so many judges share one `expected` object.
- **Session-structural** (`judges/SessionJudges.kt`) — pure judges over the synthesized `actual.body._session` trace: `MustCallToolJudge`, `MustNotCallToolJudge`, `RoundBudgetJudge` (min/max/`allowed_terminals`), `ToolCallSequenceJudge` (subsequence match), `WasteThresholdJudge`. They SKIP when there is no `_session` block (a single-shot case).
- **Retrieval** (`judges/Retrieval.kt`) — `RetrievalRecallAtK`, `RetrievalPrecisionAtK`, `RetrievalMRR`. They parse retrieved chunk ids from the `=== chunk <id>` headers the production snippet tools emit into `_session.all_tool_results`, then score against `expected.gold_chunk_ids`. Used by `rag_real_content`.
- **LLM-as-judge** (`judges/Llm.kt`) — `LlmJudge` reads `expected.llm_rubric` (SKIP if absent), renders the actual output (a full round-by-round session transcript when `_session` is present, marking user-visible `end_turn` rounds vs internal-scratch tool-use rounds since Supabase Edge Functions don't stream), asks the judge model for a `{verdict, confidence, reason}` JSON, and records cost. An infra failure (network / rate-limit / missing key) SKIPs so a flaky call never fails a clean run; `extractJsonObjectText` salvages the JSON from fenced or prefixed responses.
- **Faithfulness / grounding / fuzzy / semantic** — `FaithfulnessJudge` (`judges/Faithfulness.kt`) decomposes an answer into atomic claims and checks each against `expected.faithfulness_source` (a correct abstention with no claims passes); `GroundedExtractionJudge` (`judges/GroundedExtraction.kt`) checks extraction tool-call fields against `case.input.input.transcript`; `LevenshteinJudge` + `SetSimilarityJudge` (`judges/Fuzzy.kt`) do close-enough string comparison; `EmbeddingSimilarityJudge` (`judges/Semantic.kt`) is a parity stub that always SKIPs, matching the Python `semantic.py` which never wired an embedding judge.

## Mocked tools

When a session case declares `session.mock_tools`, `OnDeviceSystemUnderTest` hands the real agent loop a `MockToolExecutor` (`evalmode/mocks/MockToolExecutor.kt`) — an `agentcore` `ToolExecutor` that swaps **only** the tool-result bytes. The server prompt, round budget, LLM, threading, tool-call parsing, and `ask()`'s own FTS prefetch all still run real. `MockToolRegistry` (`evalmode/mocks/MockToolRegistry.kt`, a byte-faithful port of `mock_tools.py`) resolves each `tool_use` block against loose / explicit / staged mock specs (match operators `exact`, `_contains`, `_in`; a sticky-last stage clamp; `READ_ONLY_TOOL_DEFAULTS` for unmocked reads; a `MockNotFound` for an unmocked **write** tool, which surfaces up through `AgentLoop` as an error outcome — the on-device equivalent of the Python `SESSION_ERROR` hard-stop). A case without `mock_tools` is always the full real path, so the opt-in can never become a catch-all.

## Run state and results

`EvalRunState` (`evalmode/core/EvalRunState.kt`) is the single sealed state the dashboard observes; `Runner` is its only writer — `Idle`, `CheckingAccess`, `Denied`, `LoadingCases`, `LoadFailed`, `Running`, `Done`, `Aborted`, `Failed`. Per-case status runs `PENDING` → `PREPARING_CORPUS` → `RUNNING` → `JUDGING` → a terminal `PASS` / `FAIL` / `UNCERTAIN` / `SKIP` / `FLAKED` / `SYSTEM_ERROR`. `RunCounts` drives the segmented bar — only `passed` (green) and `failed` (red) render as bar segments; `uncertain`, `skipped`, and `flaked` are numbers.

`EvalViewModel` (`evalmode/ui/EvalViewModel.kt`) owns the `Runner`, exposes its live state plus a verbose log and the discovered suites, and offers `runAll` / `runSuite` / `runBucket` as single-flight. It checkpoints the accumulated results as each case completes (so an OS process-death loses at most the one in-flight case), persists the final or aborted report via `ResultWriter` under `NonCancellable` so a mid-run back-out loses nothing, and offers Continue / Save / Discard when it recovers an interrupted run on the next launch. `EvalDashboardScreen` (`evalmode/ui/EvalDashboardScreen.kt`) renders the run dashboard, a verbose Console overlay, a Results browser, and the access-denied screen.

`ResultWriter` (`evalmode/results/ResultWriter.kt`) writes a per-run results JSON to `{getExternalFilesDir}/evals/results/<yyyy-MM-dd>/<uuid>.json` (adb-pullable), with per-case `id` / `suite` / `status` / `verdict` / `reason` for the Python parity gate, plus the checkpoint/resume file that lives outside the results dir. `EvalResultStore` reads those files back for the Results browser and can upload them to `serve_apk.py` when `EvalConfig.uploadUrl` is set.

## Models and pricing

`EvalConfig` (`evalmode/EvalConfig.kt`) mirrors the constants in the Python `config.py`: `MAX_CONCURRENCY = 4`, `DEFAULT_CONFIDENCE_THRESHOLD = 0.85`, `DEFAULT_PASS_FLOOR = 0.95`, the assets root, and the model ids and pricing below (worst-case PAYG rates, no discounts, so real cost is always ≤ reported). The judge key (`judgeAnthropicKey`) and upload URL come from debug-only `BuildConfig` fields sourced from `.env.local`; when the key is blank, `LlmJudge` SKIPs cleanly rather than crashing.

| Role | Model id | Worst-case PAYG price (in / out per 1M tokens) |
| --- | --- | --- |
| Production (agent under test) | `claude-haiku-4-5-20251001` | $1.00 / $5.00 |
| Judge (first tier) | `claude-sonnet-4-6` | $3.00 / $15.00 |
| Arbiter (escalation) | `claude-opus-4-6` | $15.00 / $75.00 |

The same `agentcore` `AgentLoop`, `ToolExecutor`, `ToolCall`, and `ToolResult` contract (`app/agentcore`) drive both production KB chat and the on-device SUT — which is precisely what makes the eval exercise the literal production loop rather than a stand-in. See [Agent Loop & Tool Contract](/rollingrecord/app/ai/agent-loop).
