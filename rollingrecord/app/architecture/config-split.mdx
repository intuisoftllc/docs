---
title: "Client vs Server Configuration"
description: "The split between client-only Firebase Remote Config (ClientConfig) and server-authoritative Supabase server_config (ServerConfig), and their fetch/apply managers."
---

Every config value lives in exactly one store. Client-only knobs live in `ClientConfig` (fetched from Firebase Remote Config); server-authoritative knobs live in `ServerConfig` (fetched from the Supabase `server-config` Edge Function). Both objects live in the `app/agentcore` module and hold `private DEFAULT_*` constants, `@Volatile var` fields with `private set`, and an `update()` applier. The `DEFAULT_*` values apply only on first-ever cold start or a cache miss — once the server responds, the server always wins.

<Note>
`ClientConfig` and `ServerConfig` are in the `app/agentcore` module (`com.intuisoftllc.rollingrecord.config`), so the same objects compile into the eval runner. The `app/app` config package holds only the two managers. CLAUDE.md's references to a `RemoteConfig.kt` and an `app/app` `ServerConfig.kt` are stale — `RemoteConfig` was renamed `ClientConfig` and moved to `agentcore`.
</Note>

## Store responsibilities

| Store | Object (module) | Manager | Holds |
| --- | --- | --- | --- |
| Firebase Remote Config (client-only) | `ClientConfig` (`agentcore`) | `ClientConfigManager` (object) | client-loop limits, on-device similarity thresholds/margins, moderation toggle, reconcile cadence |
| Supabase `server_config` (server-authoritative) | `ServerConfig` (`agentcore`) | `ServerConfigManager` (class) + `ServerConfigDataSource` | token ceilings, monthly usage caps, feature kill-switches, storage quotas, trash retention, medical multiplier, min-supported-version, embedding model/dims |

## `ClientConfig`

`ClientConfig` (`app/agentcore/src/main/kotlin/com/intuisoftllc/rollingrecord/config/ClientConfig.kt`) is an `object` holding only genuinely client-only values — the ones that can't be practically enforced server-side without inspecting the opaque Claude message array, plus the similarity thresholds on-device code uses to compare **server-produced** embedding vectors. Fields include:

- `kbChatMaxHistoryPairs` (9), `aiChatMaxTranscriptSnippets` (3) — client-loop limits.
- `topicSearchThreshold` (0.48f), `sectionSemanticThreshold` (0.50f), `semanticSearchMargin` (0.02f), `semanticSearchResultCap` (8), `semanticSnippetChunkCount` (3) — on-device similarity dials.
- `blueprintModerationEnabled` (true) — client-only moderation toggle.
- `reconcilePeriodicIntervalHours` (4), `reconcileForegroundDebounceMinutes` (60) — drift-handshake cadence.

It exposes `defaults(): Map<String, Any>` (used by the manager's `setDefaultsAsync`), `update(values: Map<String, Any>)` (a partial applier — any absent key keeps its current value), and `KEY_*` constants matching the Firebase dashboard keys.

<Note>
Model selection moved fully server-side in RR-164 — `ClientConfig` holds **no** model allowlist or preference, and the client never picks, sends, or validates model names.
</Note>

## `ServerConfig`

`ServerConfig` (`app/agentcore/src/main/kotlin/com/intuisoftllc/rollingrecord/config/ServerConfig.kt`) mirrors the `public = true` rows of the Supabase `server_config` table. Callsites read fields directly — `ServerConfig.extractionMaxInputTokens` — with no injection. Its fields cover:

- **Token ceilings** — `extractionMaxInputTokens` (72,000), `kbChatMaxInputChars` (1,800), `blueprintMaxTokens` (4,200), `kbChatMaxToolRounds` (3), and more.
- **Monthly caps** — Pro+Cloud / Cloud+AI transcription minutes (480 / 1200), `aiQueriesPerMonth` (150), `synthesesPerMonth` (72), `cloudAiExtractionMinutesPerMonth` (1800).
- **Feature flags** — `kbChatEnabled` / `aiExtractionEnabled` (each with a `StateFlow` mirror so Compose can recompose on a kill-switch flip), `foundersEditionAvailable`.
- **Storage quotas** — `cloudBackupQuotaProCloudBytes` / `cloudBackupQuotaProCloudAiBytes` (Long).
- **Other dials** — `trashRetentionDays` (30), `medicalModeUsageMultiplier` (1.35), `minSupportedAppVersionCode` (0), `embeddingModel` / `embeddingDimensions`.

`update(values: Map<String, String>)` applies a partial or full map; invalid strings are ignored (the current value is kept rather than reset to the default). `setFeatureDisabled(feature)` / `setFeatureEnabled(feature)` are the RR-118 kill-switch mirror, called from `AiEngineClient` on a `feature_disabled` response (or a success) so the UI hides/shows a feature within a few frames instead of waiting for the next config fetch.

## `ClientConfigManager`

`ClientConfigManager` (`config/ClientConfigManager.kt`) is an `object`. `fetchAndApply(onApplied)` sets the Firebase min-fetch interval (0s in debug, 3600s in release), calls `setDefaultsAsync(ClientConfig.defaults())`, then `fetchAndActivate()`, then `ClientConfig.update(buildValuesMap(rc))`; `onApplied` drives `AppVersionGate` re-evaluation. `buildValuesMap` maps each RC key to its typed value (Firebase stores ints as Long and floats as Double). If the fetch fails, the in-app defaults stay in effect.

## `ServerConfigManager`

`ServerConfigManager` (`config/ServerConfigManager.kt`) is a **class** (not an object) because it needs injected dependencies — `SupabaseApi` and `ServerConfigDataSource`. Its log TAG is `"SupabaseConfig"`.

<Note>
The class is named `ServerConfigManager` — its log TAG and some internal comments say "SupabaseConfig" / "SupabaseConfigManager", and CLAUDE.md's name `SupabaseConfigManager` does not match the actual class name.
</Note>

`fetchAndApply(force, onApplied)` runs in four steps:

1. Apply the cached values from `ServerConfigDataSource` instantly and call `onApplied` (so an offline relaunch can re-evaluate the version floor without waiting for the network).
2. TTL check — skip the network fetch when `force = false` and the cache is fresh. The active TTL tightens from `NORMAL_TTL_MS` (6h) to `DISABLED_TTL_MS` (30m) whenever a kill switch is off, so re-enablement propagates faster.
3. Network fetch via `api.getServerConfig()`.
4. On success, `ServerConfig.update(fresh)`, call `onApplied`, and persist to the DataSource. On any failure, log and proceed on cached/default values.

Cold start passes `force = true` so a new install sees the latest values immediately.

## `ServerConfigDataSource`

`ServerConfigDataSource` (`data/local/ServerConfigDataSource.kt`) is an app-level single DataStore cache of the `server_config` map: `getAll()` / `putAll()` / `getLastFetchAtMs()` / `setLastFetchAtMs()`. It lets values persist across cold starts and apply instantly before the network fetch completes.

## Startup wiring

`App.onCreate` kicks both fetches, best-effort:

```kotlin
ClientConfigManager.fetchAndApply(onApplied = {})
// ...on Dispatchers.IO:
serverConfigManager.fetchAndApply(force = true) {
    getKoin().get<AppVersionGate>().reevaluate()
}
```

The app is fully functional on the baked-in `DEFAULT_*` values if either fetch fails. See [Application Shell & Entry Points](/rollingrecord/app/architecture/app-shell).
