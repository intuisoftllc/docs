The active UI is 100% Jetpack Compose under `ui/v2`, rooted at `V2App`. `V2App` wraps everything in the V2 theme, observes auth state to drive session switching, and branches three ways on the session id and the database-readiness signal — the anonymous login flow, a session-loading surface, or the signed-in main graph — stacking recovery, onboarding, permissions, App-Lock, and version-gate overlays above whichever nav host is mounted.

## `V2App` — the composition root

`V2App` (`ui/v2/V2App.kt`) is the top-level `@Composable`. Its parameters are the one-shot nav latches threaded from `MainActivity` (`navigateToScheduleList` / `navigateToRecording` / `navigateToAllRecordings` / `navigateToUpgrade`, `externalAudioUri`, and their `onConsumed` callbacks). The theme comes from `koinInject<ThemePreference>()` — an app-level indirection (`data/repository/ThemePreference.kt`) whose `darkMode` flow re-resolves the session-scoped `UserSettingsDataSource` on every `sessionIdFlow` emission, so the theme follows the **account** while still being readable from a composable that outlives every session and also wraps the pre-sign-in login flow. Signing out falls back to `UserSettingsDataSource.DEFAULT_DARK_MODE` (`"system"`), which is what stops the login screen inheriting the last user's colors. The flow is `flowOn(Dispatchers.IO)` precisely so that scope resolution never lands on Main. The collected value drives `RollingRecordV2Theme`.

Inside, a `LaunchedEffect` collects `AuthRepository.authState` and drives session switching:

- **`SignedIn`** — sets `AuthUserStore.setCurrentUserId(...)` **before** `switchTo` (so the new scope's DataStore/DB factories see the correct user id), then either swaps immediately for a returning user, or defers the swap behind a recovery-code onboarding overlay for a new account / interrupted acknowledgement.
- **`SignedOut`** — clears `AuthUserStore` and calls `sessionManager.switchTo(null)`.
- **`Loading`** — no-op.

<Note>
The auth-state observer that calls `UserSessionManager.switchTo` lives here in `V2App.kt` for the V2 surface — **not** in `AppNavHost`. `UserSessionManager`'s own KDoc still references `AppNavHost`; that describes the legacy V1 path.
</Note>

Below the overlays, the body is a **three-way branch**:

| Condition | Mounted |
| --- | --- |
| `sessionId == AuthUserStore.ANONYMOUS_DIR` | `V2LoginNavHost` |
| signed in, `SessionDatabaseState.readySessionId != sessionId` | `V2SessionLoadingScreen` |
| signed in and DB-ready | `V2MainNavHost` (wrapped in `Modifier.blur(20.dp)` while the App-Lock overlay is up or the lock decision is still resolving) |

### The session-database readiness gate

`V2MainNavHost` resolves five session-scoped repositories during composition — i.e. on Main — and each resolution runs the `AppDatabase` Koin factory synchronously under the session scope's `ScopedInstanceFactory` lock, a factory that can spend tens of seconds on the inline per-user DEK fetch. Composing the nav host before that database exists parks Main for the whole open and ANRs the app.

So `V2App` does two things. A `LaunchedEffect(sessionId)` warms the database off the main thread — `withContext(Dispatchers.IO) { sessionManager.currentScope.get<AppDatabase>() }`, skipped for the anonymous session and wrapped in `runCatching` (every way the open can fail already raises a `DatabaseRecoveryState`, and those surfaces own the retry). And the branch above withholds `V2MainNavHost` until `SessionDatabaseState.readySessionId` (`states/SessionDatabaseState.kt`) equals the current `sessionId`, showing `V2SessionLoadingScreen` (`ui/v2/screens/startup/V2SessionLoadingScreen.kt`) in the meantime. By the time the nav host composes, every one of those resolutions is a cheap read of an already-constructed instance.

`V2SessionLoadingScreen` is deliberately minimal — a `CircularProgressIndicator` plus `R.string.startup_unlocking_library` — and has **no failure branch**: a failed open surfaces through `DatabaseRecoveryState`'s dedicated screens above this point, so if this screen is what the user sees, the open is genuinely still in flight.

### Overlays stacked above the nav host

`V2App` renders these in a `Box` above whichever nav host is mounted:

| Overlay | Driven by | Purpose |
| --- | --- | --- |
| `V2FatalDbErrorScreen` | `DatabaseRecoveryState` `FatalError` | Replaces the whole tree on a non-key DB-open failure. |
| `V2DekUnavailableScreen` | `DatabaseRecoveryState` `DekUnavailable` | Retry surface; resolves the DEK then `recreate()`. |
| `V2FirstPullProgressOverlayHost` | RR-228 initial `/sync/pull` | Covers empty Home for a cloud-eligible user during first pull. |
| `V2DatabaseRecoveryDialog` | `DatabaseRecoveryState` `KeyMismatchWiped` | Re-imports on-disk audio after a key-mismatch wipe. |
| `V2OnboardingOverlay` (single slot) | `pendingOverlay` | One onboarding moment at a time — recovery-code save today. |
| `V2PermissionsScreen` | device `permissionsSetupDone` flag | First-launch, one-time permission setup. |
| `V2LockOverlay` (+ forgot-PIN, logout sheet) | `AppLockController.phase == LOCKED` | App-Lock PIN / biometric unlock. |
| `V2RecordingInterruptedSheet` | `RecordingInterruptedState` | Post-kill recovery sheet; waits out the lock. |
| `V2BlockingUpdateScreen` | `AppVersionGate.State.NeedsUpdate` | Hard version-floor block, drawn last. |

`V2SessionLoadingScreen` is **not** in this list. It is a branch of the nav-host selection above, not an overlay drawn on top of one — nothing is mounted underneath it, which is the entire point: the surfaces it replaces are exactly the ones whose composition would resolve user-scoped dependencies on Main.

### The onboarding overlay slot

`V2OnboardingOverlay` (`ui/v2/screens/onboarding/`) is a sealed type for the single `pendingOverlay` slot. Its one variant today is `RecoveryCode(code, email, isError)`, which renders `V2RecoveryCodeSaveScreen` and defers the session swap until the user acknowledges the code via `RecoveryCodeApiClient.generateRecoveryCode` / `acknowledgeRecoveryCode`. Adding a new onboarding moment is a new sealed-class variant plus a render branch.

The `SignedIn` observer enqueues that overlay when **any** of three triggers fires:

| Trigger | Source | Covers |
| --- | --- | --- |
| `V2OnboardingSignals.nextSignInIsNewAccount` | set by `V2LoginViewModel` before OTP verify | A brand-new account completing sign-up on this device. |
| `DeviceSettingsDataSource.pendingRecoveryAckUserId` matches the signing-in user | persisted before the generate call | An acknowledgement interrupted by a kill, dead battery, or network failure. |
| `V2OnboardingSignals.serverSaysNoRecoveryCode` | `get-user-key`'s `has_recovery_code == false`, read during the sign-in DEK fetch | An account that missed the sign-up window entirely — onboarding skipped, a crash mid-flow, a fresh device. |

The first and third are `@Volatile` flags read-and-cleared on every `SignedIn` arrival, so a stale value can't re-trigger a later session. `serverSaysNoRecoveryCode` is the server-authoritative backstop: the other two are only ever written on the device that ran sign-up, and a recovery code is the only way back into an account, so the authority for "do you have one" has to be the server. It defaults `false` so a fetch that never ran cannot fabricate a blocking prompt.

## `V2LoginNavHost` — the anonymous flow

`V2LoginNavHost` (`ui/v2/navigation/V2LoginNavHost.kt`) is the pre-sign-in NavHost, mounted while the session is anonymous. A single `V2LoginViewModel` is shared across all four routes so the email / name / OTP screens read and mutate the same `LoginUiState`; navigation is driven off `viewModel.navEvents` (`V2LoginNavigation.ToEmailEntry` / `ToNameEntry` / `ToOtpEntry` / `PopToRoot` / `FlowComplete`). The routes (`V2LoginRoutes.kt`) are `@Serializable` no-arg objects: `V2LoginRoot` (start), `V2EmailEntry`, `V2NameEntry`, `V2OtpEntry`.

## `V2MainNavHost` — the signed-in graph

`V2MainNavHost` (`ui/v2/navigation/V2MainNavHost.kt`) is the signed-in area — a `Scaffold` with a custom bottom bar, `startDestination = V2Home`. It consumes the one-shot latches plus `RecordingAdmissionBus.events` (`RouteToRecordingScreen` / `Blocked` / `BatteryTooLow` / `StorageTooLow`) and a cold-start safety net that suspends on `RecordingService.state` until the first `RECORDING`/`PAUSED` emission before routing to the recording screen. It registers every deep-route composable, `addDebugRoutes(navController)` (real routes in debug, no-op in release), and `V2CloudUploadErrorDialogHost`.

Tier is read reactively via `userScopedInject<EntitlementRepository>().currentTier`, and RR-486 content signals (`hasContexts` / `hasThreads` / `hasBlueprints` / `hasSessions`) are each mapped to a plain `isNotEmpty()` boolean so a tab only re-evaluates on empty↔non-empty transitions.

### Bottom-nav tabs

`MainNavItem` is a private enum of the four tabs. Each carries a `route` and `routeType` (`KClass` for `hasRoute<>`), outlined + filled `@DrawableRes` icons, a `labelRes`, an optional `minimumTier`, and a `visibleWithAiContent` flag. `isVisibleForTier(tier, hasAnyAiContent, hasSessions)` decides visibility:

| Tab | Route | Min tier | Icons | Downgrade-visible |
| --- | --- | --- | --- | --- |
| Home | `V2Home` | none | `ic_home` / `ic_home_filled` | n/a |
| Library | `V2Library` | none | `ic_library` / `ic_library_filled` | n/a |
| Contexts | `V2Contexts` | `PRO_CLOUD_AI` | `ic_brain` / `ic_brain_filled` | yes (`hasAnyAiContent`) |
| Accounts | `V2Accounts` | none | `ic_profile` / `ic_profile_filled` | n/a |

Contexts is the one gated tab: it stays visible read-only for a user who dropped below Cloud+AI but still has AI content, via `visibleWithAiContent = true`.

### The custom bottom bar

`V2BottomNavBar` is hand-built, **not** `androidx.compose.material3.NavigationBar`. It draws a 1dp top border, a `weight(1f)` `Row` of `V2BottomNavItem`s, and a single `V2BottomNavIndicator` — a `56dp × 2dp` red bar (`MaterialTheme.colorScheme.primary`) snapped to the top edge that slides between tabs (`tween`, `IndicatorAnimationMs = 250`, `FastOutSlowInEasing`) rather than teleporting like the M3 pill. Tab switches use the standard recipe: `popUpTo(graph.start) { saveState }` + `launchSingleTop` + `restoreState`, so each tab preserves its deep navigation state.

Deep screens land in the same NavHost; the bar hides for any destination that isn't one of the four tab routes, and recording / playback / trim routes draw full-bleed (they manage their own insets so the blue card sits under the status bar).

### Signed-in routes

`V2MainRoutes.kt` holds the `@Serializable` typed routes. Tabs: `V2Home`, `V2Library`, `V2Contexts`, `V2Accounts`. Deep routes include `V2ContextList(status)`, `V2ContextDetail(contextId, sectionId?)`, `V2Tasks(contextId)`, `V2BlueprintEditor(blueprintId?)`, `V2AccountSettings`, `V2AppSettings`, `V2HelpSupport`, `V2Security`, `V2SetPin(change)`, `V2Privacy`, `V2Usage(expandStorage)`, `V2Recording`, `V2Schedule`, `V2AddSchedule(scheduleId?)`, `V2Favorites`, `V2AllRecordings`, `V2Categories`, `V2CategoryDetail(categoryId)`, `V2Trash(targetItemId?)`, `V2SessionDetail(sessionId, isLive)`, `V2Playback(recordingId)`, `V2Trim(recordingId)`, `V2ExternalPlayback(uri)`, `V2KnowledgeBaseChat(contextId?, threadId?)`, `V2Threads`, `V2Bundles`, `V2ManageSubscription`, `V2Upgrade`.

## Theming

`RollingRecordV2Theme` (`ui/v2/theme/Theme.kt`) is the theme entry point. `darkModeSetting` — `"on"` forces dark, `"off"` forces light, anything else follows `isSystemInDarkTheme()` — picks `v2LightColorScheme()` or `v2DarkColorScheme()`. Both are Material 3 `ColorScheme`s built from the designer's palette: red primary (`#D43C39`), blue secondary (`#7BAFD4`), indigo tertiary (`#4F46E5`), plus `V2Typography`. The theme also provides `LocalV2Colors` with `v2LightColors()` / `v2DarkColors()`.

`V2Theme` (`ui/v2/theme/V2Colors.kt`) exposes `colors: V2Colors` via `LocalV2Colors.current` (a `staticCompositionLocalOf`). The `V2Colors` data class holds extended palette tokens (e.g. `nav`, `cardOutline`) beyond the M3 scheme — the bottom bar reads `V2Theme.colors.nav` and `V2Theme.colors.cardOutline` directly.

## Tier gating

`FeatureAccess.kt` (`ui/v2/gating/`) is the RR-486 downgrade-aware gating primitive. A user who drops below the tier that owns a feature keeps existing content **read-only** but loses mutation. Three levels resolve per-feature from `(currentTier, hasContent)`:

- `FeatureAccess.FULL` — at/above the required tier; full create/edit/delete.
- `FeatureAccess.READ_ONLY` — below the required tier but has existing content; view/play/export only.
- `FeatureAccess.LOCKED` — below the required tier with no content; apply `GatedFeature.whenLocked`.

`GatedFeature.access(tier, hasContent)` resolves the level, and when `LOCKED` the `LockedStyle` (`UPSELL` keeps an entry point that opens an upsell sheet; `HIDE` removes it) decides the fallback. The gated features and their required tiers:

| Feature | Required tier | When locked |
| --- | --- | --- |
| `SESSIONS` | `PRO` | `UPSELL` |
| `PROTECT_SEGMENT` | `PRO` | `HIDE` |
| `SCHEDULED_RECORDINGS` | `PRO` | `UPSELL` |
| `IMPORT` | `PRO` | `UPSELL` |
| `TRANSCRIBE` | `PRO_CLOUD` | `HIDE` |
| `CONTEXTS` | `PRO_CLOUD_AI` | `HIDE` |
| `KB_CHAT` | `PRO_CLOUD_AI` | `HIDE` |
| `CUSTOM_BLUEPRINT` | `PRO_CLOUD_AI` | `HIDE` |

The three AI surfaces (`CONTEXTS`, `KB_CHAT`, `CUSTOM_BLUEPRINT`) deliberately share one `hasAnyAiContent` signal so they resolve consistently. `FeatureUpsell.kt` is the companion upsell-sheet plumbing invoked when a `GatedFeature` resolves `LOCKED` with `LockedStyle.UPSELL`.
