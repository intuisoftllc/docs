Local data lives in a per-user, SQLCipher-encrypted Room database — `AppDatabase`, version 79, 19 entities and 19 DAOs. Each user's file is isolated at `databases/{auth_user_id | anonymous}/rolling_record_db`, built inside `UserSessionScope`. An anonymous session uses a legacy device-bound passphrase; a signed-in session is keyed from the account's DEK. Open failures are classified so only a genuine key mismatch ever wipes the file.

## `AppDatabase`

`AppDatabase` (`data/local/db/AppDatabase.kt`) is `@Database(version = 79, exportSchema = true)` with 19 entities and 19 abstract DAO accessors (`recordingDao()` … `pendingPullApplyDao()`). It is registered as a `scoped<AppDatabase>` in `UserSessionScope` (see [Koin Dependency Injection](/rollingrecord/app/architecture/dependency-injection)), so closing the scope on sign-in/out releases Room's file handle and the next scope opens a fresh DB against the new user's directory.

`exportSchema = true` (RR-110) makes Room write a per-version schema JSON to `app/app/schemas/` on every build. That committed JSON is what `MigrationTestHelper` builds the source-version database from and what `runMigrationsAndValidate()` diffs the post-migration schema against — the diff catches a mismatched index name, exactly the April-2026 data-loss class of bug (see [Migration-test infrastructure](#migration-test-infrastructure)).

## Building the DB for a session

`buildAppDatabaseForSession(context, scope)` (`di/DatabaseModule.kt`) resolves the key for the active segment, then delegates to `buildRoomDatabase`. The DB file path is absolute — `databases/{segment}/rolling_record_db` — and the builder attaches `SupportOpenHelperFactory` (net.zetetic SQLCipher, after `System.loadLibrary("sqlcipher")`), `addMigrations(*allMigrations)`, and `addCallback(FtsTableCallback())`.

Two key paths:

- **Anonymous (signed-out) session** — there is no account DEK and the anonymous DB is never cloud-portable, so it stays on the legacy random device-bound passphrase from `DatabaseKeyManager.getOrCreatePassphrase` (`data/local/security/DatabaseKeyManager.kt`).
- **Signed-in session** — the DB key is derived from the account DEK so the same account opens the same DB on any device. `BackupRestorer.recoverInterruptedRestore` heals any half-finished restore swap, then `DekKeyStore.loadDek` reads the persisted, Android-Keystore-wrapped DEK offline. When no persisted DEK is found yet (cold-start race), an off-main build fetches it inline via `SessionDekHolder.requireDek()`, bounded by `withTimeout(INLINE_DEK_FETCH_TIMEOUT_MS = 45_000L)` — a hung fetch degrades to the recoverable `DekUnavailable` surface rather than holding the session-scope lock. A null DEK is the recoverable `DekUnavailable` state — the DB is **never** opened and **never** wiped; instead `DatabaseRecoveryState.flagDekUnavailable(...)` is raised, `DekUnavailableException` is thrown, and the reason is reported as a deduped (per user, per reason, per process) Crashlytics non-fatal via `reportDekUnavailableToCrashlytics` (keys only — UUIDs, hashes, counts; no key material). Otherwise `DatabaseKeyTransition.resolvePassphraseOrTransition` (now also passed `kekVersion = persisted.kekVersion`) produces the DEK-derived (structure-v2) SQLCipher raw key and the DB is built and verified.

`DatabaseKeyTransition` (`data/local/security/DatabaseKeyTransition.kt`) returns `Result.Ready(passphrase)` or `Result.DekUnavailable(reason)`. RR-489 removed the legacy v1→v2 in-place re-key, so a non-v2 file now fails safe to the recovery surface rather than the wipe path.

### Publishing readiness

The `scoped<AppDatabase>` binding wraps the build in `.also { SessionDatabaseState.markReady(sessionId) }`, so readiness is published on **every** successful build path — the anonymous path, the DEK-derived path, and the `handleKeyMismatch` rebuild all funnel through the same single call site rather than each of `buildAppDatabaseForSession`'s several return points, so no future path can forget it. Equally deliberate: it never fires on a throw. A `DekUnavailableException` or a fatal open must leave the root UI on its loading or recovery surface, not wave Main into a cold factory.

The `sessionId` it publishes comes from the Koin scope's own `id`, not from re-reading `AuthUserStore`. The scope's id **is** the session id (`UserSessionManager` creates every session scope with `scopeId = newSessionId`), which makes the read both free of I/O and free of the race where the store has already been re-pointed at the incoming user while this factory is still building the outgoing one's database.

## Open-failure routing

`openVerifiedOrRecover` verifies `writableDatabase` (exercising the `DevFlags.forceFatalDbErrorOnOpen` synthetic-failure hook), and on failure `classifyOpenFailure(e)` string-matches the cause chain into a `DbOpenFailure`:

| `DbOpenFailure` | Signature matched | Action | Data safe? |
| --- | --- | --- | --- |
| `KEY_MISMATCH` | SQLCipher "file is not a database" | `handleKeyMismatch`: derive the rebuild key **before** wiping, flag recovery, wipe `*.db`/`-wal`/`-shm`, rebuild under the same current key | File wiped; audio on disk re-imported via the `KeyMismatchWiped` dialog |
| `SCHEMA_MISMATCH` | "Room cannot verify" / "identity hash" / "expected:…found:" | `handleFatalDbError`: log, Crashlytics `db.open.wipe=false`, flag fatal, rethrow — file untouched | Yes — fatal error screen |
| `MIGRATION_MISSING` | "migration from … was required but not found" | Fatal, file untouched | Yes — fatal error screen |
| `UNKNOWN` | anything else | Fatal, file untouched | Yes — fatal error screen |
| (DEK unavailable) | resolved before build | Recoverable, never opened or wiped | Yes — retry screen |

<Warning>
Only `KEY_MISMATCH` wipes. The `SCHEMA_MISMATCH` / `MIGRATION_MISSING` / `UNKNOWN` cases are fatal and leave the file untouched, and a missing DEK is a separate recoverable path that never opens or wipes. The older narrative that `DatabaseModule` catches all exceptions and wipes the whole database describes pre-RR-109 behavior; the live code narrows the wipe path to a genuine key mismatch on an already-resolved key.
</Warning>

`handleKeyMismatch` derives the rebuild key before any destructive wipe, so if the DEK has somehow become unavailable in the interim, the derive throws and the DB file is left 100% untouched (the recoverable surface handles it). The rebuild always happens under the current session's key.

## Migrations

`allMigrations` is an `Array<Migration>` of all 78 sequential migrations, `MIGRATION_1_2` through `MIGRATION_78_79`, imported from `data/local/db/migrations/*`. Version bumps are atomic across three places: `AppDatabase.version`, the `allMigrations` array in `DatabaseModule.kt`, and `DevBackupManager.CURRENT_DB_SCHEMA_VERSION`.

`MIGRATION_78_79` (`data/local/db/migrations/Migration78To79.kt`) is a representative example — a purely additive change adding two nullable columns to `blueprints`: `moderationRejectedAt INTEGER` and `moderationRejectionReason TEXT`. NULL (the value every existing row gets) means "not rejected"; the pair records that a re-pushed custom blueprint failed re-moderation after a subscription-lapse cloud-reset wiped its server row. Each migration file carries a plain-English risk statement and the version-bump checklist inline.

## Migration-test infrastructure

Every migration is validated by an instrumented `MigrationTestHelper` test, backed by committed schema exports and gated at push time (RR-110 / RR-111):

- **`MigrationTest.kt`** (`app/app/src/androidTest/.../data/local/db/`) — the `migrate78To79()` test builds the v78 DB from `78.json`, seeds real rows into both the altered table (`blueprints`) and one it must leave alone (`recordings`), then calls `runMigrationsAndValidate(TEST_DB, 79, true, MIGRATION_78_79)`. That call validates the post-migration schema against `79.json` (catching an index-name mismatch — a defect a "did the SQL throw?" test would pass) and the test then asserts the seeded rows survived with their expected values. Adding a test for a new migration copies this block and changes four things: source version, target version, the seed INSERT, and the assertions.
- **`app/app/build.gradle.kts` wiring** — the Room Gradle plugin (`alias(libs.plugins.room)`), `room { schemaDirectory("$projectDir/schemas") }`, the `androidTest` assets `srcDirs` entry pointing at `$projectDir/schemas` (ships the JSONs into the test APK), and `androidTestImplementation(libs.androidx.room.testing)`.
- **Committed schema files** — `app/app/schemas/…AppDatabase/78.json` and `79.json`. A version with no exported schema is permanently untestable, since the JSON can only be regenerated from a checkout of the code at that version.
- **`app/scripts/verify_schema_files.py`** (RR-111) — eight mechanical checks: `exportSchema = true` still set, the current version N has a schema file, `N.json`'s own recorded version equals N, `MIGRATION_{N-1}_{N}` is wired into `allMigrations`, `DevBackupManager.CURRENT_DB_SCHEMA_VERSION == N`, schema files are committed (not untracked or dirty), a version bump M → N also carries `M.json`, and a warning for any schema file ahead of N. It runs as step 0 of `scripts/hooks/pre-push` — instant and offline, so it rejects the push on schema/version drift before any Gradle work.

## FTS tables

`FtsTableCallback` is a `RoomDatabase.Callback` that creates non-Room-managed tables on `onCreate`/`onOpen` — they are not declared as `@Entity` / `@Fts` tables:

- `fts_section_index` (with `idx_fsi_contextId`) — a plain lookup table.
- `context_fts` — an `fts4` virtual table over `contextName, keywords, sectionTitle, sectionContent` with `tokenize=porter`.

## Recovery state

`DatabaseRecoveryState` (`states/DatabaseRecoveryState.kt`) is the process-static flag consumed by `V2App`/`MainActivity`. `RecoveryState` variants: `FatalError(errorCode, message)`, `DekUnavailable(reason)`, `KeyMismatchWiped`. The `flagFatalError` / `flagDekUnavailable` / `flagRecoveryNeeded` / `clearRecovery` calls drive the matching recovery screens (see [UI & Navigation](/rollingrecord/app/architecture/ui-and-navigation)).

`SessionDatabaseState` (`states/SessionDatabaseState.kt`) is its structurally identical sibling — deliberately so, since both are root-UI signals raised from deep inside the DB layer and keeping them the same shape means one place to look when the root surface misbehaves. It exposes `readySessionId: StateFlow<String?>` (the session whose database is built and resolvable, or `null`), `markReady(sessionId)` called by the `AppDatabase` factory on a successful build, and `clear()` called by `UserSessionManager.switchTo` at the scope swap. It reports the happy path rather than a failure: `readySessionId == sessionId` is the root UI's "a synchronous user-scoped Koin resolution is now cheap" signal.
