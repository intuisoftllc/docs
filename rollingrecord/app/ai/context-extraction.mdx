Extraction is a server-side asynchronous pipeline. The client's only job is to gather a context's pending sources, submit one job, watch it to a terminal state, apply the fully-merged results into Room, and acknowledge it. `ContextExtractionWorker` (`worker/ContextExtractionWorker.kt`) is that client leg — it no longer chunks transcripts, assembles prompts, calls the model, or parses tool blocks; the server runner does all of that and returns a single merged accumulator blob.

## `ContextExtractionWorker`

`ContextExtractionWorker` is a `CoroutineWorker` that drives exactly one server extraction. It runs on a single global unique-work chain (`QUEUE_NAME = "context_extraction_queue"`, `APPEND_OR_REPLACE`), so a second context queues locally behind the head rather than racing into a server-side 409. The companion object exposes `enqueue(...)` (mints a fresh job id) and `enqueueAttach(...)` (resumes a supplied job id — see [Extraction Job Lifecycle](/rollingrecord/app/ai/extraction-jobs)).

Input `Data` keys:

| Key | Meaning |
| --- | --- |
| `KEY_CONTEXT_ID` (`context_id`) | The context being extracted. Absent → `Result.failure()`. |
| `KEY_BLUEPRINT_ID` (`blueprint_id`) | The chosen blueprint id, or absent for the context's own / default blueprint. |
| `KEY_IS_REBUILD` (`is_rebuild`) | Rebuild wipes the card and resets incorporation before running. |
| `KEY_JOB_ID` (`extraction_job_id`) | The server job's primary key, minted client-side once at enqueue and preserved across every WorkManager retry. |

`MAX_RUN_ATTEMPTS = 3` bounds WorkManager retries before a transient failure becomes terminal; `ACK_MAX_ATTEMPTS = 3` bounds the ack retry.

## The run: `runJob`'s eight steps (0–7)

The worker takes the card's exact pre-run state (`snapshotForExtraction`) before any write, then runs the pipeline. Each step publishes an [`ExtractionJobPhase`](/rollingrecord/app/ai/extraction-jobs) so the Intelligence pane can narrate progress.

| Step | What happens |
| --- | --- |
| 0. Resume probe | `statusOnce(jobId)`: if the server already knows this id, settle/watch it to terminal instead of re-planning. Runs **before** the budget gate so a process-killed job's already-paid results still apply. |
| 1. Gather | `gatherSources()` resolves pending recordings + pooled sessions into `ExtractionUnit`s. Recordings without a `DONE` transcript are enqueued for transcription and left pending; silent (empty-transcript) sources are left pending, never billed. |
| 2. Budget partition | `ExtractionPlanner.partition()` splits units into authorized/deferred against the remaining extraction-minutes budget (from `UsageRepository`; dev override via `DevFlags.extractionsCapOverride`). |
| 3. Prior state | Builds `ExtractionPriorState` from the card at this instant so the runner can `replaceSection` / `completeTasks` instead of re-extracting. |
| 4. Size trim | `ExtractionPlanner.fitByBytes()` drops units from the tail until the serialized payload fits `ExtractionPayload.MAX_INLINE_PAYLOAD_BYTES` (8 MiB). |
| 5. Submit / attach | `submitOrAttach()` POSTs `extract-submit`; `Queued` → watch, `AlreadyRunning` → attach if the job belongs to this context, else retry. |
| 6. Watch | `awaitTerminal()` polls `extract-results {operation:"status"}` to a terminal `ExtractionJobStatus`, publishing a phase each tick. |
| 7. Settle | `DONE` → `applyDoneJob` (fetch → ownership checks → apply → ack); `FAILED` / `CANCELLED` / `ACKED` / `NOT_FOUND` handled with snapshot restore + a card sentinel. |

The client never runs an admission gate for context fullness — the server decides. A doomed batch costs one ~2s call that returns `chunks=0` and bills nothing, so the client is deliberately never the one saying "too full".

## Error sentinels

Terminal outcomes stamp a sentinel string into `ContextCardEntity.errorMessage`, which the Intelligence pane maps to a state and a retry affordance:

| Sentinel | Meaning |
| --- | --- |
| `CAP_ERROR_MESSAGE` (`extraction_cap_reached`) | Monthly extraction budget exhausted; sources stay pending and resume after a reset/upgrade. |
| `CONTEXT_FULL_ERROR_MESSAGE` (`extraction_context_full`) | Server stopped at the context size ceiling — a **partial** success; completed recordings applied, the rest stay pending and are named in the review sheet. |
| `CONTEXT_TOO_LARGE_ERROR_MESSAGE` (`extraction_context_too_large`) | A single unit's transcript is too large to submit. |
| `NETWORK_ERROR_MESSAGE` (`extraction_network_error`) | Connection dropped / retries exhausted. |
| `UNRECOVERABLE_ERROR_MESSAGE` (`extraction_unrecoverable`) | Failed in a way a retry cannot fix (undecryptable blob, vanished job row, rejected submit). Recovery is a fresh extraction. |

## `ExtractionPlanner`

`ExtractionPlanner` (`worker/extraction/ExtractionPlanner.kt`) is a pure, I/O-free planning object that replaced the retired `TranscriptChunker` and the server's `extract_preflight` op. The plan is **advisory** — the server's per-recording reserve is the authoritative charge, so a mis-estimate defers server-side rather than over-billing.

- `chunkCountFor` / `chunksTotalFor` — `ceil(chars / (chunkTokens × CHARS_PER_TOKEN))`, mirroring the server's arithmetic so the progress denominator matches. `CHARS_PER_TOKEN = 4`.
- `billableMsFor` — a trusted audio duration is authoritative and billed as-is; the transcript-token floor is a fallback only when no duration exists (never an inflator on top of it).
- `partition` — greedy budget fit in list order; a null `remainingMs` degrades open and authorizes everything.
- `fitByBytes` — tail-first serialize-and-measure trim to `MAX_INLINE_PAYLOAD_BYTES`, because an over-cap request body surfaces as an opaque network failure, not a clean 413.

Units can be deferred by **two** gates — the budget partition and the payload byte-size trim. Deferred units stay pending (never marked incorporated), are re-gathered on the next run, and resume when the user next extracts or after a cap reset/upgrade. There is no timer.

## `ExtractionResultsApplier`

`ExtractionResultsApplier` (`worker/extraction/ExtractionResultsApplier.kt`) writes a finished results blob into Room under one `db.withTransaction` + `NonCancellable`. Inside the transaction, in order: `mergeContent` (sections as replacements via `applyReplacements`, `syncIndexes = false`), `insertTasks`, `completeTasksByIds` (validated against the context's own task ids), `saveExtractionBudget` (the RR-497 calibration pair), `markRecordingsIncorporated` / `markSessionsIncorporated`, and `clearExtractionSnapshot`. After the commit it rebuilds the derived indexes (`refreshFts`) — outside the transaction because that ends in a WorkManager enqueue. It does NOT call `enrich`: enrichment (keywords + summary, two network calls) is a separate `ExtractionResultsApplier.enrich(contextId)` method the worker invokes from `ContextExtractionWorker.applyDoneJob` after the apply returns, not part of `apply()` itself.

The apply is safe to run twice: sections are applied as replacements (not an additive merge) and task ids are derived (not random), so a repeat apply converges instead of duplicating. That is what makes the apply→ack window interruptible.

## `ExtractionResultsMapper`

`ExtractionResultsMapper` (`worker/extraction/ExtractionResultsMapper.kt`) is a pure wire↔Room translator in both directions. `map()` produces a `Mapped(sections, newTasks, completedClientTaskIds)`; `toPriorState()` builds the `ExtractionPriorState` the runner seeds its accumulator from, splitting user-authored insights into `userNotes` (readable but unwritable, since no extraction tool addresses that field). Section ids are derived from `contextId` + the lowercased title; task ids from `jobId` + the server task id — so a repeated apply overwrites the same rows rather than minting new ones. The mapper does not re-validate; the runner already did that server-side.

## `ContextCardEntity` and `ContextStatus`

`ContextCardEntity` (`data/local/db/entity/ContextCardEntity.kt`) is the Room `@Entity("context_cards")` (PK `contextId`) that holds the extraction output and its lifecycle metadata:

- `sections` — JSON `List<ExtractedSection>`, each with `title`, `category`, and a list of `Insight`s (`text`, `status`, `confidence`, `origin`, `sourceRecordingIds`, `dateRef`).
- `status` — a `ContextStatus`: `NOT_STARTED` / `PROCESSING` / `DONE` / `ERROR`. This is the card's extraction status, distinct from the context lifecycle (`ACTIVE` / `COMPLETED` / `ARCHIVED`) and from the server job status.
- `errorMessage`, `keywords`, `contextSummary`, `digest` (see [Context Synthesis](/rollingrecord/app/ai/synthesis)).
- `extractionSnapshotJson` — the pre-run snapshot used for verbatim restore.
- `lastExtractionInputTokens` / `lastExtractionEstimatedTokens` — the RR-497 size calibration pair.
- `remoteSyncedAt`, `cloudExcludedAt` — sync / cloud-exclusion metadata.

## Idempotency and durability

| Mechanism | Guarantee |
| --- | --- |
| Client-minted job id in `inputData` (`KEY_JOB_ID`) | Survives process death / retry; a resend resolves to `queued` or `already_running`, never a duplicate job. |
| Incorporation flips only after results land | A retry after a successful apply finds nothing pending and exits before submitting. |
| Sections applied as replacements + derived task ids | A repeated apply overwrites instead of duplicating. |
| Pre-extraction snapshot (`extractionSnapshotJson`) | Cancel / failure / process-death restores the card verbatim; `App.revertOrphanedExtractionSnapshots` sweeps orphans at the next launch. |
| Server `recording_ids` from results | Only sources the job actually **processed** are marked incorporated; an empty list means it processed nothing (never "assume all"). |

### Rebuild reset and self-heal

`ContextCardRepository.resetAllForRebuild(contextId)` performs the rebuild reset **atomically** inside `database.withTransaction` — re-flags recordings + sessions pending, clears the card to `NOT_STARTED`, deletes tasks — and returns a `RebuildResetCounts`. Only the non-DB cleanup (sync enqueues, `embeddingDao.deleteByOwner`, `purgeContextFts`) runs OUTSIDE the transaction, because those end in a WorkManager enqueue. `resetToNotStarted` is now documented as **card-only** — the rebuild flow wants `resetAllForRebuild`. `V2ContextDetailViewModel.resetForRebuild` runs it on `userSessionManager.sessionScope` (not `viewModelScope`), so navigating away mid-reset can no longer leave a half-reset context.

The old non-transactional three-write reset could leave a context stuck NOT_STARTED-card-but-sources-still-incorporated. `V2ContextDetailViewModel.init` now calls `healHalfResetContext()`, which repairs exactly that contradiction: if the card is `NOT_STARTED` and `ContextRepository.getIncorporatedCountOnce(contextId) > 0`, it re-flags the sources pending so Extract works again. It fires only on that exact state, so a normally-extracted context is untouched.

Deleting a context is now one call. `ContextRepository` injects `ContextCardRepository`, and `ContextRepository.delete(id)` itself calls `contextCardRepository.deleteForContext(id)` — removing the card, tasks, keyword index, both embedding types, and both FTS tables in one operation. It was previously the caller's job to invoke `deleteForContext` first (Free Up Space forgot it, orphaning derived rows), so `V2ContextDetailViewModel.delete()` no longer calls it separately.

There is no single `ContextCardSheet` composable — the extraction surface is the Intelligence pane inside `V2ContextDetailScreen`, driven by the card's `ContextStatus`:

- `ContextIntelligencePreExtraction` (`ui/v2/screens/contexts/components/ContextIntelligencePreExtraction.kt`) — shown while status is `NOT_STARTED`: a masonry grid of blueprint picker cards plus source chips and the Extract / custom-blueprint CTAs. Custom cards get Edit/Delete (Delete gated to Cloud+AI); built-ins have no long-press menu. `BlueprintPickerItem` gained `rejectionReason: String?`, `isDeleting: Boolean`, and derived `isUnapproved` (`rejectionReason != null`): a custom blueprint that failed re-moderation after a cloud wipe (no server row) renders unapproved — `unapprovedBlueprintBg` / `unapprovedBlueprintBorder`, an `ic_alert` icon, and a "not approved" label — and stays selectable, but tapping it opens `V2UnapprovedBlueprintSheet` (see [Extraction Templates](/rollingrecord/app/ai/templates-blueprints)). A delete-in-flight card is dimmed (alpha 0.5) and inert with a "Deleting…" spinner, because delete calls the server before dropping the local row.
- `ExtractionDistillAnimation` (`ui/v2/screens/contexts/components/ExtractionDistillAnimation.kt`) — the in-progress "distillation" visual, keyed off `ExtractionJobPhase`: a particle field, a phase label, and a determinate bar (Extracting / Uploading with a fraction) or an indeterminate sweep.
- `ContextIntelligenceResults` (`ui/v2/screens/contexts/components/ContextIntelligenceResults.kt`) — shown for status `DONE` with topics: a source-chip row, a `{n} Topics found` summary with select-all, the topic cards, and a footer with Tasks plus the mode-driven primary action (Extract / Export). Per-topic detail opens in `ContextTopicDetailSheet`. `TopicSelection` drives multi-select export.

`ContextDisplayOrder.orderTopicsForDisplay` (`data/repository/ContextDisplayOrder.kt`) sorts those topic cards in three tiers: user-authored topics (an `InsightOrigin.USER` insight with no sources) sort FIRST via the new `USER_NOTE_RANK = Int.MIN_VALUE`, then attributed topics by best source rank (newest-added source first), then genuinely unattributable topics last (`NO_SOURCE_RANK`). Previously a pure user-note topic fell to the bottom under `NO_SOURCE_RANK`; a topic that merely CONTAINS a note but also has sources still ranks by its sources, so annotating a topic no longer yanks it to the top.

`ContextIntelligencePane` (`V2ContextDetailScreen.kt`) now takes a `lifecycle` param and computes `canExtractEffective = canExtract && !readOnly && lifecycle.canExtract`, so extraction is hard-blocked on Completed / Archived contexts (matching the ViewModel + worker guards) rather than offering a live Extract button that silently does nothing. A frozen, never-extracted context now renders `ContextIntelligenceFrozenEmpty(lifecycle)` instead of a dead blueprint picker, and the no-topics summary (`ContextNoTopicsState`) requires `results.sourceCount > 0` — a cancelled or orphaned 0-source run no longer renders a bogus "0 insights" end state.

`V2ContextDetailViewModel.extract(rebuild)` is the UI entry point. It pre-checks `ServerConfig.aiExtractionEnabled`, `FeatureAccess.FULL`, the context lifecycle's `canExtract`, online connectivity, that no linked recording is still transcribing, and that extraction isn't capped, then calls `ContextExtractionWorker.enqueue(...)`. The pane's live phase is no longer `ExtractionProgress.fold` alone — `extractionPhase` now `combine`s the `WorkInfo` flow with two overrides, `cancelInFlight` (→ `Cancelling`) and `cancelVerifiedIdle` (→ `Idle`). `cancelExtraction()` cancels the WorkManager tag, awaits that cancel, and does an authoritative server check (`statusOnce` / `pendingOnce`) before forcing Idle, restoring the card from its snapshot under `NonCancellable`.
