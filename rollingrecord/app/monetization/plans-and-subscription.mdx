Two V2 screens cover buying and managing a subscription: the "Choose a Plan" paywall for a first purchase, and the "Your Plan" screen for changing, resubscribing, or cancelling. Both read a shared static plan catalog, price it live from RevenueCat, and render the same full-screen result overlay after a transaction.

**Theming.** `V2UpgradeScreen`, `V2ManageSubscriptionScreen`, and the shared `PlanResultOverlay` (`PlanResultOverlays.kt`) were converted to dark mode by swapping hard-coded palette constants (`Gray500` / `Gray800` / `Gray900`, `Red50`, `Gray200`, `Blue50`) for `V2Theme.colors.*` tokens (`strongText`, `secondaryText`, `chatErrorBg`, `cardOutline`). This was purely a theming pass — behavior, the `ManagePlanKind` state machine, and the `PlanResult` states themselves were unchanged by it. (`PlanResultOverlay` has since gained a `headerTitleRes` parameter so the bundle flow can reuse its error state — see "Transaction results" below.)

## `PlanCatalog`

`PlanCatalog` (`ui/v2/screens/upgrade/PlanCatalog.kt`) is an internal enum shared by both flows. Names, descriptions, feature lists, and icons are fixed design content (string/array/drawable res IDs); prices come live from RevenueCat, matched to these product IDs. Each entry carries its `RcEntitlement`, monthly + annual store product IDs, res IDs, and a `staticBadge`.

| Catalog entry | Monthly product id | Annual product id | Static badge |
| --- | --- | --- | --- |
| `FREE` | (none) | (none) | (none) |
| `PRO` | `pro_monthly` | `pro_annual` | `POPULAR` |
| `PRO_CLOUD` | `pro_cloud_monthly` | `pro_cloud_annual` | `BEST_VALUE` |
| `CLOUD_AI` | `pro_cloud_ai_monthly` | `pro_cloud_ai_annual` | `AI_POWERED` |

The companion exposes `PAID` (the three purchasable tiers in display order), `forEntitlementKey(lookupKey)`, and `forProductId(productId)`. Two supporting enums live in the same file: `BillingPeriod { MONTHLY, ANNUAL }` and `PlanBadge { CURRENT, POPULAR, BEST_VALUE, AI_POWERED }` — where `CURRENT` always wins over a static badge.

### Package helpers

The same file provides the functions that bridge live RC packages to the catalog:

- `packageKey(catKey, period)` builds the map key `"<catalogKey>:<PERIOD>"`.
- `classifyPackage(pkg)` matches an RC `Package` to a bucket by normalized store product id (Google subs arrive as `productId:basePlanId`, so it normalizes) or by package identifier — either dashboard convention works.
- `monthlyTimesTwelve(packages, catKey)` computes the struck-through "if you paid monthly for a year" full price shown next to an annual price.
- `annualDiscountPercent(packages, catKey)` computes the percent saved versus monthly×12, returning null when the annual price is not actually cheaper (no point advertising a non-discount).

## The paywall — `V2UpgradeScreen`

`V2UpgradeScreen` (`ui/v2/screens/upgrade/V2UpgradeScreen.kt`) is the "Choose a Plan" surface, backed by `ChoosePlanViewModel` (`ui/v2/screens/upgrade/ChoosePlanViewModel.kt`). It renders one `PlanCard` per tier, a Monthly/Annual toggle with a "Save N%" floor badge, a pinned subscribe CTA, and a Restore-purchases action; a non-null `result` draws the `PlanResultOverlay` on top.

`ChoosePlanViewModel` exposes `uiState: StateFlow<ChoosePlanUiState>` and the methods `load()`, `setBillingPeriod()`, `select()`, `purchase(activity)`, `restore()`, and `dismissResult()`:

- `load()` fetches the current offering via `RevenueCatManager.getCurrentOffering()` and classifies each package into the `"<catalogKey>:<PERIOD>"` map. An `OfferingsResult.Empty` (no offering marked Current in the dashboard) surfaces as an error state rather than a spinner-forever.
- The default selected card is `PlanCatalog.PRO_CLOUD` (the Best Value tier), matching the design's pre-selected card.
- `purchase(activity)` sets `PlanResult.Processing`, calls `RevenueCatManager.purchase()`, and maps the outcome to `SuccessNew` / null (user cancelled) / `Error`.
- `restore()` emits the one-shot `ChoosePlanEvent.RestoredNothing` (a lightweight toast) when a restore finds no active entitlements; a restore that finds entitlements reuses the `SuccessNew` overlay.

`PlanCard` is the per-card render state (`key`, `iconRes`, `nameRes`, `descRes`, `featuresRes`, `badge`, `priceText`, `periodSuffixRes`, `strikeText`, `discountPercent`, `isCurrent`, `purchasable`). `ChoosePlanUiState` carries `loading`, `error`, `billingPeriod`, `cards`, `selectedKey`, `ctaPriceText`, `annualSavePercent`, and `purchaseInProgress`. `ChoosePlanEvent` is a sealed interface whose only member is `RestoredNothing`.

## The management screen — `V2ManageSubscriptionScreen`

`V2ManageSubscriptionScreen(onNavigateBack, onNavigateToUpgrade, onNavigateToBundles)` (`ui/v2/screens/subscription/V2ManageSubscriptionScreen.kt`) is the "Your Plan" surface — a current-plan card, a change-plan sheet, and resubscribe/cancel/restore actions, with `PlanResultOverlay` for transaction results. It is backed by `ManageSubscriptionViewModel` (`ui/v2/screens/subscription/ManageSubscriptionViewModel.kt`), which derives its whole state from live RC `CustomerInfo`.

`ManagePlanKind` classifies the current state, and the derivation checks Developer and lifetime cases before the ordinary recurring path:

| `ManagePlanKind` | Meaning |
| --- | --- |
| `LOADING` | RC customer info not yet resolved. |
| `FREE` | No active entitlement. |
| `SUBSCRIBED` | Active recurring sub that will renew. |
| `CANCELLED` | Active recurring sub with `willRenew == false` — full access until expiry. |
| `LIFETIME` | Internal lifetime or public Founders Edition — one-time, never expires (change is upgrade-only). |
| `DEVELOPER` | Internal-ops grant — not a purchase; no upgrade/downgrade/cancel path. |

The supporting data types are `CurrentPlan` (summary card, with `isLifetime` / `isDeveloper` flags), `ChangePlanRow` (one compact row in the change-plan sheet), `ConfirmPlanInfo` (the confirm sheet), and the `ManageEvent.OpenUrl` event used to open the Play subscriptions page.

### Change, resubscribe, cancel

- **Change plan** — `confirmChange(activity, newKey, period)` runs a replacement purchase: it passes the currently-owned recurring product id as `oldProductId` so Google applies default proration rather than rejecting a second subscription in the group. A pure-lifetime holder with no recurring sub gets a fresh purchase layered on top instead. `changePlanRows(period)` builds the sheet rows (lifetime holders see upgrades only), and `annualSaveFloor()` drives the annual "Save N%" chip.
- **Resubscribe** — `resubscribe(activity)` re-buys the same product to re-enable auto-renew on a cancelled-but-active plan.
- **Cancel** — `cancel()` is a **deep-link only**: there is no in-app cancel and no SDK cancel API on any store. It emits `ManageEvent.OpenUrl` with RC's `managementURL` when present, otherwise `https://play.google.com/store/account/subscriptions`.

The error overlay's "Try Again" replays the last attempted purchase via `retry(activity)`; `dismissResult()` clears the overlay and any pending action.

### "Purchase a bundle" — `PurchaseBundleRow`

`onNavigateToBundles` is passed down as `onPurchaseBundle` into `SubscribedStateBody`, `LifetimeStateBody`, and `CancelledStateBody`, each of which renders `PurchaseBundleRow(tier, onClick)` — under "Change plan" in SUBSCRIBED (above Cancel), under the upgrade row in LIFETIME, and under "Resubscribe" in CANCELLED. It is rendered through `ActionRow(iconRes = R.drawable.ic_plus, …, enabled = eligible)`, where `eligible = tier != null && tier.atLeast(UserTier.PRO_CLOUD)`; `ActionRow`'s `enabled` flag greys the icon/title/subtitle to `onSurfaceVariant`, disables the click, and omits the trailing chevron entirely.

The row is **always rendered, never hidden**. The other three routes into the bundle catalog only appear once the user has already hit a wall, so someone who never runs out would never learn bundles exist; Your Plan is the one screen people visit deliberately. Below Pro+Cloud it is disabled rather than absent — a greyed row that says why is information, a missing row is not.

| Tier | Row state | Subtitle string |
| --- | --- | --- |
| Below Pro+Cloud | Disabled | `your_plan_bundle_subtitle_locked` — "Upgrade to purchase a bundle" |
| `PRO_CLOUD` | Enabled | `your_plan_bundle_subtitle_cloud` — "Top up your transcription hours" |
| `PRO_CLOUD_AI` | Enabled | `your_plan_bundle_subtitle_cloud_ai` — "Top up transcription hours and chat credits" |

The CANCELLED case is deliberate: a cancellation stops the renewal but does not revoke the entitlement, so the row is gated on the tier the user actually holds right now rather than on the cancelled flag. Someone still on Pro+Cloud with a month left can buy hours, and the expiry warning directly above is what tells them the plan is ending.

## Transaction results — `PlanResultOverlay`

`PlanResult` and `PlanResultOverlay` both live in `ui/v2/screens/upgrade/PlanResultOverlays.kt`:

```kotlin
fun PlanResultOverlay(
    result: PlanResult,
    onDone: () -> Unit,
    onTryAgain: () -> Unit,
    onBack: () -> Unit,
    @StringRes headerTitleRes: Int = R.string.your_plan_title,
)
```

The sealed `PlanResult` has four states rendered full-screen over the originating screen:

| `PlanResult` state | Rendered as |
| --- | --- |
| `Processing` | Spinner + "Updating your plan…". |
| `SuccessNew(planNameRes)` | A newly activated subscription ("Welcome to X"). |
| `SuccessUpdate(planNameRes)` | An existing plan changed ("Plan Updated"). |
| `Error(reason)` | The charge failed; the plan is unchanged. Offers Try Again / Back. |

A user backing out of the store sheet maps to null (no overlay), not to a distinct state.

`headerTitleRes` names the screen the overlay is sitting on top of, and is passed through to `PlanSuccessScreen` / `PlanErrorScreen` as `ResultHeader(titleRes = headerTitleRes, …)`; `PlanProcessingScreen()` has no header and takes no title. It defaults to `R.string.your_plan_title` because that is where subscription purchases start:

| Caller | `headerTitleRes` | Header reads |
| --- | --- | --- |
| `V2UpgradeScreen` / `V2ManageSubscriptionScreen` | omitted (default) | "Your Plan" |
| `V2BundlesScreen` | `R.string.bundles_title` | "Add Hours" |

The overlay is therefore shared by three flows, not two — but the bundle catalog reuses only the **error** state. It has its own `BundleSuccessScreen` and `BundleProcessingScreen`, because a bundle's success state has to show post-webhook credit balances the plan overlay knows nothing about. See [Add-On Bundles](/rollingrecord/app/monetization/bundles).

## `RevenueCatManager` purchase surface

The purchase, offering, and restore calls all go through `RevenueCatManager` (`data/billing/RevenueCatManager.kt`):

- `getCurrentOffering()` returns an `OfferingsResult` (`Success` / `Empty` / `Error`).
- `purchase(activity, pkg, oldProductId?)` launches the store sheet and, on success, pushes the fresh `CustomerInfo` through so the tier unlock propagates on its own through `EntitlementRepository` — the caller only dismisses.
- `restorePurchases()` is the explicit "Restore purchases" path.

All of these work identically against the RC Test Store and the real Play Store; which store the SDK talks to is decided purely by the API key passed to `Purchases.configure`.

## Post-purchase entitlement race

The server caches its RevenueCat read for ~5 minutes per customer, so a user who browsed while free is answered from a cached "no entitlements" for minutes after paying. The [`X-Entitlement-Refresh`](/rollingrecord/app/monetization/entitlements-revenuecat) signal asks the server to skip that cache, but two downstream code paths also *tolerate* the stale window so a just-paid user is never wrongly refused a feature they hold.

**Transcription cap UI — `V2PlaybackViewModel`.** The transcription-cap computation (`V2PlaybackViewModel`, `ui/v2/screens/playback/`) now detects a stale snapshot: the snapshot reports the `tier` it was computed for, resolved via `RcEntitlement.fromLookupKey`, and when `snapshotTier.ordinal < tier.ordinal` (the live tier) the snapshot predates the purchase. In that case the cap falls back to the tier's `baseCapMinutes` allowance instead of the stale server cap figure — which for anything below Pro+Cloud is `0`, so `used >= cap` is trivially true at `0 >= 0` and a paid user would otherwise be told they are out of minutes. The fallback is deliberately optimistic: the server still enforces the real cap on every transcribe, so the worst case is the UI letting someone start a request the server then refuses, which is far better than refusing a feature they hold on our own.

**Transcription worker — `TranscriptionWorker`.** `AiEngineResult.Cap` and `AiEngineResult.SubscriptionRequired`, at **both** the init and submit steps, are now thrown as `TransientAiEngineException` (retried) instead of `PermanentAiEngineException` when `isEntitlementRace()` is true; otherwise they remain permanent. `isEntitlementRace()` reads the canonical, owner-checked tier via `getKoin().userSession().getOrNull<EntitlementRepository>()?.currentTier?.first()` — deliberately **not** a raw `RevenueCatManager.customerInfo` read, which would skip the owner check and could match a prior account. It returns true when the local tier `atLeast(UserTier.PRO_CLOUD)`, and defaults to **true** (allow the retry) when the tier can't be read: the two failure directions are not symmetric — a wrongly-permanent refusal leaves a paying customer's transcript dead forever, while a wrongly-transient one costs only a few bounded retries that the next attempt's re-read stops.

## Add-on bundles — `V2BundlesScreen`

Subscriptions are not the only purchase surface. `V2BundlesScreen` (`ui/v2/screens/bundles/V2BundlesScreen.kt`) is the "Add Hours" catalog: one-time top-ups of transcription hours (and, on Cloud+AI, KB queries) that stack on the monthly allotment and never expire. It is a fully implemented flow — a usage summary card above a two-column priced grid, a confirm sheet, a Play purchase, and a success screen that polls for the credit the RevenueCat webhook applies server-side.

Four surfaces navigate to it: the Usage screen's "Get More" CTA (`V2UsageScreen.onNavigateToBundles`, shown for `tier.atLeast(UserTier.PRO_CLOUD)`), the playback transcription-cap sheet's "Get More Hours" (`V2PlaybackScreen.onNavigateToBundles`), the KB chat's monthly-AI-limit banner (`onUpgrade`), and Your Plan's `PurchaseBundleRow` — the only one of the four that is visible before the user hits a wall.

See [Add-On Bundles](/rollingrecord/app/monetization/bundles) for the catalog join, the purchase phases, and the credit poll in full.
