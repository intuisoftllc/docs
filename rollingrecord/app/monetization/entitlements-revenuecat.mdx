RevenueCat is the entitlement authority. A single enum defines every entitlement the client understands, a thin manager wraps the process-wide SDK singleton, and a session-scoped repository turns entitlements into an effective tier while guarding against the SDK reporting a different user's purchases.

That authority covers *entitlements*. For the one-time add-on bundle SKUs, RevenueCat owns only purchasability and price — the resource grant is owned by the server (`bundle_config`, served by `get-bundle-catalog`) and applied by the webhook, so a client purchase callback is not evidence that credits exist yet.

## `RcEntitlement`

`RcEntitlement` (`data/billing/RcEntitlement.kt`) is the single source of truth for the RC entitlement taxonomy on Android and a mirror of `supabase/functions/_shared/billing/entitlements.ts` — when one changes, the other must too. Every reference to an RC entitlement `lookupKey` goes through this enum; no entitlement key is string-literalled anywhere else. Each member carries `lookupKey`, `displayName`, `tier`, `kind`, `hasSku`, `description`, and `bypassesCaps` (default false).

| Member | `lookupKey` | `tier` | `kind` | `hasSku` | `bypassesCaps` |
| --- | --- | --- | --- | --- | --- |
| `PRO` | `pro` | `PRO` | `RECURRING_SUB` | true | false |
| `PRO_CLOUD` | `pro_cloud` | `PRO_CLOUD` | `RECURRING_SUB` | true | false |
| `PRO_CLOUD_AI` | `pro_cloud_ai` | `PRO_CLOUD_AI` | `RECURRING_SUB` | true | false |
| `LIFETIME_PRO` | `lifetime_pro` | `PRO` | `INTERNAL_LIFETIME` | false | false |
| `LIFETIME_PRO_CLOUD` | `lifetime_pro_cloud` | `PRO_CLOUD` | `INTERNAL_LIFETIME` | false | false |
| `LIFETIME_PRO_CLOUD_AI` | `lifetime_pro_cloud_ai` | `PRO_CLOUD_AI` | `INTERNAL_LIFETIME` | false | false |
| `FOUNDERS_EDITION` | `founders_edition` | `PRO` | `PUBLIC_LIFETIME` | true | false |
| `DEVELOPER` | `developer` | `PRO_CLOUD_AI` | `INTERNAL_OPS` | false | true |

`RcEntitlement.Kind` distinguishes the four acquisition paths: `RECURRING_SUB` (sold monthly/yearly subs), `INTERNAL_LIFETIME` (comp/employee grants, never sold), `PUBLIC_LIFETIME` (the publicly-sold Founders Edition lifetime), and `INTERNAL_OPS` (the developer grant).

### Companion helpers

- `fromLookupKey(key)` resolves an entitlement by its `lookupKey`, or null if the key is unknown to this client build.
- `LIFETIME_LOOKUP_KEYS` is the set of all internal + public lifetime keys (includes `founders_edition`).
- `resolveTier(customerInfo)` returns the max-ordinal tier across the user's active entitlements — mirroring the server-side cascade — with unknown keys ignored and a null `CustomerInfo` mapping to `UserTier.FREE`.

### Subscription-lapse detection

`CustomerInfo?.isSubscriptionLapsed()` (`data/billing/RcEntitlement.kt`) is the SUBSCRIPTION_LAPSED predicate behind the scheduled-recording lapse guard — its **only** consumer. Its `internal` pure core `isSubscriptionLapsed(activeKeys: Set<String>, allKeysActive: Map<String, Boolean>)` is split from the SDK types so it unit-tests without constructing a `CustomerInfo`.

RevenueCat exposes every entitlement the user has ever held in `entitlements.all` and only the currently-valid ones in `entitlements.active`. A lapse is a known `RcEntitlement` key that appears in `entitlements.all` but is no longer active **and** no currently-active recognized entitlement. The two clauses matter:

- Never-subscribed `FREE` users have an empty `entitlements.all`, so they never trip it.
- A null `CustomerInfo` (signed out, or RC mid-fetch) is **not** lapsed. Asserting "there was a subscription and it is gone" is the whole point — a plain `tier < PRO` test cannot tell that apart from "we don't know yet", which is why it is unsafe to destroy user state on.

#### The one call site

The predicate is applied in `App.disableSchedulesIfLapsed()` (`App.kt`), not inside the repository it ends up calling. `ScheduledRecordingRepository.disableAllForLapse()` takes no decision — it unconditionally flips every enabled schedule off, enqueues each for sync, and returns the count. Two things have to be true before it is reached:

1. **The RC owner check** — `rc.appUserId != null && rc.appUserId == userSessionManager.sessionIdFlow.value`. RC's customer info carries the `appUserID` it belongs to, and the SDK's identity can lag a session switch; acting on info owned by a *different* user would switch off this user's schedules on the strength of the previous account's billing state. Signed out, the session id is `ANONYMOUS_DIR`, which no RC `appUserId` can match, so the same guard covers that case. A mismatch logs and returns.
2. **The lapse assertion** — `if (!rc.info.isSubscriptionLapsed()) return`.

Only then does `scheduleRepository.disableAllForLapse()` run. See [Feature Gating & Upsell](/rollingrecord/app/monetization/feature-gating) for why the guard is keyed on this predicate rather than `tier < PRO`.

#### Not the account-health signal

Account health deliberately does **not** use this predicate. `AccountHealthProvider` documents the reason on its `identityRepository` param: RevenueCat never removes an expired entitlement from `entitlements.all`, so `isSubscriptionLapsed()` stays true **forever** after a single cancellation — a status dot driven by it would announce "your subscription has ended" for the rest of the account's life, long after there was anything to act on. The roll-up's SUBSCRIPTION_LAPSED input is `identityRepository.graceState.map { it != null }` instead: the server sets the grace columns when a recurring cloud sub ends, the RC webhook clears them on resubscribe, and the daily sweeper clears them when the window expires, so a non-null value means "inside the window". See [Account Health](/rollingrecord/app/auth/account-health).

<Note>
The KDoc on `isSubscriptionLapsed()` in `RcEntitlement.kt` still calls it "shared by the account-health roll-up and the scheduled-recording lapse guard". That half is stale — it describes where the predicate lived before account health moved to the bounded grace-window signal. Everything the KDoc says about the predicate's *semantics* is accurate.
</Note>

## Developer bypass

`bypassesCaps` is true on `DEVELOPER` only. Per its KDoc, holding the `developer` entitlement grants `pro_cloud_ai`-tier access **and** skips the usage-cap gate and the rate-limit gate in ai-engine (the code labels these Gate 4 and Gate 5). Every tier entitlement — including the lifetimes and `FOUNDERS_EDITION` — is always subject to its tier's normal quota; only the ops grant bypasses. The developer entitlement is granted through the RC dashboard.

## `RcCustomerInfo`

`RcCustomerInfo` (`data/billing/RevenueCatManager.kt`) is a `data class(appUserId: String?, info: CustomerInfo?)`. The RevenueCat SDK is a process-wide singleton whose identity can lag the app's signed-in user (mid-`logIn`, a stuck identity switch, or an offline cold start that restored a prior user's cached receipt). Pinning each emission to the `appUserID` it was fetched for lets consumers refuse entitlements that don't belong to the currently signed-in auth user — without it, one user's paid entitlements could surface as, and get cached for, a different user.

## `RevenueCatManager`

`RevenueCatManager` (`data/billing/RevenueCatManager.kt`) is a thin wrapper over the SDK singleton. It takes one constructor param — `onTierRaised: (UserTier) -> Unit = {}` — and exposes `customerInfo: StateFlow<RcCustomerInfo>`, the `customerId`, and `isConfigured`, plus:

| Method | Purpose |
| --- | --- |
| `linkToAuthUser(authUserId, email?, displayName?)` | Logs RC in to the Supabase auth user id, sets the `$email` / `$displayName` reserved attributes, and calls `syncPurchases()` so subscriptions follow the user across devices and reinstalls. |
| `updateDisplayName(displayName)` | In-place `$displayName` update for an already-signed-in user. |
| `logOut()` | Resets the SDK to anonymous on sign-out (clears the snapshot synchronously so no stale paid entitlement lingers). |
| `checkPurchaseGuard()` | Cross-store double-billing guard. |
| `getCurrentOffering()` | Fetches `offerings.current` — the subscription paywall — for the plan screens. |
| `getOffering(identifier)` | Fetches a **named** offering (e.g. the `bundle` add-on offering) rather than `offerings.current`; a missing or package-less offering maps to `Empty`, not `Error`. |
| `purchase(activity, pkg, oldProductId?)` | Launches the store purchase / plan-change flow — also the one-time (non-subscription) bundle path, called with no `oldProductId`. |
| `restorePurchases()` | Explicit "Restore purchases" path. |
| `refreshCustomerInfo()` | Forces a cache-bypassing (`CacheFetchPolicy.FETCH_CURRENT`) customer-info fetch on app foreground so a mid-session lapse surfaces without a cold restart. Safe no-op when `Purchases` is not configured. |
| `startObserving()` | Wires the `updatedCustomerInfoListener` and does the initial customer-info fetch. |

### Named offerings — `getOffering` vs `getCurrentOffering`

Add-on bundles live in their own RevenueCat offering so they never appear as purchasable plans on the subscription paywall, and reaching them needs a lookup by identifier. `getCurrentOffering()` feeds `ChoosePlanViewModel`; `getOffering("bundle")` feeds `V2BundlesViewModel` (see [Add-On Bundles](/rollingrecord/app/monetization/bundles)).

Both return `OfferingsResult.Error("Store not ready")` when `Purchases.isConfigured` is false, but their `Empty` mappings differ: `getCurrentOffering` maps only a null `offerings.current` to `Empty`, while `getOffering` maps `offering == null || offering.availablePackages.isEmpty()` to `Empty`. An offering that has not been configured yet is an empty catalog, and "no bundles available" is a better outcome than an error banner blaming the network. It logs `getOffering($identifier): packages=N` on success and `getOffering($identifier) failed: code=…, message=…` on error.

`refreshCustomerInfo()` was added for the same class of problem on the other side of the SDK: cached customer info is served for a few minutes, so a background-to-foreground within that window kept serving the pre-lapse tier and suppressed the grace banner, whose tier gate still saw Pro+Cloud.

### `onTierRaised` — the single upward-movement hook

Every customer-info path — `linkToAuthUser`, `purchase`, `restorePurchases`, `logOut`, and the SDK's `updatedCustomerInfoListener` — funnels through the private `emitCustomerInfo(info)`. That method now also computes `RcEntitlement.resolveTier(info)`, tracks a `lastTier` (initialised `FREE`), and fires `onTierRaised(tier)` **only** when the tier moves up (`tier.ordinal > previous.ordinal`). Hooking it here rather than in the two purchase ViewModels catches every raise — purchase, restore, promotional grant, and cross-device sync — in one place. The call is wrapped in `runCatching { }` so a listener failure can never break the customer-info flow the whole UI reads.

Downgrades and lapses deliberately do **not** fire: the server is the stricter authority, so asking it to re-read could only take access away sooner, and the stale entitlement it still has cached expires on its own. `onTierRaised` is wired in `di/DataSourceModule.kt` to `EntitlementRefreshSignal.markPurchaseCompleted` (see below).

A one-time bundle purchase also flows through `emitCustomerInfo`, but it grants no entitlement — so it never raises the tier and never arms the refresh signal. That credit reaches the client through the usage snapshot instead.

The `purchase()` `onError` log now emits `error.underlyingErrorMessage` and the replaced `oldProductId` alongside `error.message`: `PurchasesError.message` is a constant `code.description`, so four distinct Play Billing failures (`BILLING_UNAVAILABLE`, `ITEM_NOT_OWNED`, `FEATURE_NOT_SUPPORTED`, and RC's own non-subscription guard) all collapse into the same `PurchaseNotAllowedError` text — a log carrying only `message` cannot tell them apart.

## Instant-purchase entitlement refresh (`X-Entitlement-Refresh`)

The server reads RevenueCat live on every request, but caches the result per customer for roughly five minutes in per-warm-instance module scope. A user who browsed the app while free leaves an empty entitlement set cached against their id; the instant they buy, the client flips to the paid tier while the server keeps answering from that cached "no" for minutes — refusing transcription and reporting "out of minutes" on a plan they just paid for. Nothing external can invalidate that cache: it is per warm instance, so neither the RevenueCat webhook nor any other request can reach the instance holding the stale entry.

### `EntitlementRefreshSignal`

`EntitlementRefreshSignal` (`data/billing/EntitlementRefreshSignal.kt`) decides when the next request should ask the server to skip that cache. It is an **app-level** `UserScopedCache` holding a single `AtomicBoolean pending` — no per-user data, but it implements the cache anyway so a pending flag from a prior account cannot stamp the next account's first call. It is constructed with `localTier: () -> UserTier` (a lambda over `RevenueCatManager` rather than the session-scoped `EntitlementRepository`, which a sign-out would tear down).

| Method | Behavior |
| --- | --- |
| `isPending()` | True while the next request should carry the header. **Not** consumed on read — the header must ride every request until the server's answer actually changes, because the request carrying it may be throttled server-side, rejected, or simply not the call the user is waiting on. |
| `markPurchaseCompleted(tier)` | Arms the hint immediately on a local purchase or restore, so the very first post-purchase request already carries it. |
| `onServerTierObserved(serverTierWire)` | Resolves the wire key via `RcEntitlement.fromLookupKey(it)?.tier` and delegates to the testable `internal reconcile(serverTier, localTier)`. |
| `clearForUserSwitch()` | Resets `pending` on a session change. |

`reconcile(serverTier, localTier)` treats a null server tier as `UserTier.FREE` (null means "no paid entitlement", the same statement as FREE, not a rung below it — otherwise every genuinely free user would look like a disagreement and arm the hint permanently). It **arms** only when `localTier.ordinal > effectiveServerTier.ordinal` — the client believes it holds more than the server granted. Local-below-server is never armed: the server is the stricter authority, and a re-read would not change its answer. Once the server agrees, `reconcile` **clears** the flag.

Firing on disagreement rather than only on a local purchase callback is what covers restores, purchases made on another device, and promotional grants — none of which fire a local purchase callback — while costing nothing for genuinely free users, whose local tier already agrees with the server's answer so the hint never fires.

### `EntitlementRefreshInterceptor`

`EntitlementRefreshInterceptor` (`data/remote/EntitlementRefreshInterceptor.kt`) is an OkHttp `Interceptor` that adds the header `X-Entitlement-Refresh: 1` while `signal.isPending()`, and otherwise proceeds untouched. It is a **caching hint, never an entitlement claim**: the server still reads the answer from RevenueCat (subject to a 20-second server-side age floor), so a forged header earns only a fresh, honest "no". Making the header itself unforgeable would mean verifying the Play receipt ourselves — precisely the job RevenueCat already does.

### Wiring

The signal is constructed in `di/NetworkModule.kt` with `localTier` resolving through `RcEntitlement.resolveTier(RevenueCatManager…)`, and it is armed from two sources:

- `RevenueCatManager.onTierRaised` → `markPurchaseCompleted` (wired in `di/DataSourceModule.kt`) for local purchase, restore, promo, and cross-device raises.
- `UsageRepository.onServerTierObserved` → `onServerTierObserved` (wired in `di/NetworkModule.kt`) for the server's own tier view reported on each usage snapshot.

See [Usage Metering & Caps](/rollingrecord/app/monetization/usage-metering) for the snapshot side of that second source.

## `EntitlementRepository`

`EntitlementRepository` (`data/repository/EntitlementRepository.kt`) is user-session-scoped and derives the effective tier. `currentTier: SharedFlow<UserTier>` combines four inputs — `AuthRepository.authState`, `RevenueCatManager.customerInfo`, `UserSettingsDataSource.lastKnownTier`, and `DevFlags.tierOverride` — deduplicates identical evaluations, logs each real change, and shares the pipeline across all subscribers (`SharingStarted.Eagerly`, `replay = 1`) so the combine + log runs exactly once regardless of observer count.

The **owner guard** is the core correctness rule: RC customer info is trusted only when its owning `appUserId` matches the signed-in auth user. Resolution order:

- **Signed out** → `UserTier.FREE` (the cache is thrown away).
- **Loading** → the cached tier (`cached ?: FREE`) — treating a mid-probe state as FREE causes an auth-flap storm.
- **Signed in, RC owner matches** → `RcEntitlement.resolveTier(rc.info)`.
- **Signed in, RC identified as a different user** → forced to `FREE` (never expose or cache a tier that can't be attributed to this user).
- **Signed in, RC not yet hydrated for this user** → the per-user cached tier, so a returning paid user isn't degraded on a cold or offline start.

There is no mutator — the tier is derived, never set. As a side effect the repository persists the resolved tier to `lastKnownTier` only when the RC owner matches the signed-in user. The server stays the authoritative gate: a genuinely-lapsed entitlement is caught at the API layer with `subscription_required`, so the worst case of a stale cache is a brief "looks paid but server rejects paid calls" window.

## Billing result types

Three sealed result types model the outcomes of the RC calls:

- `OfferingsResult` (`data/billing/PurchaseFlowResult.kt`) — `Success(offering)` / `Empty` (no offering to show — either none marked Current, or the requested named offering is missing from the RC project or has no available packages; a configuration state, not an error) / `Error(message)`.
- `PurchaseFlowResult` (`data/billing/PurchaseFlowResult.kt`) — `Success(customerInfo)` / `Cancelled` (user backed out) / `Error(message)`.
- `PurchaseGuardResult` (`data/billing/PurchaseGuardResult.kt`) — `Offer` / `AlreadySubscribedSameStore(store)` / `BlockedByOtherStore(store)`. The last blocks a purchase when the user is already subscribed via a different store (e.g. App Store while on Android), preventing double-billing.
