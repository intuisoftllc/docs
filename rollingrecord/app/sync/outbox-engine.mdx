title: "Sync Outbox & Enqueue"
description: "The pointer-based outbox: how local writes enqueue upserts and tombstones, how SyncEngine.runPush drains and packs them, and how accepted / server_wins / rejected outcomes and backoff are handled."
---

Every user-facing repository write calls the outbox after its DB write. The outbox stores **pointers only** — an `(entityType, rowId, operation)` triple, never row content — so at drain time the engine re-reads current Room state and intermediate edits coalesce naturally.

## `SyncEnqueuer` — the façade repositories call

`SyncEnqueuer` (`data/sync/SyncEnqueuer.kt`) is the typed front door the 10+ user-facing repositories call after every write. It lives in `UserSessionScope`.

| Method | For |
| --- | --- |
| `upsert(entity, rowId)` | single-PK entity insert/update |
| `tombstone(entity, rowId)` | single-PK entity delete |
| `upsertComposite(entity, parentId, childId)` | junctions (`CONTEXT_RECORDING`, `CONTEXT_SESSION`) — encodes `"parentId::childId"` via `encodeCompositeRowId` |
| `tombstoneComposite(entity, parentId, childId)` | junction delete |

Enqueue failures are logged and **swallowed** — the user's primary action (saving a recording, deleting a note) already succeeded by the time enqueue runs, so throwing would undo nothing. A missed entry only delays that row's sync until its next write, which re-enqueues successfully.

## The outbox table

`SyncOutboxEntity` (`data/local/db/entity/SyncOutboxEntity.kt`) backs table `sync_outbox`. Columns: `id` (autogen PK), `entityType`, `rowId`, `operation`, `enqueuedAt`, `attempt_count`, `last_rejected_code`, `last_attempt_at`, `next_attempt_at`. The load-bearing constraint is `UNIQUE(entityType, rowId)` — the **squash index**.

`SyncOutboxDao` (`data/local/db/dao/SyncOutboxDao.kt`) enqueues via `insertReplace` (`OnConflictStrategy.REPLACE`) so repeated writes to one row collapse to a single entry carrying the latest operation. `OP_UPSERT = "upsert"`, `OP_TOMBSTONE = "tombstone"`.

| Operation | Meaning | Squash behavior |
| --- | --- | --- |
| `upsert` | server INSERTs or UPDATEs the current Room row (revives tombstone-GC'd rows as INSERT naturally) | repeated edits collapse to one entry |
| `tombstone` | server marks the row deleted (client already set the delete intent locally) | REPLACES a pending upsert — latest op wins, so a short-lived insert-then-delete never reaches the server |

Why pointers, not snapshots: a content snapshot taken at enqueue time would push stale bytes whenever the user edited again before drain. Reading current state at drain time dedupes to whatever is current.

## `SyncOutboxRepository`

`SyncOutboxRepository` (`data/sync/SyncOutboxRepository.kt`) is a thin typed wrapper over the DAO:

| Method | Purpose |
| --- | --- |
| `enqueueUpsert` / `enqueueTombstone` | type-safe enqueue taking the `WireEntity` enum |
| `drainableNow(limit)` | rows eligible right now — `next_attempt_at IS NULL OR <= now`, capped at `limit` |
| `pendingOps()` | full list including backed-off rows (resync recovery / dev observability) |
| `markProcessed(entity, rowId)` | drop an entry after a successful push-ack |
| `removeOrphan(entity, rowId)` | drop an entry whose source row is gone (logically distinct from `markProcessed`) |
| `hasPending(entity, rowId)` | protects a locally-edited row from the pull orphan sweep |
| `recordRejection(entity, rowId, code, nextAttemptAt)` | bump `attempt_count`, stamp the code, set the backoff deadline |
| `clearAllBackoff()` | connectivity-restore wake — null out every `next_attempt_at` (keeps `attempt_count`) |
| `getStuck(threshold)` | snapshot of entries past the retry threshold, for Crashlytics |

## `SyncEngine.runPush` — the drain driver

<Note>
**Tier gate before any push.** `SyncEngine.sync()` short-circuits at the very top and returns `SyncResult(pushed = 0, pulledEntities = 0)` when the tier is below `UserTier.PRO_CLOUD` — **unless** `force` is set. Every sync endpoint is `pro_cloud`-gated server-side, so below that tier a cycle is a guaranteed 403 push *and* a 403 pull; and a free user's outbox is never empty (`SyncEnqueuer` is ungated and `SyncEnqueueRecovery` re-enqueues on cold start), so `runPush`'s empty-outbox shortcut never saves the wasted round trips. The tier is read **live** per call via `entitlementRepository.currentTier.first()` (`getOrDefault(FREE)`) then `tier.atLeast(UserTier.PRO_CLOUD)`, off the new constructor input `entitlementRepository: EntitlementRepository`. `force` **fails open** — an explicit user retry spends one 403 rather than silently no-op on someone who just upgraded; automatic callers fail closed. Like the Wi-Fi-only skip, the gate does **not** stamp `lastAttemptAt` / `lastError` (no attempt was made, so no cooldown penalty and no failure UI).
</Note>

There is no dedicated "push worker" class beyond the generic `SyncWorker`; the drain logic is `SyncEngine.runPush` (`data/sync/SyncEngine.kt`). Each `runPush` call sends at most one batch; a single `sync()` drives the drain loop up to `MAX_DRAIN_ITERATIONS` (3) times, calling `runPush` once per iteration while the prior push processed `>0` rows, so one `sync()` can send up to three `sync-push` batches. `runPush`'s steps:

1. **Fetch** `drainableNow(MAX_BATCH_OPS_CLIENT = 450)` — backoff-eligible rows only, capped so a 5000-row backlog doesn't load entirely into memory.
2. **Pack** ops until the op count or byte budget is reached. `MAX_BATCH_BYTES_CLIENT = 4_718_592` (4.5 MB) with a 10-byte wrapper allowance; the server rejects `> 500` ops or `> 5 MB` with `batch_too_large`, so the client self-caps below that. Leftover rows defer to the next sync.
3. **Skip disabled groups.** Ops whose `WireEntity.group` is disabled in the user's sync preferences are left on the outbox (so they drain when re-enabled) rather than sent to be rejected. See [Sync Preferences](/rollingrecord/app/sync/sync-preferences).
4. **Build each row** via `transform.buildPushRow(entity, rowId)` (or `buildTombstoneRow` for deletes). `opsIndexToEntry` is built in lockstep with the ops array so a rejection's `index` maps back to the originating outbox row.
5. **POST** `sync-push`, then walk `results[]`.

The pack loop has one critical safety invariant: a `DekUnavailableException` from `buildPushRow` (offline, can't unwrap the DEK to encrypt) **aborts the entire batch and leaves the whole outbox intact**. It is never treated as an orphan — letting an offline send fall through to the orphan sweep would wipe every pending change. A per-entry build error (non-DEK) skips just that entry, keeping it on the outbox; a non-tombstone entry whose `buildPushRow` returns `null` (source row deleted before push) is the one case that gets `removeOrphan`.

### Per-op outcomes

| Outcome | Action on outbox | Notes |
| --- | --- | --- |
| `accepted` | `markProcessed` by the **sent** id | authoritative row applied via `tryApplyOrDefer` |
| `server_wins` | `markProcessed` by the **sent** id | may return a *different* row (the `c_settings` `UNIQUE(auth_user_id)` reinstall case) — drain by the `opsIndexToEntry` id, adopt the server row |
| `rejected`, `code = not_found` | `markProcessed`, no retry | server row hard-deleted after its tombstone was purged; local row left for the pull orphan sweep this same cycle |
| `rejected`, `code = fk_violation` | splits on the LOCAL parent | **parent present** → transient: left with `recordRejection` + backoff, resolves on a later cycle when the parent's own push lands. **parent MISSING** → `markProcessed` (drained, no retry) plus an `AppLogger.w` (`save = true`) `runPush: FK_VIOLATION drain …` line — the entry can never be satisfied, so retrying it forever only clogs the outbox |
| `rejected` (other) | left with `recordRejection` + backoff | `attempt_count++`, `last_rejected_code` set, `next_attempt_at = now + backoff` |
| unknown | left unchanged | logged |

The two drained rejection codes are companion constants: `CODE_NOT_FOUND = "not_found"` and `CODE_FK_VIOLATION = "fk_violation"`.

### Draining by the sent id

`drainRowIdFor(responseIndex, opsIndexToEntry, echoedRowId)` (a free function in the same file) resolves which outbox key to drain by. The outbox entry is filed under the id **this client minted**; `server_wins` is precisely the outcome where the server may hand back a *different* row. On the `c_settings` reinstall path a fresh client mints a new settings id, collides with `UNIQUE(auth_user_id)`, and the server returns its stored row so the client adopts that id and content. Draining by the echoed id matched nothing, so the entry survived and re-pushed forever (`23505 → server_wins → still undrained`). Mapping index N back through `opsIndexToEntry` drains the right entry; for an ordinary `accepted` op the two ids are identical.

### `missingLocalParent` — transient vs unsatisfiable FK

`missingLocalParent(entity, rowId)` is what splits an `fk_violation` into "retry" and "drain forever". It decodes the composite `rowId` via `decodeCompositeRowId` and checks `existsById` on the parent and child DAOs. Only the two composite-PK junctions can have a *missing* parent: `WireEntity.CONTEXT_RECORDING` (checked against `contextDao` / `recordingDao`) and `WireEntity.CONTEXT_SESSION` (`contextDao` / `recordingSessionDao`). Every other entity returns `false`, so a foreign-key rejection on a normal entity keeps its existing retry behaviour untouched.

`context_sessions` / `context_recordings` carry no Room `foreignKeys`, so a junction can outlive the parent it points at (observed 2026-08-25 on a junction whose `recording_session` had been deleted locally). The check is deliberately conservative: an unparseable entity or `rowId` answers `false` and falls through to the normal rejection + backoff path — draining a row it cannot identify is unrecoverable, so the cost of a wrong `false` is one more retry while a wrong `true` would discard a real link. It needs two new engine constructor inputs, `contextDao: ContextDao` and `recordingSessionDao: RecordingSessionDao`; `RecordingSessionDao.existsById(id)` is the new query added for it.

This reactive drain has a proactive counterpart: `RecordingRepository.deleteSession` now tombstones a session's `context_session` junctions so they never strand in the first place — see [Pull & Reconciliation](/rollingrecord/app/sync/reconcile-engine).

## Backoff schedule

`SyncEngine.backoffMillis(attemptCount)` computes the cool-down applied on rejection, with ±20% jitter so a server hiccup that rejects many rows at once doesn't queue them all for the same instant.

| `attempt_count` | cool-down (±20% jitter) |
| --- | --- |
| 1 (first rejection) | 30 seconds |
| 2 | 2 minutes |
| 3+ | 10 minutes (cap) |

Connectivity-restore and manual sync override this entirely by clearing `next_attempt_at` via `clearAllBackoff()`.

## Stuck-row telemetry

When an entry crosses `CRASHLYTICS_THRESHOLD = 10` attempts, `reportCrashlyticsForStuck()` files a single non-fatal, deduped per process by an `entityType:rowId:last_rejected_code` fingerprint (a restart re-logs a still-stuck entry, which is desired). The UI surfaces a lower "stuck" threshold via `SyncOutboxDao.stuckCountFlow`.

## Diagnostics: `SyncRejectionDebugLogger`

`SyncRejectionDebugLogger` (`data/sync/SyncRejectionDebugLogger.kt`) dumps the rejected row's local NOT-NULL fields to the rolling app log (tag `SyncReject`, `save = true`) so a stuck-sync report can be diagnosed without server logs. It is PII-safe by construction — UUIDs, enums, counts, and lengths only; recording/transcript/recording-session get full field dumps, other entities get an existence check. The call site in `runPush` runs unconditionally — it is not debug-gated, so rejection dumps land in release builds too (safe by the PII contract above; written via `AppLogger` `save = true`).

## Safety net: `SyncEnqueueRecovery`

`SyncEnqueueRecovery` (`data/sync/SyncEnqueueRecovery.kt`) is a **permanent** safety-net — explicitly excluded from the backfill-cleanup sweep, not a one-shot migration. `enqueueAllUnsynced()` walks all 13 synced tables (11 single-PK + 2 composite junctions; `SETTINGS` is excluded — it lives in DataStore with no `getUnsynced*` accessor) via `getUnsyncedIds()` / `getUnsyncedPairs()` (`remoteSyncedAt IS NULL`) and re-enqueues, catching any repository write that missed its enqueuer call. It is idempotent (already-synced rows are skipped; the squash index collapses duplicates) and cheap on hot start (13 indexed scans returning empty once everything is synced).

### `prepareForCloudReset` — rebuild the outbox from device

`prepareForCloudReset()` is the recovery pass for the `cloud_reset` rebuild-from-device flow that [`runPull`](/rollingrecord/app/sync/reconcile-engine) invokes after the server hard-destroyed a lapsed account's cloud data and the user resubscribed. It runs three steps:

1. **Clears the `remoteSyncedAt` marker on all 13 synced DAOs** — `recordingDao.clearSyncMarkersForCloudReset()` plus `clearRemoteSyncedAtForCloudReset()` on the other twelve (`actionItem`, `category`, `contextCard`, `context`, `contextRecording`, `contextSession`, `note`, `recordingSession`, `scheduledRecording`, `searchMessage`, `searchThread`, `transcript`). Every survivor now looks never-pushed.
2. **Cuts the blueprint server link** via the new constructor input `blueprintDao.cutServerLinkForCloudReset()`. Blueprints replicate through `ai-engine`, not `sync-push`, so the outbox can't protect them — cutting the link turns them into offline drafts that pull leaves alone rather than deleting-as-absent.
3. **Re-enqueues everything** through the existing `enqueueAllUnsynced()` walk, which now matches every row because step 1 nulled the column it filters on.

It is idempotent (re-clears already-null markers; the outbox `UNIQUE(entityType, rowId)` collapses duplicate enqueues). **Order invariant:** the caller — `runPull`'s `cloud_reset` branch — MUST run this to completion **before** `settings.resetSyncCursor()`. If the cursor advances first and the process dies, the `cloud_reset` signal is lost and the next pull reconciles the library away. See [Pull & Reconciliation](/rollingrecord/app/sync/reconcile-engine) for the pull-side trigger.

</Note>
