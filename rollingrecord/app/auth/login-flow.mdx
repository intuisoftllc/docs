V2 requires sign-in. While the session is anonymous, `V2App` (`ui/v2/V2App.kt`) mounts a self-contained sign-in flow; once Clerk establishes a session the auth observer swaps the whole tree to `V2MainNavHost`. Sign-in is email OTP first, Google second — there is no password. A returning user goes email → OTP; a new user runs a three-page onboarding (name → profile photo → review) and the Clerk account is not created until the final "Create account" tap on the Review page.

## `V2LoginNavHost` — the six-route flow

`V2LoginNavHost` (`ui/v2/navigation/V2LoginNavHost.kt`) is a Compose `NavHost` with `startDestination = V2LoginRoot`. It creates **one** `V2LoginViewModel` via `koinViewModel()` and passes that single instance to all six routes — the email, name, photo, review, and OTP screens read and mutate the same `LoginUiState`, so a per-route ViewModel would lose state across navigations. A `LaunchedEffect` collects `viewModel.navEvents` and drives `navController`. The six destinations are `@Serializable` objects in `ui/v2/navigation/V2LoginRoutes.kt`.

| Route | Screen | VM action | Next |
| --- | --- | --- | --- |
| `V2LoginRoot` | `V2LoginScreen` | `onContinueWithEmail` (nav callback) / `onContinueWithGoogle` (VM) | Email entry, or (Google success) session swap |
| `V2EmailEntry` | `V2EmailEntryScreen` | `onEmailNext` → `checkAndStartV2` | OTP entry (existing user, code already sent) OR name entry (new user) |
| `V2NameEntry` | `V2NameEntryScreen` | `onNameNext` | Profile-photo page — **no Clerk account is created here** |
| `V2ProfilePhoto` | `V2ProfilePhotoScreen` | `onPhotoContinue` / `onPhotoSkip` | Review page |
| `V2ReviewConfirm` | `V2ReviewConfirmScreen` | `onConfirm` → `createSignUpAndSendOtpV2` | OTP entry — the account is created and the code sent here |
| `V2OtpEntry` | `V2OtpScreen` | `onOtpSubmit` → `verifySignInOtpV2` / `verifySignUpOtpV2` | No nav event — Clerk emits `SignedIn`, `V2App` swaps to `V2MainNavHost` (new accounts get the recovery-code overlay first) |

Back-stack rules are deliberate. `V2LoginRoot` has no back (it's the front door). The email, name, photo, and review steps each pop to their immediate predecessor via the default `popBackStack()` — email → root, name → email, photo → name, review → photo — so backing through onboarding preserves everything typed and the held photo. `V2OtpEntry` back pops **all the way** to root, skipping the intermediates, because by the time the user is on OTP the Clerk attempt already exists and re-entering the same email re-sends a code. `V2OtpScreen` binds system back to the same pop via `BackHandler`.

## Deferred Clerk account creation (RR-519)

The new-user path creates the Clerk account **late**. `onNameNext` no longer calls `createSignUpAndSendOtpV2` — it only validates the first/last name and emits `ToProfilePhoto`. The account is created by `onConfirm` on the Review page, which calls `AuthRepository.createSignUpAndSendOtpV2(email, firstName, lastName)` and, on success, routes to the OTP screen. Until that tap, nothing exists server-side, so a user can back out of any onboarding page and leave no partial account behind. Clerk's `SignUp.create` is atomic, so a failed `onConfirm` surfaces a generic snackbar and keeps the user on Review with no half-created account.

The three onboarding pages share a progress indicator: `V2OnboardingDots` (`ui/v2/screens/login/V2OnboardingDots.kt`) renders label-free dots via `LoginStepScaffold`'s optional `progressDots` slot — name is `current = 0`, photo `current = 1`, review `current = 2`, all `total = 3`. The email and OTP screens pass no dots.

## `V2LoginViewModel` and `LoginUiState`

`V2LoginViewModel` (`ui/v2/screens/login/V2LoginViewModel.kt`) orchestrates the flow against `AuthRepository`. It implements `V2LoginViewModelContract` (`ui/v2/screens/login/V2LoginViewModelContract.kt`), the interface the screens depend on so a debug-only `PreviewLoginViewModel` can render them without Clerk or the network.

All step screens read one immutable snapshot, `LoginUiState`:

| Field | Type | Meaning |
| --- | --- | --- |
| `email` / `firstName` / `lastName` / `otpCode` | `String` | Bound field values |
| `isLoading` | `Boolean` | A network call is in flight (drives the CTA spinner) |
| `pendingAttempt` | `AuthAttempt?` | `SignInPending` or `SignUpPending` — tells the OTP screen which verify method to call |
| `otpError` | `Boolean` | True after a verify rejects the code; flips the OTP screen into its inline error variant. Cleared on typing, resend, and the next submit |
| `personalizedAds` | `Boolean` | Sign-up "Personalized ads" opt-in (RR-521), default off, folded into the name page; applied to the new account's per-user setting after sign-in |
| `localPhotoPath` | `String?` | Cache-file path of the photo picked on the onboarding photo page (RR-519); held through Review and uploaded by `V2App` after sign-in |
| `resendNonce` | `Int` | Bumped only when an OTP resend **succeeds**; the OTP screen keys its 30-second cooldown on it so a failed resend doesn't reset the timer |

`AuthAttempt` (`SignInPending` / `SignUpPending`) is only a tag; the real Clerk attempt lives in `Clerk.auth.currentSignIn` / `currentSignUp`. Navigation is emitted as `V2LoginNavigation` (`ToEmailEntry`, `ToNameEntry`, `ToProfilePhoto`, `ToReviewConfirm`, `ToOtpEntry`, `PopToRoot`, `FlowComplete(isNewUser)`) — the production NavHost ignores `FlowComplete` (the `V2App` auth observer handles the session swap); only the dev preview NavHost consumes it.

Every network entry point first calls `offlineAndEmitted()`, which fast-fails via `ConnectivityMonitor` and emits `SnackbarMessage.NoInternet` before doing any work — the DEK-provisioning leg alone can hang ~60s against a dead connection, and on the OTP step this avoids consuming a code against a doomed request. `emitErrorSnackbar` maps exceptions to a `SnackbarMessage`:

| Exception | `SnackbarMessage` |
| --- | --- |
| `InvalidOtpException` | `InvalidCode` |
| `TooManyRequestsException` | `TooManyAttempts` |
| `DekProvisioningException` | `SecureStorageSetupFailed` |
| `IOException` | `NoInternet` |
| anything else | `SignInFailed` |

## The step screens

All the step screens share `LoginStepScaffold` (`ui/v2/screens/login/LoginStepScaffold.kt`): an optional top progress-dots slot, a back chevron, a centered icon/title/subtitle header, a caller-provided content slot, and a full-width pill CTA pinned to the bottom that rises with the keyboard. The header is fully parameterized (icon painter, tint, title, subtitle) so the OTP and name screens can swap the whole header into a red error variant rather than layering a separate error UI.

- **`V2LoginScreen`** (`ui/v2/screens/login/V2LoginScreen.kt`) — the landing screen. Renders the real launcher icon resolved from `PackageManager` (adaptive-icon layers composited and rounded-square clipped), the wordmark, and the slogan (`login_hero_subtitle`), then two bottom CTAs: "Continue with email" (filled primary pill → `onContinueWithEmail`) and "Continue with Google" (white outlined pill → `viewModel.onContinueWithGoogle(activity)`), plus a `LegalAgreementText` footer.
- **`V2EmailEntryScreen`** (`ui/v2/screens/login/V2EmailEntryScreen.kt`) — one `OutlinedTextField` bound to `state.email`. The Next pill is enabled only when `EmailValidator.isValid(email) && !isLoading`; Next calls `onEmailNext`.
- **`V2NameEntryScreen`** (`ui/v2/screens/login/V2NameEntryScreen.kt`) — onboarding page 1/3, the new-user first/last name step. Validation is press-triggered: Next stays enabled and tapping it with a missing field flips the screen into the error variant (red header icon, red field borders, inline error) rather than disabling the button. On both-valid it calls `onNameNext`, which advances to the photo page without creating the account. The RR-521 "Personalized ads" opt-in `Switch` is folded in here; its value rides `LoginUiState.personalizedAds`.
- **`V2ProfilePhotoScreen`** (`ui/v2/screens/login/V2ProfilePhotoScreen.kt`) — onboarding page 2/3, an optional profile photo. An `OnboardingProfileAvatar` previews the picked image (or a seeded fallback), and a `V2ProfilePhotoSheet` offers gallery / camera / remove. A pick is copied and compressed into a unique cache file and held in `LoginUiState.localPhotoPath` (not uploaded — no account exists yet). The single adaptive CTA reads "Skip for now" with no photo (`onPhotoSkip`) and "Continue" once one is added (`onPhotoContinue`); both advance to Review. See [Account Profile](/rollingrecord/app/auth/profile) for the held-locally-then-uploaded lifecycle.
- **`V2ReviewConfirmScreen`** (`ui/v2/screens/login/V2ReviewConfirmScreen.kt`) — onboarding page 3/3. Shows the avatar (tap to change), a card with the name (tap opens `V2EditNameDialog`, edits are in-memory only since no account exists) and the read-only sign-in email, and a "Create account" CTA (enabled when both names are non-blank) that calls `onConfirm`. This is where the Clerk account is actually created.
- **`V2OtpScreen`** (`ui/v2/screens/login/V2OtpScreen.kt`) — a six-box `OtpInput` (`OTP_LENGTH = 6`) under an "Enter code" label. A rejected code (`otpError`) flips the whole screen into its error variant: red header/boxes, an inline "request a new code" action, an expiry-note banner, and the CTA relabelled "Try again". A 30-second countdown (keyed on `resendNonce`) gates the Resend link before it becomes tappable.

## OTP verification and the account handoff

`onOtpSubmit` reads `pendingAttempt` and calls `verifySignInOtpV2` (existing user) or `verifySignUpOtpV2` (new user) on `AuthRepository`. For the sign-up path it pre-flags three values on `V2OnboardingSignals` (`ui/v2/screens/onboarding/V2OnboardingSignals.kt`) **before** verifying:

- `nextSignInIsNewAccount = true` — so `V2App` mounts the recovery-code save overlay immediately on the `SignedIn` emission instead of flashing the home screen first.
- `pendingPersonalizedAds` — the sign-up ads opt-in, applied to the new account's per-user setting once the session DB is ready (RR-521).
- `pendingProfilePhotoPath` — the locally-held onboarding photo, uploaded to Clerk after the session is established (RR-519; `setProfileImage` needs a signed-in user, which only exists post-verify).

The `nextSignInIsNewAccount` pre-flag is only the fast path — the DEK fetch inside verify also records the server's `has_recovery_code` answer on `onboardingSignals.serverSaysNoRecoveryCode`, so a plain sign-IN to an account that never got a code mounts the same blocking overlay.

On success the ViewModel resets `LoginUiState` to a clean slate (so the next sign-in after a sign-out doesn't inherit this attempt's email/code/photo) and emits `FlowComplete`; no navigation happens here — Clerk emits `SignedIn` on its `userFlow` and the `V2App` auth observer performs the session swap. On a wrong or expired code (`InvalidOtpException`) it clears the entered code and flips `otpError` with no snackbar (the screen itself carries the error). A `DekProvisioningException` is special: verify already succeeded and consumed the code, but the account key couldn't be provisioned so `AuthRepository` signed the session back out — the ViewModel resets state and emits `PopToRoot` so the user gets a fresh code from email entry. See [Authentication (Clerk)](/rollingrecord/app/auth/clerk) for the DEK gate.

## Google sign-in

`onContinueWithGoogle(activity)` calls `AuthRepository.signInWithGoogle(activity)` (`data/auth/AuthRepository.kt`), which uses the **Clerk-hosted browser OAuth** flow — `Clerk.auth.signInWithOAuth(OAuthProvider.GOOGLE)` launches a Custom Tab; there is no native account picker. The AndroidX Credential Manager selector was removed (2026-09-06) because it failed with `[16] Account reauth failed` on Play App Signing builds; the browser flow is independent of the app's signing certificate, so it behaves identically across debug / upload-key / Play builds. (The `activity` param is kept only for call-site symmetry, and the standalone `GoogleCredentialProvider` helper now has no callers.) Because the flow leaves the app, it holds `AdsGate.authFlowInProgress` across the whole hop so a returning user isn't shown an app-open ad mid-provision; on return it runs `updateDeviceMetadata()` then `provisionDekOrThrow()` (which signs back out if the DEK can't be provisioned — the same gate as OTP). Google sign-in skips the onboarding pages entirely (Clerk auto-provisions the account); like OTP success it emits no nav event — the auth observer swaps the tree, and the server-driven `serverSaysNoRecoveryCode` signal catches a brand-new Google account so it still gets the recovery-code screen.

<Note>
The active V2 flow uses the granular `AuthRepository` methods above (`checkAndStartV2`, `createSignUpAndSendOtpV2`, `verifySignInOtpV2` / `verifySignUpOtpV2`). The older combined `signInWithMagicLink` / `verifyOtpCode` methods are legacy V1 (marked `TODO V1-DELETE`); despite the "magic link" name the mechanism has always been a typed six-digit `email_code` OTP, never a tappable link.
</Note>
