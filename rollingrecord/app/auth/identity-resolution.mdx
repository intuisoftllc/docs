`IdentityRepository` (`data/repository/IdentityRepository.kt`) calls the `resolve-identity` Edge Function to upsert a `canonical_users` row for the caller and cache the server-echoed `auth_user_id` in `AuthUserStore` — the sync-readable `SharedPreferences` that every per-user-scoped singleton consults at Koin init to decide which user's directory to open.

## `resolveIdentity()`

`resolveIdentity(): String?` reads a stable caller id, POSTs it, caches the echoed id, and returns it — or returns null on any failure (network error, non-2xx, empty body). It is safe to call multiple times per launch; each call is a fresh round-trip.

The stable id it sends today is `RevenueCatManager.customerId`, **not** the Clerk identity. Per the class KDoc, this is the pre-auth arrangement (RR-137): the Clerk `sub` claim travels separately as the Bearer JWT on Edge Function calls, and post-auth the server will derive the canonical id from that verified JWT rather than trusting a body field. If the RC customer id isn't available yet (SDK not configured), the call logs and returns null.

An **account switch** — a different identity between launches — is detected by comparing the cached id against the server-echoed id. A mismatch logs an `"account switch detected"` warning and overwrites `AuthUserStore`; the local per-user wipe is an explicit TODO (a follow-up story), so today only the cached id changes. `IdentityRepository` does **not** call `UserSessionManager.switchTo` — that is driven by the `V2App` auth observer (and the legacy V1 `AppNavHost`).

## `resolve-identity` wire shape

The request and response DTOs live in `data/remote/dto/ResolveIdentityDto.kt`. The Retrofit method is `SupabaseApi.resolveIdentity` (`data/remote/SupabaseApi.kt`): `@POST "functions/v1/resolve-identity"` tagged `@EdgeTag(resolve-identity)`, returning `Response<ResolveIdentityResponse>`. It rides the `supabase` OkHttp client, so the App Check + Bearer JWT interceptors apply automatically — see [Auth Token Injection & Refresh](/rollingrecord/app/auth/jwt-interceptors).

| Symbol field | JSON key | Type | Meaning |
| --- | --- | --- | --- |
| `ResolveIdentityRequest.authUserId` | `auth_user_id` | `String` | Stable caller id sent today = `RevenueCatManager.customerId` |
| `ResolveIdentityResponse.authUserId` | `auth_user_id` | `String` | Server-echoed canonical id; cached in `AuthUserStore` |
| `ResolveIdentityResponse.status` | `status` | `String` | `canonical_users` upsert status |
| `ResolveIdentityResponse.cloudGraceStartedAt` | `cloud_grace_started_at` | `String?` (ISO 8601) | Timestamp the cloud-data deletion countdown began — set whenever the user stops holding a recurring cloud entitlement for ANY reason (expiry, plan switch down to a non-cloud tier, refund, revoke); null when they hold cloud now or never did |
| `ResolveIdentityResponse.cloudGraceTier` | `cloud_grace_tier` | `String?` | Which cloud tier's data is being preserved (`pro_cloud` / `pro_cloud_ai`); tailors banner copy |

The two `cloud_grace_*` fields are paired by a server-side `CHECK` constraint (both NULL or both non-NULL), so any populated pair is internally consistent. They are named for the deletion *window* rather than its cause on purpose: a user who switched from Pro+Cloud down to Pro has not "lapsed" — they are still paying — but their cloud data still has a deadline. The value is server-bounded, so a non-null pair always means "inside the window": the RevenueCat webhook clears it when cloud is regained and the daily sweeper clears it once the window closes. That is what lets the UI treat it as a banner on/off switch with no date math of its own.

## `GraceState` and the lapse banner

On every successful call, `resolveIdentity` refreshes an in-memory `GraceState?` from the grace fields, exposed as `graceState: StateFlow<GraceState?>`. `GraceState` is a `data class(lapsedAtEpochMs: Long, lapsedTier: String)` — the parse maps `cloudGraceStartedAt` → `lapsedAtEpochMs` and `cloudGraceTier` → `lapsedTier`, so only the DTO/JSON names changed in this commit; the `GraceState` field names are unchanged. Null means an active subscription **or** never-subscribed (banner hidden); non-null means the caller is inside the cloud-data deletion window, driving a tier-aware lapse banner with a day-count countdown. The window length is server-config-driven — the client reads `ServerConfig.cloudGraceDays` (folded from the `server_config.cloud_grace_days` row), not a hard-coded 30 — so the client counter matches the dial the server's sweeper acts on. It is deliberately not persisted — the server is the source of truth and is always called on launch, so a stale banner outliving a resubscribe would be worse than a brief cold-start gap. `cachedAuthUserId()` returns the last cached id via `AuthUserStore.getCurrentUserId`.

## Session isolation

`IdentityRepository` is an app-level Koin `single` (`di/RepositoryModule.kt`) — it tells the app *who* the user is, so it can't itself be user-scoped. Because it survives a session switch, it implements `UserScopedCache`; `clearForUserSwitch()` resets `graceState` to null so a prior user's lapse banner doesn't follow the next account for the life of the process. The banner also clears on resubscribe without any dedicated client path: the server returns a null `cloud_grace_started_at` on the next `resolveIdentity`, which sets `graceState` back to null.

## When it runs

On the active V2 surface, `resolveIdentity` runs **only on cold start**, launched from `App.onCreate` (`App.kt`) on `Dispatchers.IO` (comment: "Resolve RC customer ID → canonical user UUID"). The V2 sign-in observer in `V2App` does **not** call it — confirmed by the class KDoc: "which the V2 sign-in path does NOT call (only cold start does)". Only the legacy V1 `AppNavHost` additionally calls it at sign-in, awaiting the upsert before the new scope opens.

The actual session-scope swap that consumes the cached `auth_user_id` is `UserSessionManager.switchTo` (`data/session/UserSessionManager.kt`), invoked by the auth observer — see [Known Accounts / Account Switching](/rollingrecord/app/auth/known-accounts) for what that teardown does.
