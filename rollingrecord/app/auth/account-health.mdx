Account health is a client-only derived roll-up — never a server concept — that folds four independent local signals into one worst-case indicator surfaced as a small colored dot next to the user's name. The freeze arm is persisted and owner-stamped so it never bleeds across accounts.

## `AccountHealth` and the severity resolver

`AccountHealth` (`data/models/AccountHealth.kt`) is the enum `{ HEALTHY, OFFLINE, SUBSCRIPTION_LAPSED, SYNC_ERROR, FROZEN }`. The highest-severity active condition wins, and `HEALTHY` is the absence of every condition (no dot):

```
FROZEN > SYNC_ERROR > SUBSCRIPTION_LAPSED > OFFLINE > HEALTHY
```

There is one exception: **OFFLINE suppresses SYNC_ERROR**. A sync failure while the device has no connectivity is expected, not a real problem, so `SYNC_ERROR` only ever appears for an online device.

`AccountHealthState` is the `data class { health, frozenReason? }`. Its companion `from(frozen, frozenReason, syncError, subscriptionLapsed, offline)` is the pure severity resolver — the single place the precedence and the offline-suppresses-syncError rule live — with a `HEALTHY` sentinel.

## `AccountHealthProvider` — combining the signals

`AccountHealthProvider` (`data/repository/AccountHealthProvider.kt`) is **user-session-scoped** because it reads the per-user `SyncEngine`. It exposes `health: Flow<AccountHealthState>` (distinct-until-changed) combining the four real signals plus a debug-only `DevFlags` override, and `healthEnum: Flow<AccountHealth>` for callers that ignore the reason.

| State | Source signal | Dot color / opacity | Detail-sheet CTA |
| --- | --- | --- | --- |
| FROZEN | `AccountHealthRepository.frozenState` (persisted 403 `account_frozen`, owner-stamped) | `StatusFrozen`, full | Contact support (pre-filled email) |
| SYNC_ERROR | `SyncEngine.state` `isSyncError()` — only when ONLINE | `StatusError`, full | Retry sync |
| SUBSCRIPTION_LAPSED | `IdentityRepository.graceState` non-null — the recurring cloud subscription ended and the cloud data is inside the server's deletion grace window | `StatusWarning`, full | Manage subscription |
| OFFLINE | `ConnectivityMonitor.isOnline` inverted | `StatusWarning`, 0.45 alpha | none (informational) |
| HEALTHY | no condition active | no dot | none |

`isSyncError()` mirrors the V1 `SyncStatusViewModel` predicate exactly: `lastError` set, `lastAttemptAt` set, and `lastSuccessAt < lastAttemptAt`. The SUBSCRIPTION_LAPSED arm is `identityRepository.graceState.map { it != null }` — the provider no longer calls RevenueCat's lapse predicate at all. A non-null `GraceState` (from the `StateFlow<GraceState?>`) means the user's recurring cloud subscription ended and their cloud data is inside the server's deletion grace window; the value is bounded by construction, because the server clears the grace columns on resubscribe (via the RevenueCat webhook) and again when the window closes (the daily sweeper). The repoint exists because RevenueCat never removes an expired entitlement from `entitlements.all`, so its lapse predicate stays true forever after a single cancellation — the dot would otherwise announce "your subscription has ended" for the rest of the account's life, long after there was anything to act on.

The old RevenueCat predicate was moved, not deleted: the private `CustomerInfo?.isSubscriptionLapsed()` that used to live in `AccountHealthProvider` is now a shared top-level `CustomerInfo?.isSubscriptionLapsed()` (with a pure, unit-testable core `isSubscriptionLapsed(activeKeys, allKeysActive)`) in `RcEntitlement.kt` (`data/billing/RcEntitlement.kt`), consumed by the scheduled-recording lapse guard — not by account health anymore.

The provider also blends in a debug-only override: `DevFlags.forcedAccountHealth` / `DevFlags.forcedFrozenReason` (inert `null` in release, so R8 collapses the branch) let the dot, sheet, and CTAs be exercised without a real lapse / freeze / offline / sync failure.

## `AccountHealthRepository` — the persisted freeze signal

`AccountHealthRepository` (`data/repository/AccountHealthRepository.kt`) is **app-scoped** (a Koin `single`), backed by a DataStore file under `datastore/device/account_health`. It is app-scoped, not user-scoped, because the write side is `AccountFreezeInterceptor` — an OkHttp interceptor on the app-wide clients that fires on the dispatcher thread and must always reach a live instance.

The frozen flag is **owner-stamped** (`OWNER_USER_ID`): `frozenState` only reports frozen when the persisted owner matches the signed-in `authUserId`, so a frozen flag whose owner doesn't match is treated as not-frozen. `setFrozen(reason)` is called on a 403 `account_frozen`, `clearFrozen()` on any 2xx (proving the freeze gate was passed), `acknowledgeFrozen()` records that the user dismissed the full-screen overlay for the current freeze episode, and `reset()` wipes the row. The repository self-observes `AuthRepository.authState` and resets on every user-identity transition, so a different account never inherits the previous account's lock. `FrozenState` is the `data class { frozen, reason?, acknowledged }` with a `NOT_FROZEN` sentinel — `acknowledged` is the per-episode overlay-dismissed flag (see [The soft frozen overlay](#the-soft-frozen-overlay)).

Persisting the freeze means the dot appears on the next cold start without waiting for the first authed round-trip to re-discover the 403.

## Rendering — the dot and the detail sheet

`AccountStatusDot` (`ui/v2/components/AccountStatusDot.kt`) is a small filled circle drawn next to the name on both the main account card and the settings header card. It renders nothing for `HEALTHY` (callers guard on the same condition), and draws OFFLINE at a soft `OFFLINE_DOT_ALPHA` of 0.45 while every other state is full opacity.

Both account VMs read `AccountHealthProvider.health`: `AccountUiState.accountHealth` (main screen — glance-only, no sheet) and `AccountSettingsUiState.accountHealth` + `frozenReason` (settings). On the settings screen, tapping the header card when not `HEALTHY` opens `V2AccountHealthSheet` (`ui/v2/screens/accountsettings/components/V2AccountHealthSheet.kt`). The sheet mirrors the tapped dot, shows a plain-English title + body, and offers the per-state CTA from the table above; FROZEN centers its title, leads the admin reason with a snowflake glyph, and each CTA dismisses the sheet before firing. The FROZEN "Contact support" opens a pre-filled account-access email (`sendFrozenAccountSupportEmail`) — no support token is minted.

## The soft frozen overlay

`V2FrozenOverlay` (`ui/v2/screens/frozen/V2FrozenOverlay.kt`) is the full-screen notice shown when a signed-in account is detected frozen **while the local database still opens** — a returning device that already holds the per-user DEK, so the user keeps full local access. `V2App` draws it above the nav host, onboarding, and the permissions gate, but below App Lock and the version kill-switch: the gate is `sessionActive && sessionDbReady && !appLocked && !resolvingLock && frozenState.frozen && !frozenState.acknowledged`, so App Lock keeps full precedence and the overlay never bypasses it.

The overlay is informational, not a hard block. It paints the background opaque and consumes stray taps so nothing behind it receives input, leads with the `ic_snowflake` glyph in `StatusFrozen`, shows the generic `frozen_overlay_body` copy, and renders the admin `reason` in a muted card below **only** when the server actually sent one. Its single action is **OK**, which is deliberately disabled for the first `OK_DELAY_MS` (2000 ms) so the notice can't be dismissed reflexively, then enables. It is **not** auto-dismissed — the user still taps OK; only the button's enablement is time-gated.

Tapping OK calls `AccountHealthRepository.acknowledgeFrozen()`, which sets the per-episode `acknowledged` flag in the DataStore row so a cold-start relaunch within the same freeze episode doesn't re-nag. The flag is scoped to one freeze episode: `setFrozen()` never touches it (repeated 403s during a single freeze must not un-acknowledge), while `clearFrozen()` (an unfreeze via a 2xx) and `reset()` (sign-out / account switch) both wipe it, so a later refreeze or a fresh sign-in to a still-frozen account shows the overlay again.

<Note>
The soft overlay requires a local DEK — the database has to open for the app tree to exist beneath it. A **new** device signing into a frozen account has no local DEK and the DB can't open at all; that terminal case is handled one level up by `V2AccountFrozenScreen` (Contact support / Sign out, no "OK"). See [Database Recovery States](/rollingrecord/app/security/database-recovery).
</Note>

## The account-status legend sheet

`V2AccountStatusLegendSheet` (`ui/v2/screens/accountsettings/components/V2AccountStatusLegendSheet.kt`) is a reference guide to what every status dot means, opened by **long-pressing** the account header card on the [Account Settings](/rollingrecord/app/auth/account-settings) screen — at any status, including `HEALTHY`. The two gestures on the card never compete: a tap opens the current status's `V2AccountHealthSheet` (only when not `HEALTHY`), while the long-press (`onLongClick` in `V2AccountSettingsScreen.kt`) always opens this legend.

It is purely explanatory — it describes the state each dot represents, not how to resolve it (the live sheet owns the resolution CTA). It draws one `StatusRow` per state, least-severe first, each rendering the real `AccountStatusDot` so the legend matches exactly what the card shows (OFFLINE renders soft, etc.):

| Row | State | Dot |
| --- | --- | --- |
| Good standing | `HEALTHY` | hollow `Gray400` ring (the no-dot state) |
| Offline | `OFFLINE` | `AccountStatusDot`, soft (0.45 alpha) |
| Subscription lapsed | `SUBSCRIPTION_LAPSED` | `AccountStatusDot` |
| Sync error | `SYNC_ERROR` | `AccountStatusDot` |
| Frozen | `FROZEN` | `AccountStatusDot` |

"Good standing" leads so the normal no-dot state is explained too; because `HEALTHY` draws no dot on the card, its row shows a hollow ring of the same size instead. The sheet uses the standard V2 chrome (`cardMuted` container, 34dp top corners, `Gray400` drag handle) and closes via a Close button or dismiss.

## Lapse, grace, and quota banners

The lapse/grace/quota surfaces render on the [Account Settings](/rollingrecord/app/auth/account-settings) screen, not on the dot itself. `V2GraceBanner` and `V2QuotaBanner` (`ui/v2/screens/accountsettings/components/V2CloudPressureBanners.kt`) and `V2LapsedAccessNotice` (`ui/v2/screens/accountsettings/components/V2LapsedAccessNotice.kt`) are the cards; grace state comes from `IdentityRepository.graceState` (a `StateFlow<GraceState?>` carrying the lapse timestamp and paid tier). Exactly one lapse card shows — the cloud grace countdown wins over the quieter `SUBSCRIPTION_LAPSED` notice — and `V2QuotaBanner` opens the free-up-space sheet.
